# 儲存封存 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在 `src/storage/` 加上封存：讀取備份時檢查時間欄位的格式；全域的封存索引表；封存前在記憶體讀回驗證的 `prepareArchive` 與核對更新時間、局名後單一交易刪除明細並寫入索引的 `archiveGame`；封存清單、從封存還原時核對驗證摘要的 `readArchive` 與移除索引（需求規格 12.1、12.3、DATA-09、DATA-20～23，技術設計 4.3「封存」「讀取與驗證」「危險區」）。

**Architecture:** 儲存子計畫 3 拆成四塊，本計畫是最後一塊（3-1 備份與還原 → 3-2 檢查點與回溯 → 3-3 瀏覽器整合 → 3-4 封存）。封存分成兩個呼叫，中間由畫面下載並取得使用者確認：`prepareArchive` 匯出並以 `readBackup` 讀回驗證，回傳準備好的封存（封存檔、索引、快照當下的更新時間）；`archiveGame` 在一個 rw 交易內核對更新時間，再以既有的 `deleteGame` 核對局名並刪除整局與檢查點，最後寫入索引。索引存在新的全域表 `archives`（主鍵是原遊戲局的識別），不屬於 `GAME_TABLES`。從封存還原是 `readArchive`（`readBackup` 加上驗證摘要的核對）接既有的 `restoreBackup`，索引保留。新程式都在 `src/storage/archives.ts`；畫面還沒有，確認畫面、清單與還原的選檔由畫面計畫接上。core 不改。

**Tech Stack:** TypeScript（strict）、Dexie 4、Vitest（`node` 環境）、fake-indexeddb；瀏覽器內建的 `CompressionStream`、`DecompressionStream`、Web Crypto（沿用 `exportBackup`、`readBackup`）。不新增套件。

**技術設計 4.3 資料表、整局資料、讀取與驗證、還原、寫入操作與危險區**

> - 資料表依需求規格的實體劃分（見下方「資料表」）。索引照需求規格 12.5；除了全域的 `meta` 與封存索引 `archives`，每張表都帶遊戲局欄位，所有查詢以遊戲局為前提。識別用 `crypto.randomUUID()` 產生的字串（12.2）。IndexedDB 不能以布林值建立索引，要查詢的狀態存成字串。

> | `archives` | 一筆封存索引（需求規格 12.3） | 原遊戲局的識別、局名、封存檔的應用版本與結構版本、起始年與目前遊戲年、匯出時間、檔名、各表筆數、SHA-256；全域，不屬於任何一局，也不屬於 `GAME_TABLES`（見「封存」） |

> - **整局資料**：`GAME_TABLES` 列出一局的資料表，匯出、還原、回溯、檢查點的內容、刪除與計算筆數都用這份清單。不屬於一局資料的表明示排除：全域的 `meta`，檢查點的兩張表（備份不含檢查點，回溯要清掉整局資料而留下檢查點，刪除一局時另外刪），以及封存索引 `archives`（不屬於任何一局，局刪除後保留）；測試確認每一張表不是在 `GAME_TABLES`，就是在排除清單裡，之後加表時一併更新（使用者 2026-09-29 決定）。讀出整局在單一唯讀交易內完成，得到一致的快照（需求規格 12.2）。
> 7. 欄位：集合剛好是 `GAME_TABLES`，多或少都拒絕；每一列是物件，主鍵欄位存在且型別正確，遊戲局欄位等於這一局；`games` 與 `settings` 各一列；`games` 那一列另外驗證儲存層會取用的欄位：局名、建立與更新時間是字串，起始年與目前遊戲年是整數（使用者 2026-09-29 決定）；遊戲局摘要與 `games` 那一列一致。時間欄位（匯出時間，以及 `games` 那一列的建立與更新時間、有值時的最近備份時間）要是 `toISOString()` 格式的字串，備份提醒以它們計算：`new Date(值)` 有效，而且轉回 `toISOString()` 與原字串完全相同；最近備份時間的欄位存在就檢查，`null` 也不符（使用者 2026-09-30 決定；儲存子計畫 3-4 實作）。其他欄位不逐欄驗證型別與列舉值：檔案完整性由雜湊保證，全面驗證要隨每次改表同步。
> - **還原**：一律還原成新遊戲局（需求規格 12.2），在一個 rw 交易內寫入全部資料表，失敗時整筆回復。
> - **一個操作一個交易**：每個操作在一個 rw 交易內完成：先讀遊戲局確認存在，再從資料列重新組出核心的輸入並重做檢查，最後寫入資料列與事件，並把遊戲局的更新時間設為現在、應用版本設為目前版本（見「備份與還原」）。設定、代表色這類不寫事件的操作也更新，備份提醒（需求規格 12.2）以此判斷有沒有未備份的變更。操作可以包進呼叫端的外層交易（Dexie 的巢狀交易），CE 匯入以此在單一交易內套用多個操作（4.4）。
> - **永久刪除此局**：輸入的局名去掉前後空白後要等於局名，否則阻止，什麼都不刪；名稱核對放在儲存層，畫面漏掉也刪不掉。在一個 rw 交易內從 `GAME_TABLES` 刪除這一局的資料列，連同這一局的檢查點與內容（需求規格 12.4，使用者 2026-09-29 決定）；`meta` 的目前遊戲局指向這一局時一併清除，由畫面請使用者重新選局。不寫事件，因為這一局已不存在。回傳刪除的各表筆數；找不到遊戲局時丟出錯誤。
> - **刪除全部存檔**：輸入的文字要是「刪除全部存檔」，否則阻止；第二道確認由畫面負責（需求規格 12.1，使用者 2026-09-29 決定）。在一個交易內清空資料庫的每一張表（含 `meta`），檢查點的兩張表也包含在內；只保留 `meta` 的備份資料夾，它是管理器的設定，不是存檔（需求規格 12.1、DATA-19，使用者 2026-09-30 決定）。封存索引一併清除：它記的是被封存的局，不是管理器的設定；封存檔在外部，仍可用匯入備份還原（需求規格 12.1、DATA-23，使用者 2026-09-30 決定）。回傳刪除的遊戲局數與總筆數；總筆數只算 `GAME_TABLES`，不含檢查點（使用者 2026-09-29 決定）。

**技術設計 4.3「封存」（全文）**

> #### 封存
>
> 封存舊遊戲局與封存索引（需求規格 12.3）由儲存子計畫 3-4 負責，沿用「備份與還原」的匯出、讀取與驗證、還原，刪除沿用「危險區」的永久刪除此局（使用者 2026-09-30 決定）。流程拆成兩個呼叫，中間由畫面下載並取得使用者確認。
>
> - **準備**：`prepareArchive` 先確認瀏覽器有 `CompressionStream`，沒有時回傳拒絕（`compression-unsupported`），什麼都不讀：封存檔一律是 `.json.gz`，不比照備份改存 `.json`（需求規格 12.3，使用者 2026-09-30 決定）。接著以「匯出」匯出這一局（遊戲局不存在時丟出錯誤），再以「讀取與驗證」在記憶體讀回同一份位元組（解壓、雜湊、欄位、重複、關聯與筆數），不通過時原樣回傳拒絕原因，不丟例外。通過時回傳準備好的封存：匯出的備份（畫面拿去下載，重新下載也用它）、封存後要寫入的索引列，以及快照當下遊戲局的更新時間（取自驗證過的檔案裡 `games` 那一列，與快照是同一個時間點）。只讀。
> - **確認**：畫面以 `downloadBackup` 下載，使用者勾選已下載並輸入局名；確認前以 `listCheckpoints` 顯示將一併刪除的檢查點個數，含釘選的（需求規格 12.3）。頁面無法得知使用者有沒有存檔（同「瀏覽器整合」的下載），這一步由畫面負責；儲存層保證沒通過驗證就拿不到準備好的封存，局名不符或有異動就刪不掉（DATA-09、DATA-20）。
> - **封存**：`archiveGame` 在一個 rw 交易內（`GAME_TABLES`、`meta`、檢查點的兩張表與 `archives`）：遊戲局的更新時間要等於準備時的值，否則阻止（`changed-since-archive`），什麼都不刪，由畫面請使用者重新產生（需求規格 12.3「封存後有異動須重新產生」）；接著呼叫「永久刪除此局」（成為子交易），局名不符時阻止（`name-mismatch`），通過時刪除整局、這一局的檢查點與內容，`meta` 的目前遊戲局指向這一局時一併清除；最後寫入索引。回傳索引與刪除的各表筆數。不寫事件，因為這一局已不存在。遊戲局已不存在時丟出錯誤（例如同一份封存送出兩次）。每個寫入操作都會更新遊戲局的更新時間（見「寫入操作」），所以核對更新時間就能發現異動；自動備份的 `recordBackup` 與建立檢查點都不改更新時間，不會擋下封存：前者只改檔案裡的最近備份時間，還原時會改成匯出時間，後者建立的檢查點隨這一局刪除。
> - **交付**：只用下載，不寫備份資料夾：封存檔是本機刪除後唯一的一份，要由使用者自己放到長期保存的位置；寫進資料夾會與自動備份混在一起，「確認已下載」也要多一種說法（使用者 2026-09-30 決定）。
> - **索引**：`archives`（主鍵 `id`）是全域的表，不帶遊戲局欄位，不屬於 `GAME_TABLES`（見「整局資料」）：備份與檢查點不含它，永久刪除此局不碰它，刪除全部存檔時清除（見「危險區」）。一列記：`id` 為原遊戲局的識別（封存後原局已刪除，還原一律換新識別，所以不會重複，也查得到來源）、局名、封存檔的應用版本與結構版本（結構版本決定之後讀不讀得了）、起始年與封存時的目前遊戲年（年份範圍）、封存檔的匯出時間（也是檔名裡的時間）、檔名、各表筆數（總筆數由它加總，不另存），以及驗證摘要：封存檔裡的 `sha256`，與檢查點核對內容的方式相同（需求規格 12.3，使用者 2026-09-30 決定）。
> - **從封存還原**：`listArchives` 列出全部索引，依匯出時間由新到舊。`readArchive` 以「讀取與驗證」讀使用者選的檔案（可傳進度回呼），拒絕原因原樣回傳；檔案的 `sha256` 與索引不同時拒絕（`archive-mismatch`，選錯檔案）；通過時回傳驗證過的備份，畫面再以「還原」還原成新遊戲局，還原來源記下檔名等資訊。還原不消耗封存檔，可以重複還原，所以索引保留；`removeArchive` 只刪索引，不影響檔案，要不要先確認由畫面決定。找不到索引時兩者都丟出錯誤（DATA-21，使用者 2026-09-30 決定）。封存檔本身就是備份檔，沒有索引時（例如刪除全部存檔之後）也能走一般的匯入備份還原。
> - **測試**：Vitest 以 `vi.stubGlobal` 拿掉 `CompressionStream`，或換成會截斷輸出的假串流，讓讀回驗證失敗。封存的下載就是既有的 `downloadBackup`，不是由點擊直接觸發的下載已在 3-3 驗證（第 7 節「儲存整合的驗證」），所以不加端對端測試，也不另做 Edge 手動驗證（使用者 2026-09-30 決定）。

## 本計畫的詮釋

需求規格與技術設計沒有逐字寫出、由本計畫決定的地方。技術設計 4.3「封存」已經和使用者確認；下面是本計畫在程式層級的決定，審查時請逐條對照上一節的原文。

1. **時間格式**（Task 1）：「`toISOString()` 格式的字串」以私有的 `isIsoTime` 判斷：是字串、`new Date(值)` 是有效時間，而且 `toISOString()` 轉回來與原字串完全相同。檢查放在 `games` 那一列型別檢查之後、遊戲局摘要比對之前，先查匯出時間（拒絕的位置是 `exportedAt`），再依序查建立、更新與最近備份時間（`collections.games[0].<欄位>`）。「有值時的最近備份時間」指欄位不是 `undefined`，也就是 JSON 裡有這個鍵：`null` 也要檢查，並且不符。還原來源（`restoredFrom`）的匯出時間不在第 7 步的清單內，不檢查。管理器寫出的時間一律是 `toISOString()`，所以既有的備份與檢查點不受影響。
2. **資料表與型別**（Task 2）：`ArchiveRow` 放在 `records.ts`，`counts` 的型別是 `game-data.ts` 的 `RowCounts`（只有型別引用，執行時沒有循環）。`archives` 只以主鍵 `id` 建索引：清單在記憶體依匯出時間排序，筆數是封存過的局數。`database.test.ts` 的資料表清單與 `game-data.test.ts` 的 `EXCLUDED_TABLES` 加上 `archives`。`deleteAllGames` 的程式不改（本來就清空每一張表，只寫回備份資料夾），只改說明，並在「清空每一張表」的測試多寫一筆索引釘住。測試助手 `archiveRow(id, fields?)` 產生各表 0 筆的索引。
3. **準備封存**（Task 2）：先以 `typeof CompressionStream !== 'function'` 判斷，不支援時回傳拒絕，連遊戲局存不存在都不讀。沒有 `DecompressionStream` 時由 `readBackup` 回傳 `gzip-unsupported`，原樣回傳，一樣拿不到準備好的封存。索引的欄位取自驗證過的檔案（局名、起始年與目前遊戲年取檔案的遊戲局摘要；應用版本、結構版本、匯出時間、筆數與 `sha256` 取檔案本身），檔名取匯出的檔名；應用版本是封存檔的（目前版本），不是遊戲局那一列最後寫入的版本。不另外核對檔案的 `sha256` 與編碼時的值：`readBackup` 已從解壓後的內容重算雜湊，驗證的位元組就是交給畫面下載的那一份。
4. **封存**（Task 2）：先核對更新時間、再核對局名，兩者都不符時只回報 `changed-since-archive`（要重新產生，局名也要重新輸入）。局名核對（去除前後空白）與刪除的內容完全沿用 `deleteGame`（外層交易的子交易），`archiveGame` 回傳的筆數就是它刪除的筆數；寫入索引在 `deleteGame` 通過之後，所以阻止時不會留下索引。同一份封存再送一次時，`loadGame` 丟出「找不到遊戲局」。
5. **清單、讀取與移除**（Task 3）：`listArchives` 以匯出時間的字串比較排序（都是 `toISOString()`，可以直接比較）。`readArchive` 先讀索引（找不到時丟出錯誤），再以 `readBackup` 讀檔並傳入進度回呼；通過時回傳 `readBackup` 的結果本身。不另外核對檔案的遊戲局識別：驗證摘要相同就是同一份內容。還原直接用既有的 `restoreBackup`，不另外包裝。`removeArchive` 在一個 rw 交易內先確認索引存在再刪除。
6. **驗收**（Task 4）：DATA-09 的「未驗證」以沒有 `DecompressionStream`（讀回時解不開）代表，「未確認下載」以沒有輸入局名代表，勾選框由畫面負責；DATA-20 的異動以 `setCurrentYear` 代表；DATA-23 確認索引被清除，封存檔仍可用 `readBackup`、`restoreBackup` 還原。

```ts
import { exportBackup, readBackup, type BackupRejection, type ExportedBackup } from './backup'
import type { WPStudBookDatabase } from './database'
import { gameTables, type RowCounts } from './game-data'
import { deleteGame, loadGame, type DeleteGameBlock } from './games'
import type { ArchiveRow } from './records'
import type { WriteResult } from './writes'

// 封存舊遊戲局與封存索引（需求規格 12.3，技術設計 4.3「封存」）

/**
 * 準備封存的拒絕原因：讀回驗證的拒絕原因（BackupRejection），另加
 * - compression-unsupported：瀏覽器沒有 CompressionStream；封存檔一律是 .json.gz，不改存 .json
 */
export type ArchiveRejection = BackupRejection | { kind: 'compression-unsupported' }

/** 準備好的封存：由 prepareArchive 在驗證通過後產生 */
export interface PreparedArchive {
  /** 封存檔：畫面以 downloadBackup 下載，重新下載也用它 */
  backup: ExportedBackup
  /** 封存後寫入的索引 */
  index: ArchiveRow
  /** 快照當下遊戲局的更新時間；封存時核對 */
  updatedAt: string
}

export type ArchivePrepareResult =
  { status: 'ok'; archive: PreparedArchive } | { status: 'rejected'; reason: ArchiveRejection }

/**
 * 準備封存（需求規格 12.3、DATA-09、DATA-22）：沒有 CompressionStream 時拒絕，什麼都不讀。
 * 以 exportBackup 匯出，再以 readBackup 在記憶體讀回同一份位元組（解壓、雜湊與內容的驗證），
 * 不通過時原樣回傳拒絕原因。索引的欄位取自驗證過的檔案；更新時間取自檔案裡 games 那一列，與快照同一個時間點。
 * 只讀，不觸發下載：畫面下載、取得使用者確認後，再以 archiveGame 移除本機明細。遊戲局不存在時丟出錯誤
 */
export async function prepareArchive(
  db: WPStudBookDatabase,
  gameId: string,
  now: Date = new Date(),
): Promise<ArchivePrepareResult> {
  if (typeof CompressionStream !== 'function') {
    return { status: 'rejected', reason: { kind: 'compression-unsupported' } }
  }
  const backup = await exportBackup(db, gameId, now)
  const read = await readBackup(backup.bytes)
  if (read.status === 'rejected') return read
  const { file } = read.backup
  const index: ArchiveRow = {
    id: file.game.id,
    name: file.game.name,
    appVersion: file.appVersion,
    schemaVersion: file.schemaVersion,
    startYear: file.game.startYear,
    currentYear: file.game.currentYear,
    exportedAt: file.exportedAt,
    fileName: backup.fileName,
    counts: file.counts,
    sha256: file.sha256,
  }
  const { updatedAt } = file.collections.games[0]!
  return { status: 'ok', archive: { backup, index, updatedAt } }
}

/**
 * 封存的阻止原因：
 * - changed-since-archive：準備之後這一局有變更，封存檔不含這些變更，要重新產生（DATA-20）
 * - name-mismatch：輸入的局名不符（同永久刪除此局）
 */
export type ArchiveBlock = { kind: 'changed-since-archive' } | DeleteGameBlock

/** 封存的結果：寫入的索引與刪除的各表筆數 */
export interface ArchivedGame {
  archive: ArchiveRow
  counts: RowCounts
}

/**
 * 封存（需求規格 12.3、DATA-09、DATA-20）：畫面下載封存檔、使用者確認已下載並輸入局名後呼叫。
 * 在一個 rw 交易內：遊戲局的更新時間要等於準備時的值，否則阻止，什麼都不刪；接著以 deleteGame
 * 核對局名（不符時阻止）並刪除整局、這一局的檢查點與目前遊戲局的指向；最後寫入索引。不寫事件。
 * 遊戲局不存在時丟出錯誤（例如同一份封存送出兩次）
 */
export async function archiveGame(
  db: WPStudBookDatabase,
  prepared: PreparedArchive,
  typedName: string,
): Promise<WriteResult<ArchivedGame, ArchiveBlock>> {
  const { index } = prepared
  const tables = [...gameTables(db), db.meta, db.checkpoints, db.checkpointContents, db.archives]
  return db.transaction('rw', tables, async () => {
    const game = await loadGame(db, index.id)
    if (game.updatedAt !== prepared.updatedAt) {
      return { status: 'blocked', blocks: [{ kind: 'changed-since-archive' }] }
    }
    const deleted = await deleteGame(db, index.id, typedName)
    if (deleted.status !== 'done') return deleted
    await db.archives.add(index)
    return { status: 'done', value: { archive: index, counts: deleted.value }, warnings: [] }
  })
}

/** 全部封存索引，依匯出時間由新到舊 */
export async function listArchives(db: WPStudBookDatabase): Promise<ArchiveRow[]> {
  const rows = await db.archives.toArray()
  return rows.sort((a, b) => b.exportedAt.localeCompare(a.exportedAt))
}

/**
 * 從封存還原前讀取檔案的拒絕原因：備份的拒絕原因（BackupRejection），另加
 * - archive-mismatch：檔案的 sha256 與索引的驗證摘要不同，選錯檔案（DATA-21）
 */
export type ArchiveReadRejection = BackupRejection | { kind: 'archive-mismatch' }

export type ArchiveReadResult =
  { status: 'ok'; backup: VerifiedBackup } | { status: 'rejected'; reason: ArchiveReadRejection }

/**
 * 讀取使用者為這一筆封存索引選的檔案（需求規格 12.3、DATA-21）：以 readBackup 驗證（可傳進度回呼），
 * 拒絕原因原樣回傳；檔案的 sha256 與索引不同時拒絕。通過時回傳驗證過的備份，由畫面以 restoreBackup
 * 還原成新遊戲局；索引保留，封存檔可以重複還原。只讀；找不到索引時丟出錯誤
 */
export async function readArchive(
  db: WPStudBookDatabase,
  archiveId: string,
  bytes: Uint8Array<ArrayBuffer>,
  options: ReadBackupOptions = {},
): Promise<ArchiveReadResult> {
  const index = await loadArchive(db, archiveId)
  const read = await readBackup(bytes, options)
  if (read.status === 'rejected') return read
  if (read.backup.file.sha256 !== index.sha256) {
    return { status: 'rejected', reason: { kind: 'archive-mismatch' } }
  }
  return read
}

/**
 * 移除封存索引（需求規格 12.3、DATA-21）：只刪這一筆索引，封存檔不受影響；要不要先確認由畫面決定。
 * 找不到索引時丟出錯誤
 */
export async function removeArchive(db: WPStudBookDatabase, archiveId: string): Promise<void> {
  await db.transaction('rw', db.archives, async () => {
    await loadArchive(db, archiveId)
    await db.archives.delete(archiveId)
  })
}

/** 讀取封存索引；找不到時丟出錯誤 */
async function loadArchive(db: WPStudBookDatabase, archiveId: string): Promise<ArchiveRow> {
  const index = await db.archives.get(archiveId)
  if (!index) throw new Error(`找不到封存索引：${archiveId}`)
  return index
}
```
