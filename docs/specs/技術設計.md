# WPStudBook 技術設計

## 1. 文件資訊

- 對應需求：[需求規格](需求規格.md)
- 最後更新：2026-09-29

## 2. 決策摘要

| 項目 | 決定 | 主要理由 |
| --- | --- | --- |
| 成品形式 | 單一 HTML 檔，以 `file://` 在 Windows 最新版 Edge／Chrome 離線使用 | 免安裝、工具鏈最單純；資料安全以備份強化補足（需求規格 12.2） |
| 語言 | TypeScript（strict） | 規則、匯入與畫面同一種語言 |
| 前端框架 | Vue 3（`<script setup>`）＋Pinia＋Vue Router（hash 模式） | 模板接近 HTML、狀態管理直覺、生態成熟；`file://` 只能用 hash 路由 |
| 可及性元件、大清單 | Reka UI、TanStack Virtual | 對話框、頁籤、清單已處理鍵盤與焦點；匯入預覽與清單需要虛擬捲動 |
| 建置 | Vite＋`vite-plugin-singlefile` | JS、CSS 全部內嵌，輸出 `WPStudBook.html` |
| 資料庫 | IndexedDB＋Dexie | 結構版本升級、複合索引、批次寫入與交易 |
| 測試 | Vitest、`fake-indexeddb`、Vue Test Utils、Playwright | 核心與資料庫層在 Node 測；端對端以 `file://` 開建置出的單檔 |
| 程式風格 | ESLint（Vue、TypeScript 規則）＋Prettier | |
| 執行環境 | Node 24、npm | 本機已安裝；`package-lock.json` 納入版控 |

瀏覽器內建能力直接使用，不加套件：CP932 解碼（`TextDecoder`）、gzip（`CompressionStream`）、SHA-256（`crypto.subtle`）。只有測試用的 CP932 範例檔需要在 Node 產生，因此加入開發用套件 `iconv-lite`。

## 3. 考慮過但未採用

- **桌面版（WPF＋WebView2 或 MAUI HybridWebView）**：好處是資料存成本機檔案、可監看 CE 匯出資料夾、可用 SQLite 查詢。未採用的原因：一年只匯入 4～5 次，拖放檔案不麻煩；單局幾萬筆資料在瀏覽器記憶體內計算就夠快；真正的差別只剩資料安全，改以需求規格 12.2 的持久保存與自動備份處理。桌面版還要重寫需求規格第 12、14 章，並多一套 .NET 工具鏈。日後若改走桌面，建議 WPF＋Blazor Hybrid（規則、資料、畫面全用 C#），不建議 MAUI（只用 Windows 時多出 WinUI 3 與打包的複雜度）。
- **React**：生態與可及性元件（React Aria）最完整，但 hooks 的依賴陣列與重複渲染較容易出錯，程式也較不像 HTML。
- **Svelte 5**：程式碼最少，但生態較小，寫法與一般 HTML 差異較大。

## 4. 架構

### 4.1 模組與依賴方向

| 模組 | 路徑 | 責任 | 可依賴 |
| --- | --- | --- | --- |
| 核心 | `src/core/` | 領域模型與規則，全部是作用於一般資料的純函式 | 無（不得引用 Vue、Dexie、DOM 或其他 `src` 模組） |
| CE 匯入 | `src/ce-import/` | 匯出檔解碼、解析、驗證、身分比對、差異預覽、產生套用計畫 | `core` |
| 儲存 | `src/storage/` | Dexie 資料庫、套用計畫的單一交易寫入、檢查點、備份與還原、持久保存、備份資料夾 | `core` |
| 畫面 | `src/ui/` | Vue 元件、頁面、Pinia store、路由 | 以上全部 |
| 進入點 | `src/main.ts` | 建立 Vue 應用、開啟資料庫、申請持久保存 | 以上全部 |

依賴方向以 ESLint 的 `no-restricted-imports` 強制：`core` 不得引用其他模組；`ce-import` 與 `storage` 只能引用 `core`；沒有模組可以引用 `ui`。

### 4.2 核心的內容

- 系位置、建系分支與新系編號（需求規格 7.3）、兩兩互換配對表（4.3）。
- 產駒的系與代數，替代母馬以她替代的代數計（8.2）。
- 任務產生：可開啟的分支、循環任務、世代交接（7.3、7.4）；斷血補系的補公系配對、補母系、暫停與結束，以及宣告補系前的檢查（7.6）。
- 規則檢查：阻止（10.3）、警告並確認（8.3、10.2）、零代種牡馬例外補入（7.3）。
- 血統推算：3 代前 8 匹祖先、推定父親的系統與始祖例外、4 代內重複（10.2），以及活血種數與「至少 N 種」的判斷（4.3、10.2）。
- 系統對照表查詢：子系統的親系統與分出來源、八系親系統的種類數與重複（7.2）。
- 同一匹馬的判斷（6.2）；姊妹接替狀態與代的成立（8.9、8.2）；母馬的定年、高齡與出售母親提醒，以及是否列入任務（8.5）。
- 種牡馬的兄弟比較、選定現任、替換時的系統比對與年齡提醒（7.7）；正式後繼的核對（9.6）。
- 產駒的追蹤名與 `サ`（9.3、9.4）。
- 馬名、能力番号與系統名稱的正規化（6.4、6.2、11.1），手動輸入與 CE 匯入共用。

`docs/specs/八系巡迴圖.html` 裡的配對與血統推算是這部分的參考實作，移入核心時改寫成 TypeScript 並補上測試。

#### 規則輸入快照

核心不定義資料表結構，也不保存狀態。規則以「規則輸入快照」為輸入，快照由儲存層依資料表彙整：

- 八個系位置各一筆：是否已開啟（建系起點或建立新系時已填寫系統與零代市場種牡馬，需求規格 7.1），以及各代種牡馬狀態與各代母馬群。
- 種牡馬狀態每（系, 代）一個值（需求規格 7.7）：在崗；已指定但還沒正式供用（尚未誕生、競走中、已引退待指定）；已離場，指退出生產行列或已引退、而且同一代沒有其他在崗或已指定的種牡馬。
- 母馬群每（系, 代）一筆：是否已成立（第一匹自家母駒以暫定或正式保留轉入，需求規格 8.2，依 `establishesGeneration` 判斷；只有替代母馬時為未成立）、列入任務的母馬數（依 `mareListedInTasks`：在繁殖圈內、未達定年，自家母駒還要是暫定保留、候選或正式保留），以及其中的自家母馬數（建立新系時由使用者判斷自家母馬是否不足，需求規格 7.3；不得多於列入任務的母馬數）。母馬歸哪個母馬群依 `damPlacement`：自家母駒依出生紀錄的系與代數，替代母馬依她替代的系與代數，起點母馬歸第 1 系起點母馬群；待指定用途的市場母馬（需求規格 8.4）與自由配種所生的母駒（11.5）不屬於任何母馬群，不計入。
- 第 1 系 0 代母馬群就是第 1 系起點母馬群。
- 已宣告的斷血補系（需求規格 7.6）：每系一份清單，每筆是斷血的代數與斷掉的一方（公系或母系）；補公系另帶補入的零代市場種牡馬狀態（與種牡馬狀態同樣三種，還沒選定時留空）。代數要在該系成立的代數以後，同一系同一代同一方只有一筆；使用者更正（撤銷）宣告時從清單移除。補入的零代市場種牡馬不放進該系的種牡馬狀態，零代那一格仍是建系時的零代市場種牡馬。補系結束後這一筆仍留在清單，因為補公系配對永久取代一般配對。補入的零代市場種牡馬依 7.7 提前引退並替換時，狀態取替換後那一匹，比照零代那一格。補公系配對產出 4 代以內（建系期）時，補入的零代市場種牡馬算 10.2 的建系期市場種牡馬，血統樹的建系期標記為是；循環期補入的不算（使用者 2026-09-24 決定）。
- 系統對照表：每個子系統一筆，含親系統與選填的分出來源；分出來源只用在始祖例外（10.2）。
- 八系目前的系統：每個系位置的目前子系統與親系統，系尚未開啟時兩者都沒有值。
- 血統樹：一次配種往上四代，每個位置是一匹馬或「沒有內部紀錄」。每匹馬帶內部識別（判斷 4 代內重複）、馬名（判斷始祖例外，10.2）、本身的父系，以及是不是建系期的市場馬（零代市場種牡馬或替代母馬，10.2 的例外判斷用）。
- 零代市場種牡馬的父系欄留空時，儲存層彙整快照時改填該系目前的子系統（需求規格 10.2）；核心只看快照裡的父系，不另外查系位置。

#### 任務看板的判斷

以下是需求規格 7.3、7.4、7.6、7.7 的詮釋，`src/core/board.ts` 依此實作：

- **到達某代**：該系該代有種牡馬紀錄（任何狀態），或該代母馬群已成立。只有替代母馬的母馬群不算。
- **可開啟的分支**：新系尚未開啟，且原系到達分支前一代。建系起點在第 1 系開啟前一直可開啟。
- **任務出現**：建系起點與建立新系在該系開啟後出現；推進原系在原系到達前一代時出現；循環任務在該系前一代有種牡馬紀錄、而且配對系前一代母馬群已成立時出現。
- **任務結束**：同系下一代任務已出現，而且這條任務的母馬群已沒有列入任務的母馬，或種牡馬已離場。
- **沒有下一代任務時**：母馬群已成立但沒有母馬，顯示「已成立，母馬群待補」；種牡馬已離場，任務暫停並顯示缺少現任種牡馬（零代時為缺少目標種牡馬）。
- 指定配種檢查只比對系與代數；種牡馬是否為現任，由任務看板的種牡馬狀態判斷。
- **補公系**：第 p 系 N 代宣告補公系後，第 p 系 N+1 代的指定配對固定為補公系配對（`restorationPairing`：第 p 系零代 × 原本指定的配對系 N 代母馬群），補系結束後也一樣。補公系任務宣告後就出現，種牡馬狀態看補入的零代市場種牡馬；世代交接照一般規則，所以斷血那一代的重試任務在原本的種牡馬離場或母馬全部離圈時結束。
- **補母系**：第 q 系 N 代宣告補母系後，配它的循環任務不等母馬群成立，配對系 N 代有種牡馬紀錄就出現。
- **補系進行中與結束**：補公系進行中，該系還沒開啟的分支都不能開啟；補母系不暫停。補公系在第 p 系 N+1 代有種牡馬紀錄（任何狀態）時結束，補母系在補系任務產出的那一代母馬群成立時結束；結束只解除暫停。看板列出每筆補系的補系任務與是否進行中。
- **宣告補系的檢查**（`checkRestoration`）：該系還沒開啟、那一代還沒成立、同一代同一方已經宣告，都阻止。補公系另外阻止：該系還沒到達那一代（沒有種牡馬紀錄，母馬群也沒成立）、那一代已有在崗或已指定的種牡馬、下一代已有種牡馬紀錄；那一代的種牡馬已離場時不阻止。補母系另外阻止那一代母馬群已成立。

#### 身分、母馬、種牡馬與後繼

以下是需求規格 4.6、6.2、7.6、7.7、8.1、8.5、8.9、9.3、9.4、9.6 在核心的輸入約定，以及規格沒有逐字寫出、由核心決定的判斷。儲存層與匯入層依此彙整輸入：

- **同一匹馬**（`identity.ts`）：只傳目前遊戲局的馬匹，馬番号不參與判斷。能力番号由匯入層與手動輸入統一寫法後保存與比對，`0x0000` 是有效值。馬名與父母名稱用基本馬名；還不是正式馬名的名稱（四月的「母馬名の0歳」、未命名的產駒）不傳。手動輸入、尚未經匯入確認的馬名要標 `manualName`：只用來輔助配對，與匯入名稱不同時不算衝突，由匯入名稱取代（需求規格 6.4、9.4、BRD-09）；經匯入確認的馬名不同時仍是衝突（ID-08）。兩邊都有值而且不同才算「明顯不符」，比較時忽略前後空白。以馬名輔助配對時，候選是馬名相符、出生年相同或未填的紀錄；候選兩筆以上，或能力番号與出生年配到兩筆以上，都列為衝突（需求規格 11.5「無法判斷的身分列入衝突」）；輔助配對到的紀錄父母明顯不符也是衝突；以馬名配到的紀錄已有不同的能力番号時也是衝突，不得覆寫。同一匯入檔內重複的能力番号由 `duplicateAbilityNumbers` 列出，只看能力番号、不看出生年，有任何一個時整份停止套用。一月總表以父馬、母馬、出生年配對舊產駒（11.3）屬於匯入層。
- **名稱與番号的正規化**（`identity.ts`、`systems.ts`）：`splitHorseName` 去掉開頭的 `(外)` 或 `[地]` 得到基本馬名，只有前綴、沒有馬名時表示資料異常（需求規格 6.4）。`normalizeAbilityNumber` 忽略前後空白，把 `0x` 加 1～4 位十六進位統一成 `0x` 加 4 位大寫（例：`0x30f` → `0x030F`），其他寫法視為格式不符。`normalizeSystemName` 去掉前後空白與結尾「系」（11.1），剩下空白時視為沒有填；手動輸入的系統名稱也照做，免得與匯入的名稱對不上。
- **姊妹接替**（`sisters.ts`）：同父同母以父母的內部識別判斷，任一方不明就不算姊妹。「在圈」指在繁殖圈內，被取代但還沒賣出的姊妹也算。選定正式保留時，只把在圈而且列入任務的姊妹改為已被取代。輸入有在圈但狀態是已售出的母馬時丟 `RangeError`。儲存層不把接替狀態改成已售出：自家母駒售出或定年引退時保留離圈前的接替狀態，已售出由在圈狀態表示，畫面在售出時顯示已售出；姊妹判斷只看在圈的母馬，結果不變。撤銷誤登記的離圈時就能回到原本的接替狀態（需求規格 8.5）（使用者 2026-09-26 決定）。
- **母馬的年齡與列入任務**（`mares.ts`）：定年與高齡提醒年齡由儲存層從設定帶入，預設 25、18 歲。高齡提醒只在未達定年時顯示，因為已達定年的母馬不能賣出（需求規格 4.6）。五月缺席的預設原因只看上次五月的馬齡，被取代的姊妹也照同一條規則；馬齡不明時預設售出。列入任務時馬齡不明當作未達定年。出售母親提醒只看暫定保留或正式保留的女兒。馬齡不是 0 以上的整數時丟 `RangeError`。
- **種牡馬**（`stallions.ts`）：兄弟比較以比較對象（通常是現任）為準，選入的要同系、同代、同父，任一方的父馬不明就不算同父。選定現任只把同系同代原本在崗的一匹改為已被取代；前任、後任、生效年與原因由儲存層保存。市場種牡馬替換零代種牡馬，或補公系補入零代市場種牡馬（需求規格 7.6）時，比較他本身的父系與該系目前的子系統，父系不明時不警告；他的子系統沒登錄在對照表、查不到親系統時，仍回報親系統不同，讓畫面提示補登。現任的提醒年齡由設定帶入，預設 26 歲。`StallionStatus` 的 `retired` 是種牡馬已引退；預定後繼的「已引退待指定」（競走馬已引退、還沒接任）對應 `status` 留空，不是 `retired`，否則 `chooseIncumbent` 會拒絕接任。
- **正式後繼**（`successor.ts`）：用出生紀錄連結的配種紀錄的規則快照（實際種牡馬的系與代數、母馬當時的身分）核對，不用母馬目前的用途，因為用途修改從下一次配種才生效（需求規格 8.4）。除了父母與重算的系與代數，也以 10.3 確認這次配種是出生紀錄那一代的指定配對，所以偏離規則配到別系種牡馬的產駒會被阻止（5.2；10.3「刻意偏離請登記為自由配種」，使用者 2026-09-23 確認）。沒有配種紀錄、或配到八系以外種牡馬的產駒比照自由配種。`verifySuccessor` 的第二個參數是要進入的母馬群，或要接任、指定為預定後繼的系與代數，與出生紀錄不符時阻止。補公系所生的產駒，配種紀錄的規則快照要記 `restoration`，以補公系配對核對（需求規格 7.6）；補母系所生的產駒是一般指定配對，照常核對。
- **產駒名稱與 `サ`**（`foal.ts`）：追蹤名用母馬的基本馬名加實際出生年，不帶 `(外)`、`[地]` 前綴（產駒在自家牧場出生，前綴不適用；使用者 2026-09-23 決定）；正式馬名是空字串或只有空白時視為清空，回退追蹤名。`サ` 由 `checkSubAbilityTotal` 計算並與匯入值比對：七項副能力都有等級時才計算，沒有匯入值時不比對。等級文字只接受 `G`～`S+`，匯入層用 `isSubAbilityGrade` 判斷欄位內容。

### 4.3 儲存

- 資料表依需求規格的實體劃分（見下方「資料表」）。索引照需求規格 12.5；除了全域的 `meta`，每張表都帶遊戲局欄位，所有查詢以遊戲局為前提。識別用 `crypto.randomUUID()` 產生的字串（12.2）。IndexedDB 不能以布林值建立索引，要查詢的狀態存成字串。
- 資料列保存目前狀態（在圈、接替狀態、種牡馬狀態、用途、據點），供索引查詢；每次變更另外寫一筆事件作為歷程（需求規格 5.3）。年齡、母馬群匹數、代的成立、是否到達某代等可推導的值不保存，彙整規則輸入快照時計算。
- 結構版本用 Dexie 的版本升級管理；備份檔的結構版本與遷移沿用同一套版本號。正式發布前結構版本維持 1，各計畫直接修改版本 1 的結構；第一次發布後才以版本升級變更。
- 檢查點：整局資料以備份檔的格式（gzip）存入檢查點內容表，年、時點、時間與 SHA-256 等中繼資料另存一張表（12.4）；見「檢查點與回溯」。

`mareYears` 以 `[gameId+horseId+year]` 為主鍵，另以 `[gameId+year]` 建索引（依年篩選今年計畫）（使用者 2026-09-26 決定）。活力的「不適用」與「待更新」（需求規格 8.7）不保存，讀取時推導：母馬不在圈為不適用，沒有快照為待更新。母馬的活力在程式裡稱為 `vigor`，與 core 的血脈活性化 `vitality` 分開。

`matingRatings` 以 `[gameId+mareId]` 建索引；同一匹母馬、同一匹種牡馬、同一年只有一列，由寫入操作維持。配種紀錄的產駒連結、預定出生（受胎的隔年 4 月 1 週）、輪空與未登記年度都不另外保存，由出生紀錄、受胎狀態與有沒有紀錄推導（需求規格 5.3、9.1、BRD-01、BRD-04）；同母同年的產駒以 `horses` 的 `[gameId+damId]` 查詢後篩出生年（BRD-06）。追蹤名也不保存，由母馬的基本馬名與出生年推導（9.4）（使用者 2026-09-27 確認）。

`horseNumbers` 以 `[gameId+horseId]` 建索引。一列是一次取得；同一匹馬同一階段已有相同馬番号時不再新增（需求規格 6.4、MAY-06）。這張表本身就是階段馬番号的歷程，不另寫事件。馬番号以 `normalizeAbilityNumber` 統一寫法（`0x` 加 4 位大寫），格式不符時阻止。儲存子計畫 2-4 只在自家種牡馬接任時寫入種牡馬階段，其他階段由 CE 匯入寫入（使用者 2026-09-28 確認）。

預定後繼沿用 `stallions` 的任用列：狀態留空；尚未誕生時存受胎的配種紀錄 `breedingId`，確認出生後改存 `horseId` 並拿掉 `breedingId`；就緒存在 `readiness`。取消預定後繼時刪除那一列，歷程留在事件：狀態留空的列代表目前的指定，保留已取消的列要多一種狀態，快照與「每系一匹」都得跳過它（使用者 2026-09-28 決定）。

#### 規則輸入快照的彙整

4.2 各項核心輸入由儲存層依下列方式彙整。彙整分兩層：純函式把資料列組成核心的輸入，讀取函式負責查詢 Dexie。年齡以遊戲局的目前遊戲年計算。讀取時找不到遊戲局，或資料列之間的關聯斷掉，丟出帶識別的錯誤（第 5 章的預期外失敗）。

- **系統**：系統對照表取 `systems`。八系目前的系統固定八筆：已開啟的系，子系統取 `lines`，親系統查對照表，查不到時留空。
- **種牡馬狀態**：依 `stallions` 中不屬於補系的任用。同系同代有在崗的為在崗；否則有狀態留空的（預定後繼）為已指定；否則為已離場。沒有任用時不產生那一格，所以 4.2「任何狀態的種牡馬紀錄」就是 `stallions` 有沒有那一系那一代的任用。
- **母馬群**：依 `mares` 的用途分群，待指定用途與自由配種所生的母馬不分群。已成立看「是否使該代成立」：以暫定保留或正式保留轉入時設為是，之後不改回（需求規格 8.2「成立後不可回溯」）；以候選轉入的不算。列入任務的匹數依 `mareListedInTasks` 計算，另計其中的自家母馬數。母馬全部離圈的群仍然列出，才能顯示「已成立，母馬群待補」。
- **自家母駒與出生紀錄的一致性**：在圈的自家母駒，母馬群的系與代數要等於出生紀錄的系與代數；在圈的自由配種所生要有出生紀錄，而且沒有系與代數。不符時丟 `RangeError`（資料列互相矛盾）。只查在圈的，與列入任務需要馬匹資料的範圍相同（使用者 2026-09-28 確認）。
- **補系**：不含已撤銷的宣告。補公系補入的種牡馬狀態以同樣規則，只看屬於這次補系的任用；還沒選定時留空。
- **血統樹**：從配種雙方往上展開到第 4 代。馬名用基本馬名。零代市場種牡馬（含補公系補入的）父系留空時，改填他零代任用所在系目前的子系統；同一匹馬同時有建系與補公系的零代任用時，取建系那一系。建系期標記：建系起點與建立新系的零代市場種牡馬（含依 7.7 替換上來的）一律為是，補公系補入的只在補公系配對產出 4 代以內時為是；母馬依目前的用途，第 1 系起點用或替代 3 代以內時為是。用途在配種後才修改的少數情況，標記跟著新用途，只影響 10.2 的例外是提示還是要求確認。
- **姊妹**（`OwnMare`）：同父同母的自家母馬。
- **種牡馬紀錄**（`StallionRecord`）：某系某代的任用。兄弟比較選入的馬也要組出：格位取他在那一格的任用，沒有任用時取出生紀錄的系與代數；狀態取任用的，沒有任用時留空（需求規格 7.7、LINE-31）。
- **正式後繼**（`SuccessorCandidate`）：產駒的父母，加上出生紀錄連結的配種紀錄的規則快照；沒有配種紀錄、自由配種、沒有規則快照，或出生紀錄沒有系與代數（例如偏離規則、配到八系以外的種牡馬，4.2）時，比照自由配種（使用者 2026-09-24 確認）。
- **替代母馬**（`SubstituteMare`，需求規格 8.3）：同一代的替代母馬包含已離圈的，因為她已生的產駒仍會出現在後代的 3 代前；這項檢查只警告，多算一匹的代價比漏掉警告小。
- **既有馬匹**（`KnownHorse`）：父母名優先用保存的匯入名稱，沒有才用連結馬匹經匯入確認的基本馬名；那匹馬的馬名還是手動輸入、尚未經匯入確認時不傳，免得手動名打錯時子女被誤判為衝突（使用者 2026-09-24 決定）。手動輸入的父母名（父母名與父系的來源為手動）同樣不當作匯入名稱，改用連結馬匹經匯入確認的馬名，沒有時不傳（需求規格 6.4，使用者 2026-09-26 決定）；追蹤名與「母馬名の0歳」不是正式馬名，不傳。
- **年齡設定**：定年、高齡提醒年齡與種牡馬提醒年齡取自 `settings`。

#### 寫入操作

使用者的操作與之後 CE 匯入的套用，都經由儲存層的寫入操作（使用者 2026-09-26 確認）。共用的做法：

- **一個操作一個交易**：每個操作在一個 rw 交易內完成：先讀遊戲局確認存在，再從資料列重新組出核心的輸入並重做檢查，最後寫入資料列與事件，並把遊戲局的更新時間設為現在、應用版本設為目前版本（見「備份與還原」）。設定、代表色這類不寫事件的操作也更新，備份提醒（需求規格 12.2）以此判斷有沒有未備份的變更。操作可以包進呼叫端的外層交易（Dexie 的巢狀交易），CE 匯入以此在單一交易內套用多個操作（4.4）。
- **結果**：完成時附寫入的結果與確認過的警告；阻止時附原因；有警告而呼叫端沒有帶確認時回傳待確認並附警告。阻止與待確認都什麼都不寫。畫面先呼叫一次取得警告，使用者確認後帶確認再呼叫；儲存層在交易內重做檢查，畫面漏掉檢查也存不進違規資料（需求規格 5.2）。確認過的警告存在這次操作的事件上。
- **錯誤**：使用者的輸入或操作違反規則時回傳阻止；畫面不會送出的狀況（找不到資料列、屬於其他局、對已撤銷的宣告再撤銷）丟出帶識別的錯誤；資料列內容互相矛盾時丟 `RangeError`。
- **事件**：會留下年份的操作一律寫事件，事件的年份是操作當時的目前遊戲年；遊戲年變更本身不寫事件。對象欄位填事件關於的馬匹、系位置或子系統，例如種牡馬狀態變更同時填系位置與馬匹；母馬的事件只填馬匹，因為替代母馬不屬於她替代的系（需求規格 8.3）。事件另記來源與時點（見「資料表」）。
- **手動建立的馬**：完整馬名必填，只有前綴時阻止（需求規格 6.4）；馬名來源為手動輸入。能力番号與出生年選填：能力番号格式不符時阻止；出生年晚於目前遊戲年時阻止；能力番号與出生年都和這一局既有的馬相同時阻止並指出那匹馬（6.2：同一匹馬，應選既有的）。父母名與父系選填：父母名去掉前綴後存基本馬名，只有前綴時阻止；有填時，父母名與父系的來源為手動輸入（6.4：只輔助身分配對，匯入時改用匯入值，經匯入確認前可以更正）。
- **系統名稱**：子系統、親系統、分出來源與父系都經 `normalizeSystemName`，必填的欄位空白時阻止。
- **親系統重複的警告**：修改對照表、開啟新系、變更系統名稱或補入、替換零代種牡馬後，親系統因此改變的已開啟的系，與其他系目前的親系統相同時警告並確認（需求規格 7.2、LINE-03）。

各操作的規則：

- **目前遊戲年**（需求規格 12.1）：往後可以改成任何年份；往回不能早於起始年，也不能早於最後紀錄年，也就是這一局事件的最大年份與馬的最大出生年，阻止時附可以改的最早年份。
- **設定**：定年、高齡提醒年齡、種牡馬提醒年齡、檢查點的保留個數都要是 1 以上的整數；不寫事件，新設定從下一次判斷開始生效（MARE-10）。
- **系統對照表**（需求規格 7.2）：新增時子系統不能已登錄，分出來源不能是自己；修改親系統（升格）或分出來源時（分出來源省略表示不變，傳 `null` 才清除），事件記原值、新值與年份。不提供刪除，也不改子系統名稱：打錯時新增正確的一筆，沒有系在用的那一筆不影響任何判斷。
- **開啟新系**（需求規格 7.1、7.3）：該系要在任務看板的可開啟分支中（4.2；補公系進行中的系不能開分支）。填子系統、親系統、代表色（`#rrggbb`，自動分配由畫面預填）與零代市場種牡馬：新建，或選既有的市場馬（沒有出生紀錄、不是牝馬），因為補公系可以沿用建系時的零代種牡馬，兩處共用同一種輸入。子系統沒登錄時新增一筆，已登錄但親系統不同時改為填入的親系統。寫入系位置（開啟年為目前遊戲年）、零代的在崗任用與開啟事件。開啟後不提供撤銷（7.1 位置固定），開錯時以系統名稱變更與零代種牡馬替換更正。
- **系統名稱變更**（需求規格 7.1、7.2、LINE-06）：系要已開啟，新名稱要與目前不同；可一併填親系統，照對照表的規則新增或修改，沒填而對照表查不到時親系統未知。事件記原名稱、新名稱與年份；「該系用過的舊名」（7.2）由開啟與名稱變更的事件查得。
- **代表色**：只檢查格式，不寫事件。
- **補入或替換零代市場種牡馬**（需求規格 7.6、7.7）：對象是某系建系的零代，或某次未撤銷的補公系宣告。那一格已有在崗或已指定的種牡馬時阻止（先標示前任引退，再替換）；選的馬已在這一格任用過時阻止。格是空的（補公系第一次選定）不需原因；只剩已離場的是替換，附 7.7 的原因（弟弟較優、前任引退、無法供用、斷血補系、遊戲依史實引退、其他，可附說明），生效年為目前遊戲年。以 `checkMarketStallionSystem` 比對他的父系，子系統不同時警告並確認，確認後該系的子系統改為他的父系並寫名稱變更事件，事件也記上這匹種牡馬；父系不明時不比較。
- **種牡馬狀態**（需求規格 7.7）：在崗或已被取代的種牡馬可以標示退出生產行列或已引退；更正回在崗只在同一格沒有其他在崗時可以，否則阻止（換人用更換現任）。原本已被取代、誤標為退出或引退的，可以更正回已被取代，只在同一格另有在崗時可以（使用者 2026-09-26 決定）；其他情況的已被取代只由更換現任設定，預定後繼的取消也不在這裡。同一匹馬同時有建系與補公系的零代任用時，引退逐任用標示（使用者 2026-09-26 決定），要不要一次標示全部由畫面決定。這些操作都維持每格（某系某代的一般任用，或同一次補公系的任用）最多一匹在崗；彙整八系快照時遇到同一格有兩匹以上在崗，丟 `RangeError`。
- **斷血補系**（需求規格 7.6）：宣告時原因必填，在交易內組出八系快照以 `checkRestoration` 檢查，年度為目前遊戲年；補入的零代市場種牡馬另外選定。撤銷時設為已撤銷並寫事件，不因已有補系的配種或產駒而阻止：配種紀錄的規則快照自帶補公系標記，補入的任用留著，快照略過已撤銷宣告底下的任用；撤銷後可以重新宣告。
- **母馬的用途**（需求規格 7.3、8.3、8.4）：新增市場母馬、修改用途與從任務買回時，畫面傳任務看板上的一條配對（產出的系與代數）或待指定用途，不直接傳替代的系與代數。交易內組出八系快照，以 `listBoard` 從任務（含暫停中的）與可開啟分支的配對中找產出相同的那一條，找不到時阻止；一個產出只有一條配對，已宣告補公系時就是補公系配對。由配對推出：母馬群是起點時為第 1 系起點用，否則為替代配對母馬群的系與代數；種牡馬是零代而且不是建系起點（建立新系、補公系）時為例外補入，警告並確認、原因必填，其他情況不保存原因。替代母馬以 `checkSubstituteMare` 檢查親系統（8.3），同一代的其他替代母馬包含已離圈的、不含她自己；撞到時警告並確認，自身父系未知時只在完成的結果帶提示。
- **新增市場母馬**（需求規格 8.4、MARE-05、MARE-29、MARE-31）：馬匹照手動建立的馬，性別為牝；在圈，不使該代成立；據點選填，事件一併記下初次據點。來源由配對推出：補公系配對，或配對的母馬群已宣告補母系（未撤銷）時為市場補系；否則建系起點、推進原系與建立新系為市場創系，循環為市場補血；待指定用途由使用者選市場混血或其他；都可附備註。已售出的母馬中，基本馬名相同、能力番号與出生年也不矛盾（兩邊都有值而且不同才算矛盾）時，警告可能是買回並列出那些母馬：使用者確認不是買回就照常建立；是買回時畫面改用買回操作，不建立新馬。
- **修改用途**（需求規格 8.4、MARE-28）：只限在圈的市場母馬（替代、起點用、待指定用途）；自家母駒與自由配種所生的系與代數由出生紀錄決定，不提供。與目前相同時阻止。來源記的是購入時的目的（8.1），不隨用途改變。已有的配種紀錄保留自己的規則快照，新用途從下一次配種生效，不另外處理。
- **賣出**（需求規格 8.5、MARE-08）：只限在圈的母馬；已達定年時阻止（4.6「無法再生產的母馬不能賣出」），出生年不明時可以賣出。這條只適用於手動賣出；五月缺席的判定由 CE 匯入計畫接上，缺席時的馬齡可能已達定年。
- **更正離圈原因**（需求規格 8.5、11.5、MARE-32）：已離圈的母馬可以改為售出、定年引退，或撤銷回到生產中；與目前相同時阻止。撤銷不建立回歸事件；自家母駒回到保留的接替狀態（4.2），原本是正式保留而圈內已有另一匹正式保留的姊妹時改為候選。
- **買回與回歸**（需求規格 8.5、8.9、ID-04、MARE-30、CAND-07）：只限已離圈的母馬。自家母駒沿用出生紀錄的系與代數，接替狀態以 `entrySisterStatus` 重新判定，成為暫定保留時 `establishedGeneration` 設為 true（不改回）；自由配種所生只恢復生產中。市場母馬沒有傳用途時沿用原用途，不重做 8.3 檢查；從任務買回時傳配對，照「母馬的用途」處理，事件記原用途與新用途。自家母駒與自由配種所生不接受用途。可以一併填據點。
- **轉場**（需求規格 8.6、MARE-19）：只限在圈的母馬，與目前相同時阻止；事件記原據點（原本不知道時留空）與新據點，年份、時點與來源在事件的共用欄位。
- **今年計畫**（需求規格 8.7、MARE-22）：只限在圈的母馬，年份為目前遊戲年；沒有值視為待定，與目前相同時阻止。不限用途。
- **活力更正**（需求規格 8.7、MARE-13、MARE-14）：指定年份與五月或七月的快照，數值是 0～100 的整數，是否増強另外指定（`100` 也可以不増強）；年份不能晚於目前遊戲年。快照原本沒有值時也可以填入，不提供清除。與目前相同時阻止。
- **手動資料更正**（需求規格 6.4、ID-08、ID-13）：只限沒有出生紀錄、馬名還是手動輸入的市場馬（市場母馬與零代市場種牡馬），經匯入確認的唯讀。可以更正完整馬名、能力番号、出生年、父母名與自身父系：省略表示不變，`null` 表示清除，完整馬名不能清除；檢查同手動建立的馬，同一匹馬的比對排除自己；什麼都沒改時阻止。替代母馬的自身父系改了時重做 8.3 檢查。零代市場種牡馬改了父系時不重做 7.7 的比對：那只在補入或替換當下比對，要改系的名稱用系統名稱變更。
- **配種的登記：指定配種**（需求規格 7.4、9.1、10.2、10.3）：只登記目前遊戲年，一匹母馬一年一筆，已有時阻止並指出那一筆（改用更正）；母馬要在圈。畫面傳任務看板上的一條配對（產出的系與代數）與實際種牡馬。交易內組出八系快照，以 `listBoard` 從任務（含暫停中的）找產出相同的那一條，找不到時阻止；還沒開啟的分支沒有零代種牡馬，不算。母馬沒有列入任務（`mareListedInTasks`：已達定年、已被取代的姊妹）時阻止。以 `checkDesignatedBreeding` 比對，種牡馬的系與代數取他的任用（優先在崗的，沒有任用時為八系以外），不符時阻止；系與代數相符、但不是那一格在崗的任用時也阻止（10.3「現任種牡馬」）：一般配對看該系該代不屬於補系的任用，補公系配對看那一次補公系的任用。零代種牡馬配替代母馬（例外補入）時警告並確認，原因沒有傳時沿用母馬的例外補入原因，兩邊都空時阻止（使用者 2026-09-27 決定）；替代母馬重做 8.3 親系統檢查（同「母馬的用途」）。10.2 以 `loadMating` 讀血統樹、以 `checkPedigree` 檢查：要確認的警告（`hintOnly` 為否）警告並確認，只提示的放在完成的結果裡。規則快照記距離、種牡馬的系與代數、母馬當時的身分、預計產出、補公系標記與 `checkPedigree` 的完整結果（當時的快照，之後對照表變更不回頭更新）；例外補入原因與確認過的警告另存在配種紀錄上。登記不改今年計畫。
- **配種的登記：自由配種**（需求規格 7.8、9.1）：種牡馬是內部馬匹或外部名稱（去掉前綴存基本馬名，只有前綴時阻止）；不做規則與血統檢查，母馬只要在圈，不看用途與馬齡。
- **配種的更正**（需求規格 9.1、BRD-25）：只限目前遊戲年的紀錄，已有產駒的出生紀錄連到這一筆，或被尚未出生的預定後繼引用時阻止（預定後繼的部分使用者 2026-09-28 決定），內容與目前相同時阻止。指定與自由可以互換，檢查全部照登記重做，受胎狀態不變；事件記原內容與新內容。
- **受胎狀態**（需求規格 9.1、BRD-02）：四種狀態原樣保存，也可以清回沒有結果；不限年份，母馬不必在圈。與目前相同時阻止；已有產駒連到這一筆，或被尚未出生的預定後繼引用時，改成 `受胎` 以外（含清空）阻止（預定後繼的部分使用者 2026-09-28 決定）。不建立產駒。
- **建立產駒**（需求規格 9.3、9.5、11.4、BRD-06）：母馬要是這一局的母馬（`mares` 有這一列），在圈與否不限；性別與出生年必填，出生年不能晚於目前遊戲年。同一母馬同一出生年已有產駒時阻止並指出那一匹。母馬「出生年減 1」那一年的配種紀錄是 `受胎` 時連結：父馬取自配種紀錄，有傳父馬而不一致時阻止；八系指定配種所生的出生紀錄記規則快照的預計產出，牧場處置為保留；自由配種所生沒有系與代數，處置為待售。沒有 `受胎` 紀錄時警告並確認，確認後不連結，父馬用輸入的（可以不知道），出生紀錄是空的，處置為待售，比照自由配種（使用者 2026-09-27 決定）。能力番号照手動建立的馬檢查；能力值不合法時阻止：`SP`、`ST` 為 0 以上的整數，`サ` 為 0～105 的整數，芝與ダート為 `◎○△×` 之一，出生時的仔出為 0～15 的整數，距離適性原樣存文字。七項副能力齊全、也帶了 `サ` 而不符時警告並確認（BRD-11）。父母名與父系的來源依事件的來源：手動為手動輸入，匯入為經匯入確認。牝駒不進繁殖圈，轉入見「自家母駒轉入」。不改預定後繼：產駒出生後由使用者確認（需求規格 7.7）。
- **正式馬名**（需求規格 9.4、BRD-08、BRD-10）：只限自家產駒（有出生紀錄）；市場馬的手動馬名用「手動資料更正」。馬名經匯入確認時阻止，只有前綴、與目前相同時阻止。可以清空，清空後沒有馬名，顯示回退追蹤名；牧場處置不變。事件記原名與新名；手動名之間的更正只留歷程，一月總表取代手動名時的別名由 CE 匯入計畫處理。
- **牧場處置**（需求規格 9.3、9.5、BRD-15、BRD-26）：只限自家產駒；出生紀錄沒有系與代數的產駒不能改為保留；與目前相同時阻止。
- **總合評價與爆發力**（需求規格 9.2、BRD-17、BRD-18）：記在目前遊戲年；母馬要是這一局的母馬，不限在圈；種牡馬是內部馬匹或外部名稱（去掉前綴存基本馬名），同一匹種牡馬以內部識別與外部名稱登記時算不同的組合。評價與爆發力至少填一項，爆發力要是 0 以上的整數（使用者 2026-09-27 決定）。同一組同一年已有時整組取代，與目前相同時阻止；跨年另起一列，舊值保留。
- **重新連結出生紀錄**（需求規格 9.3、BRD-27）：只限沒有連結配種紀錄的自家產駒（有出生紀錄、沒有 `breedingId`），其他的丟出錯誤。母馬「出生年減 1」那一年的配種紀錄要是 `受胎`，否則阻止並附那一筆與它的狀態；產駒已記的父馬與紀錄不同時阻止；牝駒已轉入繁殖圈（`mares` 有這一列，不論在圈與否）而要連到八系指定配種時也阻止：她的用途是自由配種所生，連上後出生紀錄有了系與代數，會違反「自家母駒與出生紀錄的一致性」，連到自由配種不影響用途，可以（使用者 2026-09-29 決定）。母馬不必在圈。連結後出生紀錄記配種紀錄，八系指定配種所生另記規則快照的預計產出；產駒沒有父馬時補上紀錄的父馬。連到八系指定配種、原本待售時，牧場處置改為保留，比照建立產駒的預設（原本待售是沒有連結時強制的）；已售出不變，連到自由配種也不變。事件記配種紀錄與牧場處置的變化（使用者 2026-09-28 決定）。
- **自家母駒轉入**（需求規格 8.4、8.9、9.6、11.5、LINE-17、MARE-07）：只限這一局還沒進過繁殖圈（`mares` 沒有這一列）的自家牝駒，其他的丟出錯誤；已在 `mares` 的用「買回與回歸」。以 `buildSuccessorCandidate` 組出核對輸入：八系指定配種所生以 `verifySuccessor` 核對（目標是出生紀錄的系與代數），不符時阻止；通過時用途為自家，母馬群依出生紀錄，接替狀態以 `entrySisterStatus` 判定，暫定保留時 `establishedGeneration` 設為 true。自由配種所生或比照自由配種（核對輸入為 free）：生產中，用途為自由配種所生，不分群、沒有接替狀態。需求規格 8.4 的手動轉入只提非自由配種所生，但五月匯入（11.5）用同一個操作，所以儲存層兩種都接受；畫面是否對自由配種所生提供手動轉入由畫面計畫決定。來源為所屬競走馬引退轉入，可附備註；據點選填。不設年齡門檻，不改牧場處置。事件記用途與母馬群、接替狀態與據點（使用者 2026-09-28 確認）。
- **選定正式保留**（需求規格 8.9、MARE-12、MARE-24）：只限在圈的自家母駒，其他的丟出錯誤。以 `chooseKeptSister` 套用：她改為正式保留，同父同母、在圈而且列入任務的姊妹改為已被取代；沒有姊妹時也可以選（暫定保留改為正式保留）；沒有任何變化時阻止。選為正式保留時 `establishedGeneration` 設為 true，不改回（8.2：正式保留會使該代成立）。狀態有變的每匹母馬各寫一筆事件，記原狀態、新狀態與選定的母馬。之後改保留另一匹，對她再做一次（使用者 2026-09-28 確認）。
- **預定後繼的指定**（需求規格 7.6、7.7、9.6、LINE-40～42）：對象是已出生的自家公駒，或已受胎、產駒還沒出生的八系指定配種；其他對象（牝駒、市場馬、不是 `受胎` 或不是指定配種的紀錄）丟出錯誤。系與代數不由畫面選：公駒取出生紀錄，配種取規則快照的預計產出；以 `verifySuccessor` 核對，不符時阻止（未出生時以配種紀錄的父母與規則快照組出核對輸入）。同一系已有預定後繼時阻止並指出那一筆，改指定要先取消；公駒在那一格已有任用時阻止；配種已有產駒出生時阻止，改為指定那匹產駒。就緒預設競走中，也可以直接指定為已引退待指定。指定後那一格就有種牡馬紀錄：以他為種牡馬的任務依任務看板的規則出現，暫停到他接任；那一代是補公系產出的那一代時，補公系也在此時結束（需求規格 7.6「指定預定後繼即可」）（使用者 2026-09-28 決定）。
- **預定後繼的確認出生、就緒與取消**（需求規格 7.7、LINE-42）：確認出生只限尚未出生的預定後繼：連到那筆配種的產駒還沒有時阻止，產駒是牝時阻止（預定後繼失效，由使用者取消）；公駒以 `verifySuccessor` 再核對，通過後改存馬匹、拿掉配種紀錄，就緒為競走中。就緒在競走中與已引退待指定之間切換，只限已出生的預定後繼，和目前相同時阻止。取消只限預定後繼（狀態留空），刪除那一列並寫事件；已接任的改用「種牡馬狀態」（使用者 2026-09-28 決定）。
- **正式接任與更換現任**（需求規格 7.7、9.6、PED-08、LINE-22、LINE-30、STL-03）：對象是自家公駒，格位取出生紀錄的系與代數，不由畫面選；不是自家公駒時丟出錯誤。以 `verifySuccessor` 核對，不符時阻止。他在那一格是預定後繼或已被取代時沿用那一列；已退出生產行列或已引退時阻止（先用「種牡馬狀態」更正）；已在崗時阻止；那一格尚未出生的預定後繼指定的就是他出生的配種時阻止，先確認出生（使用者 2026-09-29 決定）；沒有任用時新增一列。那一格另有接任過的任用（在崗、已被取代、退出生產行列、已引退）時是更換現任，要附 7.7 的原因；第一次接任不需原因；同一格其他還沒接任的預定後繼不算。以 `chooseIncumbent` 套用：他改為在崗並拿掉就緒，同一格原本在崗的改為已被取代；上一代的現任（交接期間可同時在崗）與這一系其他的預定後繼不動，前任的配種、產駒與血緣保持原連結。生效年為目前遊戲年。種牡馬馬番号選填，寫法不符時阻止，有填時記一筆種牡馬階段。事件記格位、原因與被取代的馬。兄弟比較只提供讀取（見「規則輸入快照的彙整」的種牡馬紀錄），由畫面以 `checkBrothers` 檢查；接任不另外檢查同父，因為其他原因的更換本來就不要求同父。保留原現任時不寫任何紀錄（使用者 2026-09-28 決定）。

#### 備份與還原

備份、還原與危險區（需求規格 12.1、12.2）由儲存子計畫 3-1 負責；檢查點（3-2）與封存、瀏覽器整合（3-3）沿用這裡的整局讀寫與備份格式（使用者 2026-09-29 確認）。

- **整局資料**：`GAME_TABLES` 列出一局的資料表，匯出、還原、回溯、檢查點的內容、刪除與計算筆數都用這份清單。不屬於一局資料的表明示排除：全域的 `meta`，以及檢查點的兩張表（備份不含檢查點，回溯要清掉整局資料而留下檢查點，刪除一局時另外刪）；測試確認每一張表不是在 `GAME_TABLES`，就是在排除清單裡，之後加表時一併更新（使用者 2026-09-29 決定）。讀出整局在單一唯讀交易內完成，得到一致的快照（需求規格 12.2）。
- **應用版本**：取 `package.json` 的 `version`，由 Vite 的 `define` 注入（Vitest 共用同一份設定）。建立遊戲局、還原與每個寫入操作都把遊戲局的應用版本設為目前版本（需求規格 12.1「最後寫入這一局的管理器版本」）。
- **備份檔**：一個 JSON 物件，欄位依序為格式識別 `format`（`wpstudbook-backup`）、結構版本 `schemaVersion`（Dexie 的版本號）、應用版本、匯出時間、遊戲局摘要（識別、局名、起始年、目前遊戲年）、各集合的筆數 `counts`、集合 `collections`（`GAME_TABLES` 每張表一個陣列，資料列原樣）與 `sha256`。雜湊是 `sha256` 以外的欄位依上述順序 `JSON.stringify` 後，UTF-8 位元組的 SHA-256（小寫十六進位）；驗證時拿掉 `sha256` 重新序列化再比對，`JSON.parse` 保留欄位順序，所以結果一致。留空的欄位在資料列裡本來就不存在，`0`、空字串與 `false` 原樣保留（DATA-03）；寫入操作不留下值為 `undefined` 的欄位。JSON 不縮排；有 `CompressionStream` 時 gzip 成 `.json.gz`，否則輸出 `.json`（DATA-06）。
- **匯出**：先取現在時間作為匯出時間，再以唯讀交易讀出整局；序列化、雜湊與壓縮在交易外進行，因為它們是瀏覽器的非同步 API，不能放在 Dexie 交易內。檔名為 `WPStudBook_<局名>_<目前遊戲年>年_<YYYYMMDD-HHmmss>` 加副檔名，時間用本機時間，局名裡 Windows 檔名不允許的字元（`\ / : * ? " < > |` 與控制字元）換成 `_`，超過 60 字時只取前 60 字（使用者 2026-09-29 決定）。回傳檔名、位元組與摘要：檔名、局名、各集合筆數與總筆數、大小、結構版本、應用版本、匯出時間與是否壓縮（DATA-07）。匯出只讀，不觸發下載；下載由畫面或 3-3 的自動備份負責。
- **最近備份時間**：由呼叫端在交出檔案（觸發下載，或寫入備份資料夾成功）後另外記錄，設為匯出時間，只往後不往回；不改更新時間與應用版本，因為記錄備份不是資料變更。用快照的時間而不用記錄的時間：快照之後的修改，更新時間晚於最近備份時間，仍算未備份（需求規格 12.2「備份提醒」）。匯出與記錄分開，是因為 3-3 寫入資料夾失敗時要改為自動下載，確定交出後才記錄。
- **讀取與驗證**：依序檢查，任一步不通過就回傳拒絕與原因，資料不變（DATA-04）。這屬於第 5 章的資料來源異常，以回傳結果表達，不丟例外。
  1. 解壓：開頭是 `1F 8B` 時以 `DecompressionStream` 解壓，失敗為錯誤或截斷的 gzip，瀏覽器不支援解壓時也拒絕；其他開頭當作未壓縮的 JSON。
  2. 解析：UTF-8 嚴格解碼後 `JSON.parse`，失敗為截斷或不是 JSON。
  3. 格式：格式識別相符、結構版本是 1 以上的整數，否則不是備份檔。
  4. 版本：結構版本大於目前版本時為未來版本，附版本號。
  5. 雜湊：依「備份檔」重算並比對，在遷移前進行；重算失敗（例如極深的巢狀）也是雜湊不符。
  6. 遷移：較舊的結構版本逐版套用遷移函式。結構版本 1 是第一版，目前沒有遷移；遷移表可由參數傳入，測試以假的遷移驗證（DATA-05）。
  7. 欄位：集合剛好是 `GAME_TABLES`，多或少都拒絕；每一列是物件，主鍵欄位存在且型別正確，遊戲局欄位等於這一局；`games` 與 `settings` 各一列；`games` 那一列另外驗證儲存層會取用的欄位：局名、建立與更新時間是字串，起始年與目前遊戲年是整數（使用者 2026-09-29 決定）；遊戲局摘要與 `games` 那一列一致。其他欄位不逐欄驗證型別與列舉值：檔案完整性由雜湊保證，全面驗證要隨每次改表同步。
  8. 重複：各表主鍵不重複，所有 `id` 跨表也不重複，因為還原時所有識別共用一張新舊對照表。
  9. 關聯：`horses` 的父、母指向 `horses`，出生紀錄的配種指向 `breedings`；`mares`、`horseNumbers` 與 `events` 的馬匹指向 `horses`；`mareYears` 的馬匹指向 `mares`；`stallions` 的馬匹、配種、補系分別指向 `horses`、`breedings`、`restorations`；`breedings` 與 `matingRatings` 的母馬指向 `mares`，種牡馬指向 `horses`。指向 `mares` 的，現有寫入操作都已要求母馬在 `mares`。事件內容裡的引用不查：取消預定後繼會刪除任用列，事件裡的任用識別本來就可能懸空。
  10. 筆數：`counts` 的鍵與各集合的筆數相符；只看集合自己的鍵，不讀到繼承的屬性（例如 `constructor`）。

  通過時回傳驗證過的備份與預覽：局名、起始年與目前遊戲年、匯出時間、結構版本、應用版本、各集合筆數與總筆數。可傳進度回呼，回報解壓、解析、驗證等步驟（需求規格 12.2「大型檔案顯示進度」）。
- **還原**：一律還原成新遊戲局（需求規格 12.2），在一個 rw 交易內寫入全部資料表，失敗時整筆回復。
  - 識別重新產生：遊戲局與各列的 `id` 換成新的 UUID，任何欄位（含事件內容）中整個字串等於舊識別的值一律換成新的，懸空的引用保持原值。原局通常還在同一個瀏覽器裡（12.2「還原後再到危險區刪除舊局」），保留原識別會撞到它（使用者 2026-09-29 決定）。
  - 局名用呼叫端傳的，沒傳時用備份的局名；空白時丟 `RangeError`，同建立遊戲局；可以與既有的局重複，由畫面預填。
  - 建立時間為還原的時間，更新時間沿用備份的（資料最後修改的時間）；應用版本為目前版本；最近備份時間為備份的匯出時間，因為內容與備份檔相同，沒有未備份的變更。
  - 還原來源記檔名、匯出時間、原局名、備份的應用版本與結構版本；結構版本比目前舊就是經過遷移，這就是 DATA-05 的紀錄。
  - 寫入時依集合回報進度（已寫筆數與總筆數）。不切換目前遊戲局，回傳新局，由畫面決定。

#### 檢查點與回溯

檢查點與回溯（需求規格 11.1、12.4）由儲存子計畫 3-2 負責，沿用「備份與還原」的整局讀寫與備份格式（使用者 2026-09-29 決定）。

- **資料表**：中繼資料與內容分成兩張表，都不屬於 `GAME_TABLES`（見「整局資料」）。以設計目標的單局 3 萬列估算，內容 gzip 後約 1 MB，12 個約 12 MB；IndexedDB 只能整列讀寫，分表後開啟清單與釘選只讀寫幾 KB（使用者 2026-09-29 決定）。
  - `checkpoints`（主鍵 `id`，索引 `gameId`）：遊戲局、建立方式（年度匯入後自動、手動）、年、時點（選填）、補匯的年與時點（直接補匯時，CKPT-08）、建立時間、SHA-256（內容檔案裡的 `sha256`）、註記（選填）、是否釘選（只讀取不建索引，存布林值）。
  - `checkpointContents`（主鍵 `checkpointId`，索引 `gameId`）：內容的位元組。
- **內容**：與備份檔相同的位元組，建立時間就是檔案的匯出時間。匯出與檢查點共用同一個編碼函式（組出內容、雜湊與壓縮），沒有 `CompressionStream` 時同樣存未壓縮的 JSON。驗證沿用備份的讀取與驗證，結構升版後，舊檢查點在回溯時逐版遷移（使用者 2026-09-29 決定）。
- **年與時點**：年取建立當下這一局的目前遊戲年，所以回溯後的目前遊戲年一定等於檢查點的年（CKPT-06）。時點由呼叫端傳入：年度匯入由 CE 匯入傳目前進度的時點，直接補匯另傳補匯的年與時點（需求規格 12.4）；手動建立由畫面決定是否帶時點（使用者 2026-09-29 決定）。
- **建立**：先取現在時間作為建立時間，再以唯讀交易讀出整局（一致快照）；編碼在交易外進行，再以一個 rw 交易寫入兩張表並清除超過保留個數的檢查點，回傳新的檢查點與被清除的檢查點。時點不是 1～12 月、1～4 週，或補匯的年不是整數時丟出 `RangeError`；註記去除前後空白，空白時不存。建立檢查點不是資料變更，不改遊戲局的更新時間與應用版本（同「最近備份時間」）。檢查點的建立與年度匯入的交易分開，因為瀏覽器的非同步 API 不能放在 Dexie 交易內；匯入提交後、檢查點寫入前關閉頁面時，那次匯入沒有檢查點。
- **保留**：這一局未釘選的檢查點依建立時間由新到舊，超過保留個數（`settings` 的 `checkpointLimit`，預設 12，要是 1 以上的整數）的連同內容刪除；釘選的不計入也不刪除。剛建立的一定留著，其他未釘選的最多留保留個數減一個：系統時鐘往回調時，新檢查點的建立時間可能不是最新的，不能讓它被自己清掉（使用者 2026-09-29 決定）。只在建立時清除：取消釘選或調低個數不會立即刪除，免得使用者剛取消釘選的檢查點當場消失（使用者 2026-09-29 決定）。
- **管理**：列出一局的檢查點（只讀中繼資料，由新到舊）、釘選與取消釘選（不觸發清除）、事後修改註記（空白時移除），都不改遊戲局的更新時間；找不到遊戲局、檢查點，或檢查點屬於其他局時丟出錯誤。不提供手動刪除單一檢查點（使用者 2026-09-29 決定）。
- **驗證與預覽**：以一個唯讀交易讀出遊戲局、檢查點、內容、目前整局資料與較晚的檢查點；交易外依「讀取與驗證」驗證內容，再核對檢查點的 `sha256` 等於檔案的 `sha256`、檔案的遊戲局識別等於這一局。不通過時回傳拒絕與原因，資料不變（CKPT-05）：備份的拒絕原因之外，另有內容不見與內容對不上。通過時回傳驗證過的檢查點（已遷移到目前的結構）與預覽（CKPT-04）：檢查點本身、目前遊戲年的變化、各表目前與檢查點的筆數、將捨棄的事件（目前有而檢查點沒有的事件，依寫入時間排序）、將移除的較晚檢查點（建立時間晚於這個檢查點，含釘選的），以及預覽當下遊戲局的更新時間。每個寫入操作都寫事件，所以將捨棄的事件就是將捨棄的操作；設定、代表色這類操作不寫事件，預覽列不出來：設定在回溯時沿用目前的值，代表色隨系位置回到檢查點（使用者 2026-09-29 決定）。找不到遊戲局、檢查點，或檢查點屬於其他局時丟出錯誤。
- **回溯**：先以「匯出」匯出目前這一局，交給呼叫端傳入的交付函式（下載由 3-3 的輔助函式負責）；交付函式丟出錯誤時回溯停止，資料不變。接著在一個 rw 交易內（`GAME_TABLES` 與檢查點的兩張表）：遊戲局的更新時間要等於預覽時的值，否則阻止，因為預覽或備份之後有變更時，交付的備份不一定含有將捨棄的全部資料；目標檢查點要還在，否則丟出錯誤；以 `deleteGameData` 刪除整局，再以 `addGameData` 寫回檢查點的資料，識別不變；刪除較晚的檢查點與內容。回傳回溯後的遊戲局與被移除的檢查點（需求規格 12.4、CKPT-06、CKPT-07）。先驗證預覽再下載，是因為預覽本來就要解開檢查點，驗證失敗時也不會白下載一份；資料變動前一定已交出備份（使用者 2026-09-29 決定）。
  - `games` 那一列：目前遊戲年取檢查點（CKPT-06）；局名、起始年、建立時間與還原來源沿用目前的列，它們描述的是這一局本身，不是遊戲進度；應用版本為目前版本；更新時間為回溯的時間，因為回溯本身就是資料變更；最近備份時間沿用目前的列，它只往後不往回，目前的列一定不早於檢查點的列（使用者 2026-09-29 決定）。
  - 不記錄最近備份時間：交付的備份是回溯前的狀態，不含回溯後的資料；記錄下來時，匯出時間與回溯的更新時間是同一個時間，更新時間不晚於最近備份時間，備份提醒就不會請使用者備份回溯後的狀態。交付後被阻止時那次備份不記錄，最多多提醒一次。
  - `settings` 沿用目前的列：定年、提醒年齡與保留個數是管理器的設定，新設定從下一次判斷開始生效（MARE-10），不是遊戲的歷程（使用者 2026-09-29 決定）。系統對照表、系位置（含代表色）與其他資料取檢查點。
  - 回溯不寫事件：歷程整個回到檢查點，回溯前的完整狀態在交付的備份裡。

#### 危險區

- **筆數**：回傳一局 `GAME_TABLES` 各表的筆數與總筆數，供確認前顯示（需求規格 12.1「顯示筆數」）；檢查點的個數由畫面從檢查點清單另外顯示（使用者 2026-09-29 決定）。
- **永久刪除此局**：輸入的局名去掉前後空白後要等於局名，否則阻止，什麼都不刪；名稱核對放在儲存層，畫面漏掉也刪不掉。在一個 rw 交易內從 `GAME_TABLES` 刪除這一局的資料列，連同這一局的檢查點與內容（需求規格 12.4，使用者 2026-09-29 決定）；`meta` 的目前遊戲局指向這一局時一併清除，由畫面請使用者重新選局。不寫事件，因為這一局已不存在。回傳刪除的各表筆數；找不到遊戲局時丟出錯誤。
- **刪除全部存檔**：輸入的文字要是「刪除全部存檔」，否則阻止；第二道確認由畫面負責（需求規格 12.1，使用者 2026-09-29 決定）。在一個交易內清空資料庫的每一張表（含 `meta`），檢查點的兩張表也包含在內；3-3 的封存索引要不要保留由 3-3 決定。回傳刪除的遊戲局數與總筆數；總筆數只算 `GAME_TABLES`，不含檢查點（使用者 2026-09-29 決定）。

### 4.4 資料流：年度匯入

以五月繁殖圈名單為例，對應需求規格 11.1 的流程：

1. 畫面取得檔案（選檔或拖放，一次一個）。
2. `ce-import` 解碼 CP932、判斷分隔字元、依位置讀欄，並從檔名解析年與時點。
3. `ce-import` 用 `core` 比對身分，產生差異預覽：繼續在圈、新進、回歸、缺席、衝突，以及用途把關。
4. 畫面顯示預覽，使用者修改用途並確認需要確認的警告。
5. `ce-import` 產生套用計畫，也就是要新增、更新哪些資料，要建立哪些事件。
6. `storage` 在單一 Dexie 交易內寫入計畫；接著建立檢查點，並依需求規格 12.2 自動備份。
7. 畫面顯示結果摘要。

任一步發生阻擋錯誤時，交易不會開始，或者整筆回復，資料保持不變。

## 5. 錯誤處理

對應需求規格 5.2 的三類處理：

| 類型 | 做法 |
| --- | --- |
| 阻止 | 核心回傳「阻止」結果，附上錯誤的一方與正確的系、代數；畫面顯示原因，不能保存 |
| 警告並確認 | 核心回傳警告清單；畫面逐項取得確認後，帶確認再呼叫寫入操作；確認內容寫進該次操作的事件、配種紀錄或匯入紀錄 |
| 資料來源異常 | 解析器回傳錯誤；依需求規格決定整份停止或略過該筆 |

- 規則檢查用回傳結果表達，不用例外；例外只用在預期外的失敗。
- 寫入操作在交易內重做規則檢查，阻止或尚未確認時什麼都不寫（4.3「寫入操作」）。
- 預期外的失敗讓 Dexie 交易回復，畫面顯示錯誤，資料不變。

- 不能用的項目只有「持久保存」：採用本節表格的替代做法「顯示未取得，加強備份提醒」。需求規格已有對應規則（12.2「持久保存」與 DATA-14），不修改需求規格。

- CP932 解碼結果與 Windows 全部一致，`ce-import` 不需要額外正規化，第 4.4 節不修改。
