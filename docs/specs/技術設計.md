# WPStudBook 技術設計

## 1. 文件資訊

- 對應需求：[需求規格](需求規格.md)
- 最後更新：2026-10-08

## 2. 決策摘要

| 項目 | 決定 | 主要理由 |
| --- | --- | --- |
| 成品形式 | 單一 HTML 檔，以 `file://` 在 Windows 最新版 Edge／Chrome 離線使用 | 免安裝、工具鏈最單純；資料安全以備份強化補足（需求規格 12.2） |
| 語言 | TypeScript（strict） | 規則、匯入與畫面同一種語言 |
| 前端框架 | Vue 3（`<script setup>`）＋Pinia＋Vue Router（hash 模式） | 模板接近 HTML、狀態管理直覺、生態成熟；`file://` 只能用 hash 路由 |
| 可及性元件、大清單 | Reka UI、TanStack Virtual | 對話框、頁籤、清單已處理鍵盤與焦點；匯入預覽與清單需要虛擬捲動 |
| 建置 | Vite＋`vite-plugin-singlefile` | JS、CSS 全部內嵌，輸出 `WPStudBook.html` |
| 資料庫 | IndexedDB＋Dexie | 結構版本升級、複合索引、批次寫入與交易 |
| 測試 | Vitest、`fake-indexeddb`、Vue Test Utils、Playwright | 核心與資料庫層在 Node 測；端對端以 `file://` 開建置出的單檔 |
| 程式風格 | ESLint（Vue、TypeScript 規則）＋Prettier | |
| 執行環境 | Node 24、npm | 本機已安裝；`package-lock.json` 納入版控 |

瀏覽器內建能力直接使用，不加套件：CP932 解碼（`TextDecoder`）、gzip（`CompressionStream`）、SHA-256（`crypto.subtle`）。只有測試用的 CP932 範例檔需要在 Node 產生，因此加入開發用套件 `iconv-lite`。

## 3. 考慮過但未採用

- **桌面版（WPF＋WebView2 或 MAUI HybridWebView）**：好處是資料存成本機檔案、可監看 CE 匯出資料夾、可用 SQLite 查詢。未採用的原因：一年只匯入 4～5 次，拖放檔案不麻煩；單局幾萬筆資料在瀏覽器記憶體內計算就夠快；真正的差別只剩資料安全，改以需求規格 12.2 的持久保存與自動備份處理。桌面版還要重寫需求規格第 12、14 章，並多一套 .NET 工具鏈。日後若改走桌面，建議 WPF＋Blazor Hybrid（規則、資料、畫面全用 C#），不建議 MAUI（只用 Windows 時多出 WinUI 3 與打包的複雜度）。
- **React**：生態與可及性元件（React Aria）最完整，但 hooks 的依賴陣列與重複渲染較容易出錯，程式也較不像 HTML。
- **Svelte 5**：程式碼最少，但生態較小，寫法與一般 HTML 差異較大。

## 4. 架構

### 4.1 模組與依賴方向

| 模組 | 路徑 | 責任 | 可依賴 |
| --- | --- | --- | --- |
| 核心 | `src/core/` | 領域模型與規則，全部是作用於一般資料的純函式；也放 `ce-import` 與 `storage` 共用的匯入型別（4.4） | 無（不得引用 Vue、Dexie、DOM 或其他 `src` 模組） |
| CE 匯入 | `src/ce-import/` | 匯出檔解碼、解析、驗證、身分比對、差異預覽、產生套用計畫 | `core` |
| 儲存 | `src/storage/` | Dexie 資料庫、套用計畫的單一交易寫入、檢查點、備份與還原、封存、持久保存、備份資料夾 | `core` |
| 畫面 | `src/ui/` | Vue 元件、頁面、Pinia store、路由 | 以上全部 |
| 進入點 | `src/main.ts` | 建立 Vue 應用、開啟資料庫、申請持久保存 | 以上全部 |

依賴方向以 ESLint 的 `no-restricted-imports` 強制：`core` 不得引用其他模組；`ce-import` 與 `storage` 只能引用 `core`；沒有模組可以引用 `ui`。

### 4.2 核心的內容

- 系位置、建系分支與新系編號（需求規格 7.3）、兩兩互換配對表（4.3）。
- 產駒的系與代數，替代母馬以她替代的代數計（8.2）。
- 任務產生：可開啟的分支、循環任務、世代交接（7.3、7.4）；斷血補系的補公系配對、補母系、暫停與結束，以及宣告補系前的檢查（7.6）。
- 規則檢查：阻止（10.3）、警告並確認（8.3、10.2）、零代種牡馬例外補入（7.3）。
- 血統推算：3 代前 8 匹祖先、推定父親的系統與始祖例外、4 代內重複（10.2），以及活血種數與「至少 N 種」的判斷（4.3、10.2）。
- 系統對照表查詢：子系統的親系統與分出來源、八系親系統的種類數與重複（7.2）。
- 同一匹馬的判斷（6.2）；姊妹接替狀態與代的成立（8.9、8.2）；母馬的定年、高齡與出售母親提醒，以及是否列入任務（8.5）。
- 種牡馬的兄弟比較、選定現任、替換時的系統比對與年齡提醒（7.7）；正式後繼的核對（9.6）。
- 產駒的追蹤名與 `サ`（9.3、9.4）。
- 馬名、能力番号與系統名稱的正規化（6.4、6.2、11.1），手動輸入與 CE 匯入共用。
- 匯入的種類與遊戲內時點（`ImportType`、`GameTiming`）、年度匯入的固定時點與目前進度、兩邊都用到的馬匹屬性與常數（`Sex`、`SurfaceAptitude`、`Vigor`、`Conception`、據點 `Base`），以及匯入紀錄、匯入比對快照與套用計畫的型別（11.1）：`ce-import` 與 `storage` 互不引用，兩邊共用的型別放在核心（4.4）。

`docs/specs/八系巡迴圖.html` 裡的配對與血統推算是這部分的參考實作，移入核心時改寫成 TypeScript 並補上測試。

#### 規則輸入快照

核心不定義資料表結構，也不保存狀態。規則以「規則輸入快照」為輸入，快照由儲存層依資料表彙整：

- 八個系位置各一筆：是否已開啟（建系起點或建立新系時已填寫系統與零代市場種牡馬，需求規格 7.1），以及各代種牡馬狀態與各代母馬群。
- 種牡馬狀態每（系, 代）一個值（需求規格 7.7）：在崗；已指定但還沒正式供用（尚未誕生、競走中、已引退待指定）；已離場，指退出生產行列或已引退、而且同一代沒有其他在崗或已指定的種牡馬。
- 母馬群每（系, 代）一筆：是否已成立（第一匹自家母駒以暫定或正式保留轉入，需求規格 8.2，依 `establishesGeneration` 判斷；只有替代母馬時為未成立）、列入任務的母馬數（依 `mareListedInTasks`：在繁殖圈內、未達定年，自家母駒還要是暫定保留、候選或正式保留），以及其中的自家母馬數（建立新系時由使用者判斷自家母馬是否不足，需求規格 7.3；不得多於列入任務的母馬數）。母馬歸哪個母馬群依 `damPlacement`：自家母駒依出生紀錄的系與代數，替代母馬依她替代的系與代數，起點母馬歸第 1 系起點母馬群；待指定用途的市場母馬（需求規格 8.4）與自由配種所生的母駒（11.5）不屬於任何母馬群，不計入。
- 第 1 系 0 代母馬群就是第 1 系起點母馬群。
- 已宣告的斷血補系（需求規格 7.6）：每系一份清單，每筆是斷血的代數與斷掉的一方（公系或母系）；補公系另帶補入的零代市場種牡馬狀態（與種牡馬狀態同樣三種，還沒選定時留空）。代數要在該系成立的代數以後，同一系同一代同一方只有一筆；使用者更正（撤銷）宣告時從清單移除。補入的零代市場種牡馬不放進該系的種牡馬狀態，零代那一格仍是建系時的零代市場種牡馬。補系結束後這一筆仍留在清單，因為補公系配對永久取代一般配對。補入的零代市場種牡馬依 7.7 提前引退並替換時，狀態取替換後那一匹，比照零代那一格。補公系配對產出 4 代以內（建系期）時，補入的零代市場種牡馬算 10.2 的建系期市場種牡馬，血統樹的建系期標記為是；循環期補入的不算（使用者 2026-09-24 決定）。
- 系統對照表：每個子系統一筆，含親系統與選填的分出來源；分出來源只用在始祖例外（10.2）。
- 八系目前的系統：每個系位置的目前子系統與親系統，系尚未開啟時兩者都沒有值。
- 血統樹：一次配種往上四代，每個位置是一匹馬或「沒有內部紀錄」。每匹馬帶內部識別（判斷 4 代內重複）、馬名（判斷始祖例外，10.2）、本身的父系，以及是不是建系期的市場馬（零代市場種牡馬或替代母馬，10.2 的例外判斷用）。
- 零代市場種牡馬的父系欄留空時，儲存層彙整快照時改填該系目前的子系統（需求規格 10.2）；核心只看快照裡的父系，不另外查系位置。

#### 任務看板的判斷

以下是需求規格 7.3、7.4、7.6、7.7 的詮釋，`src/core/board.ts` 依此實作：

- **到達某代**：該系該代有種牡馬紀錄（任何狀態），或該代母馬群已成立。只有替代母馬的母馬群不算。
- **可開啟的分支**：新系尚未開啟，且原系到達分支前一代。建系起點在第 1 系開啟前一直可開啟。
- **任務出現**：建系起點與建立新系在該系開啟後出現；推進原系在原系到達前一代時出現；循環任務在該系前一代有種牡馬紀錄、而且配對系前一代母馬群已成立時出現。
- **任務結束**：同系下一代任務已出現，而且這條任務的母馬群已沒有列入任務的母馬，或種牡馬已離場。
- **沒有下一代任務時**：母馬群已成立但沒有母馬，顯示「已成立，母馬群待補」；種牡馬已離場，任務暫停並顯示缺少現任種牡馬（零代時為缺少目標種牡馬）。
- 指定配種檢查只比對系與代數；種牡馬是否為現任，由任務看板的種牡馬狀態判斷。
- **補公系**：第 p 系 N 代宣告補公系後，第 p 系 N+1 代的指定配對固定為補公系配對（`restorationPairing`：第 p 系零代 × 原本指定的配對系 N 代母馬群），補系結束後也一樣。補公系任務宣告後就出現，種牡馬狀態看補入的零代市場種牡馬；世代交接照一般規則，所以斷血那一代的重試任務在原本的種牡馬離場或母馬全部離圈時結束。
- **補母系**：第 q 系 N 代宣告補母系後，配它的循環任務不等母馬群成立，配對系 N 代有種牡馬紀錄就出現。
- **補系進行中與結束**：補公系進行中，該系還沒開啟的分支都不能開啟；補母系不暫停。補公系在第 p 系 N+1 代有種牡馬紀錄（任何狀態）時結束，補母系在補系任務產出的那一代母馬群成立時結束；結束只解除暫停。看板列出每筆補系的補系任務與是否進行中。
- **宣告補系的檢查**（`checkRestoration`）：該系還沒開啟、那一代還沒成立、同一代同一方已經宣告，都阻止。補公系另外阻止：該系還沒到達那一代（沒有種牡馬紀錄，母馬群也沒成立）、那一代已有在崗或已指定的種牡馬、下一代已有種牡馬紀錄；那一代的種牡馬已離場時不阻止。補母系另外阻止那一代母馬群已成立。

#### 身分、母馬、種牡馬與後繼

以下是需求規格 4.6、6.2、7.6、7.7、8.1、8.5、8.9、9.3、9.4、9.6 在核心的輸入約定，以及規格沒有逐字寫出、由核心決定的判斷。儲存層與匯入層依此彙整輸入：

- **同一匹馬**（`identity.ts`）：只傳目前遊戲局的馬匹，馬番号不參與判斷。能力番号由匯入層與手動輸入統一寫法後保存與比對，`0x0000` 是有效值。馬名與父母名稱用基本馬名；還不是正式馬名的名稱（四月的「母馬名の0歳」、未命名的產駒）不傳。手動輸入、尚未經匯入確認的馬名要標 `manualName`：只用來輔助配對，與匯入名稱不同時不算衝突，由匯入名稱取代（需求規格 6.4、9.4、BRD-09）；經匯入確認的馬名不同時仍是衝突（ID-08）。兩邊都有值而且不同才算「明顯不符」，比較時忽略前後空白。以馬名輔助配對時，候選是馬名相符、出生年相同或未填的紀錄；候選兩筆以上，或能力番号與出生年配到兩筆以上，都列為衝突（需求規格 11.5「無法判斷的身分列入衝突」）；輔助配對到的紀錄父母明顯不符也是衝突；以馬名配到的紀錄已有不同的能力番号時也是衝突，不得覆寫。同一匯入檔內重複的能力番号由 `duplicateAbilityNumbers` 列出，只看能力番号、不看出生年，有任何一個時整份停止套用。一月總表以父馬、母馬、出生年配對舊產駒（11.3）屬於匯入層（4.4「一月」）。
- **名稱與番号的正規化**（`identity.ts`、`systems.ts`）：`splitHorseName` 去掉開頭的 `(外)` 或 `[地]` 得到基本馬名，只有前綴、沒有馬名時表示資料異常（需求規格 6.4）。`normalizeAbilityNumber` 忽略前後空白，把 `0x` 加 1～4 位十六進位統一成 `0x` 加 4 位大寫（例：`0x30f` → `0x030F`），其他寫法視為格式不符。`normalizeSystemName` 去掉前後空白與結尾「系」（11.1），剩下空白時視為沒有填；手動輸入的系統名稱也照做，免得與匯入的名稱對不上。
- **姊妹接替**（`sisters.ts`）：同父同母以父母的內部識別判斷，任一方不明就不算姊妹。「在圈」指在繁殖圈內，被取代但還沒賣出的姊妹也算。選定正式保留時，只把在圈而且列入任務的姊妹改為已被取代。輸入有在圈但狀態是已售出的母馬時丟 `RangeError`。儲存層不把接替狀態改成已售出：自家母駒售出或定年引退時保留離圈前的接替狀態，已售出由在圈狀態表示，畫面在售出時顯示已售出；姊妹判斷只看在圈的母馬，結果不變。撤銷誤登記的離圈時就能回到原本的接替狀態（需求規格 8.5）（使用者 2026-09-26 決定）。
- **母馬的年齡與列入任務**（`mares.ts`）：定年與高齡提醒年齡由儲存層從設定帶入，預設 25、18 歲。高齡提醒只在未達定年時顯示，因為已達定年的母馬不能賣出（需求規格 4.6）。五月缺席的預設原因只看上次五月的馬齡，被取代的姊妹也照同一條規則；馬齡不明時預設售出。列入任務時馬齡不明當作未達定年。出售母親提醒只看暫定保留或正式保留的女兒。馬齡不是 0 以上的整數時丟 `RangeError`。
- **種牡馬**（`stallions.ts`）：兄弟比較以比較對象（通常是現任）為準，選入的要同系、同代、同父，任一方的父馬不明就不算同父。選定現任只把同系同代原本在崗的一匹改為已被取代；前任、後任、生效年與原因由儲存層保存。市場種牡馬替換零代種牡馬，或補公系補入零代市場種牡馬（需求規格 7.6）時，比較他本身的父系與該系目前的子系統，父系不明時不警告；他的子系統沒登錄在對照表、查不到親系統時，仍回報親系統不同，讓畫面提示補登。現任的提醒年齡由設定帶入，預設 26 歲。`StallionStatus` 的 `retired` 是種牡馬已引退；預定後繼的「已引退待指定」（競走馬已引退、還沒接任）對應 `status` 留空，不是 `retired`，否則 `chooseIncumbent` 會拒絕接任。
- **正式後繼**（`successor.ts`）：用出生紀錄連結的配種紀錄的規則快照（實際種牡馬的系與代數、母馬當時的身分）核對，不用母馬目前的用途，因為用途修改從下一次配種才生效（需求規格 8.4）。除了父母與重算的系與代數，也以 10.3 確認這次配種是出生紀錄那一代的指定配對，所以偏離規則配到別系種牡馬的產駒會被阻止（5.2；10.3「刻意偏離請登記為自由配種」，使用者 2026-09-23 確認）。沒有配種紀錄、或配到八系以外種牡馬的產駒比照自由配種。`verifySuccessor` 的第二個參數是要進入的母馬群，或要接任、指定為預定後繼的系與代數，與出生紀錄不符時阻止。補公系所生的產駒，配種紀錄的規則快照要記 `restoration`，以補公系配對核對（需求規格 7.6）；補母系所生的產駒是一般指定配對，照常核對。
- **產駒名稱與 `サ`**（`foal.ts`）：追蹤名用母馬的基本馬名加實際出生年，不帶 `(外)`、`[地]` 前綴（產駒在自家牧場出生，前綴不適用；使用者 2026-09-23 決定）；正式馬名是空字串或只有空白時視為清空，回退追蹤名。`サ` 由 `checkSubAbilityTotal` 計算並與匯入值比對：七項副能力都有等級時才計算，沒有匯入值時不比對。等級文字只接受 `G`～`S+`，匯入層用 `isSubAbilityGrade` 判斷欄位內容。

### 4.3 儲存

- 資料表依需求規格的實體劃分（見下方「資料表」）。索引照需求規格 12.5；除了全域的 `meta` 與封存索引 `archives`，每張表都帶遊戲局欄位，所有查詢以遊戲局為前提。識別用 `crypto.randomUUID()` 產生的字串（12.2）。IndexedDB 不能以布林值建立索引，要查詢的狀態存成字串。
- 資料列保存目前狀態（在圈、接替狀態、種牡馬狀態、用途、據點），供索引查詢；每次變更另外寫一筆事件作為歷程（需求規格 5.3）。年齡、母馬群匹數、代的成立、是否到達某代等可推導的值不保存，彙整規則輸入快照時計算。
- 結構版本用 Dexie 的版本升級管理；備份檔的結構版本與遷移沿用同一套版本號。正式發布前結構版本維持 1，各計畫直接修改版本 1 的結構；第一次發布後才以版本升級變更。
- 檢查點：整局資料以備份檔的格式（gzip）存入檢查點內容表，年、時點、時間與 SHA-256 等中繼資料另存一張表（12.4）；見「檢查點與回溯」。

#### 規則輸入快照的彙整

4.2 各項核心輸入由儲存層依下列方式彙整。彙整分兩層：純函式把資料列組成核心的輸入，讀取函式負責查詢 Dexie。年齡以遊戲局的目前遊戲年計算。讀取時找不到遊戲局，或資料列之間的關聯斷掉，丟出帶識別的錯誤（第 5 章的預期外失敗）。

- **系統**：系統對照表取 `systems`。八系目前的系統固定八筆：已開啟的系，子系統取 `lines`，親系統查對照表，查不到時留空。
- **種牡馬狀態**：依 `stallions` 中不屬於補系的任用。同系同代有在崗的為在崗；否則有狀態留空的（預定後繼）為已指定；否則為已離場。沒有任用時不產生那一格，所以 4.2「任何狀態的種牡馬紀錄」就是 `stallions` 有沒有那一系那一代的任用。
- **母馬群**：依 `mares` 的用途分群，待指定用途與自由配種所生的母馬不分群。已成立看「是否使該代成立」：以暫定保留或正式保留轉入時設為是，之後不改回（需求規格 8.2「成立後不可回溯」）；以候選轉入的不算。列入任務的匹數依 `mareListedInTasks` 計算，另計其中的自家母馬數。母馬全部離圈的群仍然列出，才能顯示「已成立，母馬群待補」。
- **自家母駒與出生紀錄的一致性**：在圈的自家母駒，母馬群的系與代數要等於出生紀錄的系與代數；在圈的自由配種所生要有出生紀錄，而且沒有系與代數。不符時丟 `RangeError`（資料列互相矛盾）。只查在圈的，與列入任務需要馬匹資料的範圍相同（使用者 2026-09-28 確認）。
- **補系**：不含已撤銷的宣告。補公系補入的種牡馬狀態以同樣規則，只看屬於這次補系的任用；還沒選定時留空。
- **血統樹**：從配種雙方往上展開到第 4 代。馬名用基本馬名。零代市場種牡馬（含補公系補入的）父系留空時，改填他零代任用所在系目前的子系統；同一匹馬同時有建系與補公系的零代任用時，取建系那一系。建系期標記：建系起點與建立新系的零代市場種牡馬（含依 7.7 替換上來的）一律為是，補公系補入的只在補公系配對產出 4 代以內時為是；母馬依目前的用途，第 1 系起點用或替代 3 代以內時為是。用途在配種後才修改的少數情況，標記跟著新用途，只影響 10.2 的例外是提示還是要求確認。
- **姊妹**（`OwnMare`）：同父同母的自家母馬。
- **種牡馬紀錄**（`StallionRecord`）：某系某代的任用。兄弟比較選入的馬也要組出：格位取他在那一格的任用，沒有任用時取出生紀錄的系與代數；狀態取任用的，沒有任用時留空（需求規格 7.7、LINE-31）。
- **正式後繼**（`SuccessorCandidate`）：產駒的父母，加上出生紀錄連結的配種紀錄的規則快照；沒有配種紀錄、自由配種、沒有規則快照，或出生紀錄沒有系與代數（例如偏離規則、配到八系以外的種牡馬，4.2）時，比照自由配種（使用者 2026-09-24 確認）。
- **替代母馬**（`SubstituteMare`，需求規格 8.3）：同一代的替代母馬包含已離圈的，因為她已生的產駒仍會出現在後代的 3 代前；這項檢查只警告，多算一匹的代價比漏掉警告小。
- **既有馬匹**（`KnownHorse`）：父母名優先用保存的匯入名稱，沒有才用連結馬匹經匯入確認的基本馬名；那匹馬的馬名還是手動輸入、尚未經匯入確認時不傳，免得手動名打錯時子女被誤判為衝突（使用者 2026-09-24 決定）。手動輸入的父母名（父母名與父系的來源為手動）同樣不當作匯入名稱，改用連結馬匹經匯入確認的馬名，沒有時不傳（需求規格 6.4，使用者 2026-09-26 決定）；追蹤名與「母馬名の0歳」不是正式馬名，不傳。
- **年齡設定**：定年、高齡提醒年齡與種牡馬提醒年齡取自 `settings`。

#### 寫入操作

使用者的操作與之後 CE 匯入的套用，都經由儲存層的寫入操作（使用者 2026-09-26 確認）。共用的做法：

- **一個操作一個交易**：每個操作在一個 rw 交易內完成：先讀遊戲局確認存在，再從資料列重新組出核心的輸入並重做檢查，最後寫入資料列與事件，並把遊戲局的更新時間設為現在、應用版本設為目前版本（見「備份與還原」）。設定、代表色這類不寫事件的操作也更新，備份提醒（需求規格 12.2）以此判斷有沒有未備份的變更。操作可以包進呼叫端的外層交易（Dexie 的巢狀交易），CE 匯入以此在單一交易內套用多個操作（4.4）。
- **結果**：完成時附寫入的結果與確認過的警告；阻止時附原因；有警告而呼叫端沒有帶確認時回傳待確認並附警告。阻止與待確認都什麼都不寫。畫面先呼叫一次取得警告，使用者確認後帶確認再呼叫；儲存層在交易內重做檢查，畫面漏掉檢查也存不進違規資料（需求規格 5.2）。確認過的警告存在這次操作的事件上。
- **錯誤**：使用者的輸入或操作違反規則時回傳阻止；畫面不會送出的狀況（找不到資料列、屬於其他局、對已撤銷的宣告再撤銷）丟出帶識別的錯誤；資料列內容互相矛盾時丟 `RangeError`。
- **事件**：會留下年份的操作一律寫事件，事件的年份是操作當時的目前遊戲年；遊戲年變更本身不寫事件。對象欄位填事件關於的馬匹、系位置或子系統，例如種牡馬狀態變更同時填系位置與馬匹；母馬的事件只填馬匹，因為替代母馬不屬於她替代的系（需求規格 8.3）。事件另記來源與時點（見「資料表」）。
- **手動建立的馬**：完整馬名必填，只有前綴時阻止（需求規格 6.4）；馬名來源為手動輸入。能力番号與出生年選填：能力番号格式不符時阻止；出生年晚於目前遊戲年時阻止；能力番号與出生年都和這一局既有的馬相同時阻止並指出那匹馬（6.2：同一匹馬，應選既有的）。父母名與父系選填：父母名去掉前綴後存基本馬名，只有前綴時阻止；有填時，父母名與父系的來源為手動輸入（6.4：只輔助身分配對，匯入時改用匯入值，經匯入確認前可以更正）。
- **系統名稱**：子系統、親系統、分出來源與父系都經 `normalizeSystemName`，必填的欄位空白時阻止。
- **親系統重複的警告**：修改對照表、開啟新系、變更系統名稱或補入、替換零代種牡馬後，親系統因此改變的已開啟的系，與其他系目前的親系統相同時警告並確認（需求規格 7.2、LINE-03）。

各操作的規則：

- **目前遊戲年**（需求規格 12.1）：往後可以改成任何年份；往回不能早於起始年，也不能早於最後紀錄年，也就是這一局事件的最大年份、馬的最大出生年與匯入紀錄的最大年份（匯入紀錄由 CE 匯入子計畫 4-2 加入，免得遊戲年落在目前進度之前），阻止時附可以改的最早年份。
- **設定**：定年、高齡提醒年齡、種牡馬提醒年齡、檢查點的保留個數、備份提醒天數都要是 1 以上的整數；不寫事件，新設定從下一次判斷開始生效（MARE-10）。
- **系統對照表**（需求規格 7.2）：新增時子系統不能已登錄，分出來源不能是自己；修改親系統（升格）或分出來源時（分出來源省略表示不變，傳 `null` 才清除），事件記原值、新值與年份。不提供刪除，也不改子系統名稱：打錯時新增正確的一筆，沒有系在用的那一筆不影響任何判斷。
- **開啟新系**（需求規格 7.1、7.3）：該系要在任務看板的可開啟分支中（4.2；補公系進行中的系不能開分支）。填子系統、親系統、代表色（`#rrggbb`，自動分配由畫面預填）與零代市場種牡馬：新建，或選既有的市場馬（沒有出生紀錄、不是牝馬），因為補公系可以沿用建系時的零代種牡馬，兩處共用同一種輸入。子系統沒登錄時新增一筆，已登錄但親系統不同時改為填入的親系統。寫入系位置（開啟年為目前遊戲年）、零代的在崗任用與開啟事件。開啟後不提供撤銷（7.1 位置固定），開錯時以系統名稱變更與零代種牡馬替換更正。
- **系統名稱變更**（需求規格 7.1、7.2、LINE-06）：系要已開啟，新名稱要與目前不同；可一併填親系統，照對照表的規則新增或修改，沒填而對照表查不到時親系統未知。事件記原名稱、新名稱與年份；「該系用過的舊名」（7.2）由開啟與名稱變更的事件查得。
- **代表色**：只檢查格式，不寫事件。
- **補入或替換零代市場種牡馬**（需求規格 7.6、7.7）：對象是某系建系的零代，或某次未撤銷的補公系宣告。那一格已有在崗或已指定的種牡馬時阻止（先標示前任引退，再替換）；選的馬已在這一格任用過時阻止。格是空的（補公系第一次選定）不需原因；只剩已離場的是替換，附 7.7 的原因（弟弟較優、前任引退、無法供用、斷血補系、遊戲依史實引退、其他，可附說明），生效年為目前遊戲年。以 `checkMarketStallionSystem` 比對他的父系，子系統不同時警告並確認，確認後該系的子系統改為他的父系並寫名稱變更事件，事件也記上這匹種牡馬；父系不明時不比較。
- **種牡馬狀態**（需求規格 7.7）：在崗或已被取代的種牡馬可以標示退出生產行列或已引退；更正回在崗只在同一格沒有其他在崗時可以，否則阻止（換人用更換現任）。原本已被取代、誤標為退出或引退的，可以更正回已被取代，只在同一格另有在崗時可以（使用者 2026-09-26 決定）；其他情況的已被取代只由更換現任設定，預定後繼的取消也不在這裡。同一匹馬同時有建系與補公系的零代任用時，引退逐任用標示（使用者 2026-09-26 決定），要不要一次標示全部由畫面決定。這些操作都維持每格（某系某代的一般任用，或同一次補公系的任用）最多一匹在崗；彙整八系快照時遇到同一格有兩匹以上在崗，丟 `RangeError`。
- **斷血補系**（需求規格 7.6）：宣告時原因必填，在交易內組出八系快照以 `checkRestoration` 檢查，年度為目前遊戲年；補入的零代市場種牡馬另外選定。撤銷時設為已撤銷並寫事件，不因已有補系的配種或產駒而阻止：配種紀錄的規則快照自帶補公系標記，補入的任用留著，快照略過已撤銷宣告底下的任用；撤銷後可以重新宣告。
- **母馬的用途**（需求規格 7.3、8.3、8.4）：新增市場母馬、修改用途與從任務買回時，畫面傳任務看板上的一條配對（產出的系與代數）或待指定用途，不直接傳替代的系與代數。交易內組出八系快照，以 `listBoard` 從任務（含暫停中的）與可開啟分支的配對中找產出相同的那一條，找不到時阻止；一個產出只有一條配對，已宣告補公系時就是補公系配對。由配對推出：母馬群是起點時為第 1 系起點用，否則為替代配對母馬群的系與代數；種牡馬是零代而且不是建系起點（建立新系、補公系）時為例外補入，警告並確認、原因必填，其他情況不保存原因。替代母馬以 `checkSubstituteMare` 檢查親系統（8.3），同一代的其他替代母馬包含已離圈的、不含她自己；撞到時警告並確認，自身父系未知時只在完成的結果帶提示。
- **新增市場母馬**（需求規格 8.4、MARE-05、MARE-29、MARE-31）：馬匹照手動建立的馬，性別為牝；在圈，不使該代成立；據點選填，事件一併記下初次據點。來源由配對推出：補公系配對，或配對的母馬群已宣告補母系（未撤銷）時為市場補系；否則建系起點、推進原系與建立新系為市場創系，循環為市場補血；待指定用途由使用者選市場混血或其他；都可附備註。已售出的母馬中，基本馬名相同、能力番号與出生年也不矛盾（兩邊都有值而且不同才算矛盾）時，警告可能是買回並列出那些母馬：使用者確認不是買回就照常建立；是買回時畫面改用買回操作，不建立新馬。
- **修改用途**（需求規格 8.4、MARE-28）：只限在圈的市場母馬（替代、起點用、待指定用途）；自家母駒與自由配種所生的系與代數由出生紀錄決定，不提供。與目前相同時阻止。來源記的是購入時的目的（8.1），不隨用途改變。已有的配種紀錄保留自己的規則快照，新用途從下一次配種生效，不另外處理。
- **賣出**（需求規格 8.5、MARE-08）：只限在圈的母馬；已達定年時阻止（4.6「無法再生產的母馬不能賣出」），出生年不明時可以賣出。這條只適用於手動賣出；五月缺席由「五月缺席的離圈」處理，缺席時的馬齡可能已達定年。
- **更正離圈原因**（需求規格 8.5、11.5、MARE-32）：已離圈的母馬可以改為售出、定年引退，或撤銷回到生產中；與目前相同時阻止。撤銷不建立回歸事件；自家母駒回到保留的接替狀態（4.2），原本是正式保留而圈內已有另一匹正式保留的姊妹時改為候選。
- **買回與回歸**（需求規格 8.5、8.9、ID-04、MARE-30、CAND-07）：只限已離圈的母馬。自家母駒沿用出生紀錄的系與代數，接替狀態以 `entrySisterStatus` 重新判定，成為暫定保留時 `establishedGeneration` 設為 true（不改回）；自由配種所生只恢復生產中。市場母馬沒有傳用途時沿用原用途，不重做 8.3 檢查；從任務買回時傳配對，照「母馬的用途」處理，事件記原用途與新用途。自家母駒與自由配種所生不接受用途。可以一併填據點。
- **轉場**（需求規格 8.6、MARE-19）：只限在圈的母馬，與目前相同時阻止；事件記原據點（原本不知道時留空）與新據點，年份、時點與來源在事件的共用欄位。
- **今年計畫**（需求規格 8.7、MARE-22）：只限在圈的母馬，年份為目前遊戲年；沒有值視為待定，與目前相同時阻止。不限用途。
- **活力更正**（需求規格 8.7、MARE-13、MARE-14）：指定年份與五月或七月的快照，數值是 0～100 的整數，是否増強另外指定（`100` 也可以不増強）；年份不能晚於目前遊戲年。快照原本沒有值時也可以填入，不提供清除。與目前相同時阻止。
- **手動資料更正**（需求規格 6.4、ID-08、ID-13）：只限沒有出生紀錄、馬名還是手動輸入的市場馬（市場母馬與零代市場種牡馬），經匯入確認的唯讀。可以更正完整馬名、能力番号、出生年、父母名與自身父系：省略表示不變，`null` 表示清除，完整馬名不能清除；檢查同手動建立的馬，同一匹馬的比對排除自己；什麼都沒改時阻止。替代母馬的自身父系改了時重做 8.3 檢查。零代市場種牡馬改了父系時不重做 7.7 的比對：那只在補入或替換當下比對，要改系的名稱用系統名稱變更。
- **配種的登記：指定配種**（需求規格 7.4、9.1、10.2、10.3）：只登記目前遊戲年，一匹母馬一年一筆，已有時阻止並指出那一筆（改用更正）；母馬要在圈。畫面傳任務看板上的一條配對（產出的系與代數）與實際種牡馬。交易內組出八系快照，以 `listBoard` 從任務（含暫停中的）找產出相同的那一條，找不到時阻止；還沒開啟的分支沒有零代種牡馬，不算。母馬沒有列入任務（`mareListedInTasks`：已達定年、已被取代的姊妹）時阻止。以 `checkDesignatedBreeding` 比對，種牡馬的系與代數取他的任用（優先在崗的，沒有任用時為八系以外），不符時阻止；系與代數相符、但不是那一格在崗的任用時也阻止（10.3「現任種牡馬」）：一般配對看該系該代不屬於補系的任用，補公系配對看那一次補公系的任用。零代種牡馬配替代母馬（例外補入）時警告並確認，原因沒有傳時沿用母馬的例外補入原因，兩邊都空時阻止（使用者 2026-09-27 決定）；替代母馬重做 8.3 親系統檢查（同「母馬的用途」）。10.2 以 `loadMating` 讀血統樹、以 `checkPedigree` 檢查：要確認的警告（`hintOnly` 為否）警告並確認，只提示的放在完成的結果裡。規則快照記距離、種牡馬的系與代數、母馬當時的身分、預計產出、補公系標記與 `checkPedigree` 的完整結果（當時的快照，之後對照表變更不回頭更新）；例外補入原因與確認過的警告另存在配種紀錄上。登記不改今年計畫。
- **配種的登記：自由配種**（需求規格 7.8、9.1）：種牡馬是內部馬匹或外部名稱（去掉前綴存基本馬名，只有前綴時阻止）；不做規則與血統檢查，母馬只要在圈，不看用途與馬齡。
- **配種的更正**（需求規格 9.1、BRD-25）：只限目前遊戲年的紀錄，已有產駒的出生紀錄連到這一筆，或被尚未出生的預定後繼引用時阻止（預定後繼的部分使用者 2026-09-28 決定），內容與目前相同時阻止。指定與自由可以互換，檢查全部照登記重做，受胎狀態不變；事件記原內容與新內容。
- **受胎狀態**（需求規格 9.1、BRD-02）：四種狀態原樣保存，也可以清回沒有結果；不限年份，母馬不必在圈。與目前相同時阻止；已有產駒連到這一筆，或被尚未出生的預定後繼引用時，改成 `受胎` 以外（含清空）阻止（預定後繼的部分使用者 2026-09-28 決定）。不建立產駒。
- **建立產駒**（需求規格 9.3、9.5、11.4、BRD-06）：母馬要是這一局的母馬（`mares` 有這一列），在圈與否不限；性別與出生年必填，出生年不能晚於目前遊戲年。同一母馬同一出生年已有產駒時阻止並指出那一匹。母馬「出生年減 1」那一年的配種紀錄是 `受胎` 時連結：父馬取自配種紀錄，有傳父馬而不一致時阻止；八系指定配種所生的出生紀錄記規則快照的預計產出，牧場處置為保留；自由配種所生沒有系與代數，處置為待售。沒有 `受胎` 紀錄時警告並確認，確認後不連結，父馬用輸入的（可以不知道），出生紀錄是空的，處置為待售，比照自由配種（使用者 2026-09-27 決定）。能力番号照手動建立的馬檢查；能力值不合法時阻止：`SP`、`ST` 為 0 以上的整數，`サ` 為 0～105 的整數，芝與ダート為 `◎○△×` 之一，出生時的仔出為 0～15 的整數，距離適性原樣存文字。七項副能力齊全、也帶了 `サ` 而不符時警告並確認（BRD-11）。父母名與父系的來源依事件的來源：手動為手動輸入，匯入為經匯入確認。牝駒不進繁殖圈，轉入見「自家母駒轉入」。不改預定後繼：產駒出生後由使用者確認（需求規格 7.7）。
- **正式馬名**（需求規格 9.4、BRD-08、BRD-10）：只限自家產駒（有出生紀錄）；市場馬的手動馬名用「手動資料更正」。馬名經匯入確認時阻止，只有前綴、與目前相同時阻止。可以清空，清空後沒有馬名，顯示回退追蹤名；牧場處置不變。事件記原名與新名；手動名之間的更正只留歷程，一月總表取代手動名時的別名見下一條。
- **一月總表的正式馬名**（需求規格 9.4、11.2、11.3、BRD-09、JAN-05、IMP-10）：`importFoalName`，一月二歲馬總表的計畫項目（4.4「一月」），由 `applyImport` 在匯入的交易內呼叫。只限自家產駒，其他的丟出錯誤。項目帶出生年、完整馬名（第 1 欄）、基本馬名（第 77 欄）、能力番号與競走馬馬番号；這次是不是資料更正由 `applyImport` 依計畫的套用方式傳入。阻止：出生年不同；產駒已有不同的能力番号；這一局另一匹馬已有相同的能力番号與出生年（`findSameHorse`，排除自己，附那一匹，需求規格 6.2）；馬名已經匯入確認、與項目的完整馬名或基本馬名不同，而這次不是資料更正；完整馬名只有前綴，或基本馬名空白；什麼都不用改（馬名、馬名來源與能力番号都相同，競走馬馬番号也已記過）。通過時：完整馬名與基本馬名改用項目的值，馬名來源為經匯入確認；原本是手動輸入的馬名而且與新的完整馬名不同時，把原本的完整馬名加到別名的最後；沒有能力番号時補上；以 `recordHorseNumber` 記競走馬階段的馬番号（相同的不重複記）。不改父母、出生年、性別、能力、出生紀錄與牧場處置，也不碰繁殖圈（11.2、IMP-10）。馬名、馬名來源或能力番号有變時寫事件 `foal-name-imported`：原本的完整馬名（沒有時不記；與新名相同也記，表示經匯入確認）、新的完整馬名與補上的能力番号；只記了馬番号時不寫事件，`horseNumbers` 本身就是歷程（使用者 2026-10-07 決定）。父母是否明顯不符（6.2）只在預覽檢查（4.4「一月」）：項目不帶檔案的父母名，套用前又核對更新時間，預覽之後資料不會改變。
- **牧場處置**（需求規格 9.3、9.5、BRD-15、BRD-26）：只限自家產駒；出生紀錄沒有系與代數的產駒不能改為保留；與目前相同時阻止。
- **總合評價與爆發力**（需求規格 9.2、BRD-17、BRD-18）：記在目前遊戲年；母馬要是這一局的母馬，不限在圈；種牡馬是內部馬匹或外部名稱（去掉前綴存基本馬名），同一匹種牡馬以內部識別與外部名稱登記時算不同的組合。評價與爆發力至少填一項，爆發力要是 0 以上的整數（使用者 2026-09-27 決定）。同一組同一年已有時整組取代，與目前相同時阻止；跨年另起一列，舊值保留。
- **重新連結出生紀錄**（需求規格 9.3、BRD-27）：只限沒有連結配種紀錄的自家產駒（有出生紀錄、沒有 `breedingId`），其他的丟出錯誤。母馬「出生年減 1」那一年的配種紀錄要是 `受胎`，否則阻止並附那一筆與它的狀態；產駒已記的父馬與紀錄不同時阻止；牝駒已轉入繁殖圈（`mares` 有這一列，不論在圈與否）而要連到八系指定配種時也阻止：她的用途是自由配種所生，連上後出生紀錄有了系與代數，會違反「自家母駒與出生紀錄的一致性」，連到自由配種不影響用途，可以（使用者 2026-09-29 決定）。母馬不必在圈。連結後出生紀錄記配種紀錄，八系指定配種所生另記規則快照的預計產出；產駒沒有父馬時補上紀錄的父馬。連到八系指定配種、原本待售時，牧場處置改為保留，比照建立產駒的預設（原本待售是沒有連結時強制的）；已售出不變，連到自由配種也不變。事件記配種紀錄與牧場處置的變化（使用者 2026-09-28 決定）。
- **自家母駒轉入**（需求規格 8.4、8.9、9.6、11.5、LINE-17、MARE-07）：只限這一局還沒進過繁殖圈（`mares` 沒有這一列）的自家牝駒，其他的丟出錯誤；已在 `mares` 的用「買回與回歸」。以 `buildSuccessorCandidate` 組出核對輸入：八系指定配種所生以 `verifySuccessor` 核對（目標是出生紀錄的系與代數），不符時阻止；通過時用途為自家，母馬群依出生紀錄，接替狀態以 `entrySisterStatus` 判定，暫定保留時 `establishedGeneration` 設為 true。自由配種所生或比照自由配種（核對輸入為 free）：生產中，用途為自由配種所生，不分群、沒有接替狀態。需求規格 8.4 的手動轉入只提非自由配種所生，但五月匯入（11.5）用同一個操作，所以儲存層兩種都接受；畫面是否對自由配種所生提供手動轉入由畫面計畫決定。來源為所屬競走馬引退轉入，牧場處置已售出的產駒（售出後再買回）為其他（需求規格 8.4，使用者 2026-10-08 決定），可附備註；據點選填。不設年齡門檻，不改牧場處置。事件記用途與母馬群、接替狀態與據點（使用者 2026-09-28 確認）。
- **五月缺席的離圈**（需求規格 8.5、11.5、MARE-09、MAY-12）：`departMare`，五月繁殖圈名單的計畫項目（4.4「五月對帳」），由 `applyImport` 在匯入的交易內呼叫。只限在圈的母馬，其他的丟出錯誤；原因是售出或定年引退，由預覽依馬齡預設、使用者可以更正。在圈狀態改為那個原因，自家母駒的接替狀態保留離圈前的值（4.2）。不檢查定年：缺席時的馬齡可能已達定年，「無法再生產的母馬不能賣出」只限制手動賣出。事件 `mare-departed`，不會阻止。
- **補齊身分**（需求規格 6.2、ID-07、MAY-14）：`fillHorseIdentity`，五月以馬名輔助或使用者指定配到、缺能力番号或出生年的馬（4.4「五月對帳」），由 `applyImport` 呼叫。項目帶名單的能力番号與出生年，只補空白：馬匹已有不同的值時丟出錯誤（配對時已排除）；兩者都已有相同的值時阻止（什麼都不用改）；這一局另一匹馬已有相同的能力番号與出生年時阻止並附那一匹（`same-horse`，6.2）。事件 `horse-identity-filled` 記補上的值。不改馬名、父母與父系（4-5 五月資料補齊）。
- **五月新進的市場母馬**（需求規格 8.4、11.5、MAY-03、MAY-11）：`importMare`，五月名單上沒配到任何紀錄的列，由 `applyImport` 呼叫。項目帶名單的完整馬名（第 1 欄）、基本馬名（第 59 欄）、能力番号、出生年、父母名、父系、牝系、據點、繁殖牝馬馬番号與用途。馬匹：性別為牝，馬名來源與父母名、父系的來源都是經匯入確認；父母名去掉前綴存基本馬名，空白或只有前綴的父母名、空白的父系與牝系不存。阻止：完整馬名只有前綴或基本馬名空白（6.4）；這一局已有相同能力番号與出生年的馬（`same-horse`）；用途的阻止同「母馬的用途」。用途、例外補入與來源照「新增市場母馬」，待指定用途的來源為其他；8.3 親系統與例外補入的警告要確認。不做「可能是買回」的警告：已售出的母馬由匯入的配對找到，配不到才新建。母馬在圈、不使該代成立；以 `recordHorseNumber` 記繁殖牝馬階段的馬番号。事件 `mare-added` 記初次據點。
- **繁殖牝馬馬番号**（需求規格 6.4、MAY-06）：`importHorseNumber`，五月配到的母馬（新建的由 `importMare` 一併記），由 `applyImport` 呼叫。以 `recordHorseNumber` 記繁殖牝馬階段；同一階段已記過相同的馬番号時阻止（什麼都不用改；預覽只為還沒記過的產生項目）。不寫事件，`horseNumbers` 本身就是歷程。
- **選定正式保留**（需求規格 8.9、MARE-12、MARE-24）：只限在圈的自家母駒，其他的丟出錯誤。以 `chooseKeptSister` 套用：她改為正式保留，同父同母、在圈而且列入任務的姊妹改為已被取代；沒有姊妹時也可以選（暫定保留改為正式保留）；沒有任何變化時阻止。選為正式保留時 `establishedGeneration` 設為 true，不改回（8.2：正式保留會使該代成立）。狀態有變的每匹母馬各寫一筆事件，記原狀態、新狀態與選定的母馬。之後改保留另一匹，對她再做一次（使用者 2026-09-28 確認）。
- **預定後繼的指定**（需求規格 7.6、7.7、9.6、LINE-40～42）：對象是已出生的自家公駒，或已受胎、產駒還沒出生的八系指定配種；其他對象（牝駒、市場馬、不是 `受胎` 或不是指定配種的紀錄）丟出錯誤。系與代數不由畫面選：公駒取出生紀錄，配種取規則快照的預計產出；以 `verifySuccessor` 核對，不符時阻止（未出生時以配種紀錄的父母與規則快照組出核對輸入）。同一系已有預定後繼時阻止並指出那一筆，改指定要先取消；公駒在那一格已有任用時阻止；配種已有產駒出生時阻止，改為指定那匹產駒。就緒預設競走中，也可以直接指定為已引退待指定。指定後那一格就有種牡馬紀錄：以他為種牡馬的任務依任務看板的規則出現，暫停到他接任；那一代是補公系產出的那一代時，補公系也在此時結束（需求規格 7.6「指定預定後繼即可」）（使用者 2026-09-28 決定）。
- **預定後繼的確認出生、就緒與取消**（需求規格 7.7、LINE-42）：確認出生只限尚未出生的預定後繼：連到那筆配種的產駒還沒有時阻止，產駒是牝時阻止（預定後繼失效，由使用者取消）；公駒以 `verifySuccessor` 再核對，通過後改存馬匹、拿掉配種紀錄，就緒為競走中。就緒在競走中與已引退待指定之間切換，只限已出生的預定後繼，和目前相同時阻止。取消只限預定後繼（狀態留空），刪除那一列並寫事件；已接任的改用「種牡馬狀態」（使用者 2026-09-28 決定）。
- **正式接任與更換現任**（需求規格 7.7、9.6、PED-08、LINE-22、LINE-30、STL-03）：對象是自家公駒，格位取出生紀錄的系與代數，不由畫面選；不是自家公駒時丟出錯誤。以 `verifySuccessor` 核對，不符時阻止。他在那一格是預定後繼或已被取代時沿用那一列；已退出生產行列或已引退時阻止（先用「種牡馬狀態」更正）；已在崗時阻止；那一格尚未出生的預定後繼指定的就是他出生的配種時阻止，先確認出生（使用者 2026-09-29 決定）；沒有任用時新增一列。那一格另有接任過的任用（在崗、已被取代、退出生產行列、已引退）時是更換現任，要附 7.7 的原因；第一次接任不需原因；同一格其他還沒接任的預定後繼不算。以 `chooseIncumbent` 套用：他改為在崗並拿掉就緒，同一格原本在崗的改為已被取代；上一代的現任（交接期間可同時在崗）與這一系其他的預定後繼不動，前任的配種、產駒與血緣保持原連結。生效年為目前遊戲年。種牡馬馬番号選填，寫法不符時阻止，有填時記一筆種牡馬階段。事件記格位、原因與被取代的馬。兄弟比較只提供讀取（見「規則輸入快照的彙整」的種牡馬紀錄），由畫面以 `checkBrothers` 檢查；接任不另外檢查同父，因為其他原因的更換本來就不要求同父。保留原現任時不寫任何紀錄（使用者 2026-09-28 決定）。

#### 備份與還原

備份、還原與危險區（需求規格 12.1、12.2）由儲存子計畫 3-1 負責；檢查點（3-2）、瀏覽器整合（3-3）與封存（3-4）沿用這裡的整局讀寫與備份格式（使用者 2026-09-29 確認；2026-09-30 把封存從 3-3 拆出）。

- **整局資料**：`GAME_TABLES` 列出一局的資料表，匯出、還原、回溯、檢查點的內容、刪除與計算筆數都用這份清單。不屬於一局資料的表明示排除：全域的 `meta`，檢查點的兩張表（備份不含檢查點，回溯要清掉整局資料而留下檢查點，刪除一局時另外刪），以及封存索引 `archives`（不屬於任何一局，局刪除後保留）；測試確認每一張表不是在 `GAME_TABLES`，就是在排除清單裡，之後加表時一併更新（使用者 2026-09-29 決定）。讀出整局在單一唯讀交易內完成，得到一致的快照（需求規格 12.2）。
- **應用版本**：取 `package.json` 的 `version`，由 Vite 的 `define` 注入（Vitest 共用同一份設定）。建立遊戲局、還原與每個寫入操作都把遊戲局的應用版本設為目前版本（需求規格 12.1「最後寫入這一局的管理器版本」）。
- **備份檔**：一個 JSON 物件，欄位依序為格式識別 `format`（`wpstudbook-backup`）、結構版本 `schemaVersion`（Dexie 的版本號）、應用版本、匯出時間、遊戲局摘要（識別、局名、起始年、目前遊戲年）、各集合的筆數 `counts`、集合 `collections`（`GAME_TABLES` 每張表一個陣列，資料列原樣）與 `sha256`。雜湊是 `sha256` 以外的欄位依上述順序 `JSON.stringify` 後，UTF-8 位元組的 SHA-256（小寫十六進位）；驗證時拿掉 `sha256` 重新序列化再比對，`JSON.parse` 保留欄位順序，所以結果一致。留空的欄位在資料列裡本來就不存在，`0`、空字串與 `false` 原樣保留（DATA-03）；寫入操作不留下值為 `undefined` 的欄位。JSON 不縮排；有 `CompressionStream` 時 gzip 成 `.json.gz`，否則輸出 `.json`（DATA-06）。
- **匯出**：先取現在時間作為匯出時間，再以唯讀交易讀出整局；序列化、雜湊與壓縮在交易外進行，因為它們是瀏覽器的非同步 API，不能放在 Dexie 交易內。檔名為 `WPStudBook_<局名>_<目前遊戲年>年_<YYYYMMDD-HHmmss>` 加副檔名，時間用本機時間，局名裡 Windows 檔名不允許的字元（`\ / : * ? " < > |` 與控制字元）換成 `_`，超過 60 字時只取前 60 字（使用者 2026-09-29 決定）。時間只到秒：同一秒內再匯出局名與目前遊戲年都相同的局時檔名相同，寫入備份資料夾時覆寫前一份（使用者 2026-09-30 決定接受）。回傳檔名、位元組與摘要：檔名、局名、各集合筆數與總筆數、大小、結構版本、應用版本、匯出時間與是否壓縮（DATA-07）。匯出只讀，不觸發下載；下載與寫入備份資料夾見「瀏覽器整合」。
- **最近備份時間**：由呼叫端在交出檔案（觸發下載，或寫入備份資料夾成功）後另外記錄，設為匯出時間，只往後不往回；不改更新時間與應用版本，因為記錄備份不是資料變更。用快照的時間而不用記錄的時間：快照之後的修改，更新時間晚於最近備份時間，仍算未備份（需求規格 12.2「備份提醒」）。匯出與記錄分開，是因為 3-3 寫入資料夾失敗時要改為自動下載，確定交出後才記錄。
- **讀取與驗證**：依序檢查，任一步不通過就回傳拒絕與原因，資料不變（DATA-04）。這屬於第 5 章的資料來源異常，以回傳結果表達，不丟例外。
  1. 解壓：開頭是 `1F 8B` 時以 `DecompressionStream` 解壓，失敗為錯誤或截斷的 gzip，瀏覽器不支援解壓時也拒絕；其他開頭當作未壓縮的 JSON。
  2. 解析：UTF-8 嚴格解碼後 `JSON.parse`，失敗為截斷或不是 JSON。
  3. 格式：格式識別相符、結構版本是 1 以上的整數，否則不是備份檔。
  4. 版本：結構版本大於目前版本時為未來版本，附版本號。
  5. 雜湊：依「備份檔」重算並比對，在遷移前進行；重算失敗（例如極深的巢狀）也是雜湊不符。
  6. 遷移：較舊的結構版本逐版套用遷移函式。結構版本 1 是第一版，目前沒有遷移；遷移表可由參數傳入，測試以假的遷移驗證（DATA-05）。
  7. 欄位：集合剛好是 `GAME_TABLES`，多或少都拒絕；每一列是物件，主鍵欄位存在且型別正確，遊戲局欄位等於這一局；`games` 與 `settings` 各一列；`games` 那一列另外驗證儲存層會取用的欄位：局名、建立與更新時間是字串，起始年與目前遊戲年是整數（使用者 2026-09-29 決定）；遊戲局摘要與 `games` 那一列一致。時間欄位（匯出時間，以及 `games` 那一列的建立與更新時間、有值時的最近備份時間）要是 `toISOString()` 格式的字串，備份提醒以它們計算：`new Date(值)` 有效，而且轉回 `toISOString()` 與原字串完全相同；最近備份時間的欄位存在就檢查，`null` 也不符（使用者 2026-09-30 決定；儲存子計畫 3-4 實作）。其他欄位不逐欄驗證型別與列舉值：檔案完整性由雜湊保證，全面驗證要隨每次改表同步。
  8. 重複：各表主鍵不重複，所有 `id` 跨表也不重複，因為還原時所有識別共用一張新舊對照表。
  9. 關聯：`horses` 的父、母指向 `horses`，出生紀錄的配種指向 `breedings`；`mares`、`horseNumbers` 與 `events` 的馬匹指向 `horses`；`mareYears` 的馬匹指向 `mares`；`stallions` 的馬匹、配種、補系分別指向 `horses`、`breedings`、`restorations`；`breedings` 與 `matingRatings` 的母馬指向 `mares`，種牡馬指向 `horses`；`imports` 的被更正的那一筆（`corrects`），以及 `events` 與 `horseNumbers` 來源裡的匯入紀錄（`source.importId`），指向 `imports`（4.4「流程」）。指向 `mares` 的，現有寫入操作都已要求母馬在 `mares`。事件內容裡的引用不查：取消預定後繼會刪除任用列，事件裡的任用識別本來就可能懸空。
  10. 筆數：`counts` 的鍵與各集合的筆數相符；只看集合自己的鍵，不讀到繼承的屬性（例如 `constructor`）。

  通過時回傳驗證過的備份與預覽：局名、起始年與目前遊戲年、匯出時間、結構版本、應用版本、各集合筆數與總筆數。可傳進度回呼，回報解壓、解析、驗證等步驟（需求規格 12.2「大型檔案顯示進度」）。
- **還原**：一律還原成新遊戲局（需求規格 12.2），在一個 rw 交易內寫入全部資料表，失敗時整筆回復。
  - 識別重新產生：遊戲局與各列的 `id` 換成新的 UUID，任何欄位（含事件內容）中整個字串等於舊識別的值一律換成新的，懸空的引用保持原值。原局通常還在同一個瀏覽器裡（12.2「還原後再到危險區刪除舊局」），保留原識別會撞到它（使用者 2026-09-29 決定）。
  - 局名用呼叫端傳的，沒傳時用備份的局名；空白時丟 `RangeError`，同建立遊戲局；可以與既有的局重複，由畫面預填。
  - 建立時間為還原的時間，更新時間沿用備份的（資料最後修改的時間）；應用版本為目前版本；最近備份時間為備份的匯出時間，因為內容與備份檔相同，沒有未備份的變更。
  - 還原來源記檔名、匯出時間、原局名、備份的應用版本與結構版本；結構版本比目前舊就是經過遷移，這就是 DATA-05 的紀錄。
  - 寫入時依集合回報進度（已寫筆數與總筆數）。不切換目前遊戲局，回傳新局，由畫面決定。

#### 檢查點與回溯

檢查點與回溯（需求規格 11.1、12.4）由儲存子計畫 3-2 負責，沿用「備份與還原」的整局讀寫與備份格式（使用者 2026-09-29 決定）。

- **資料表**：中繼資料與內容分成兩張表，都不屬於 `GAME_TABLES`（見「整局資料」）。以設計目標的單局 3 萬列估算，內容 gzip 後約 1 MB，12 個約 12 MB；IndexedDB 只能整列讀寫，分表後開啟清單與釘選只讀寫幾 KB（使用者 2026-09-29 決定）。
  - `checkpoints`（主鍵 `id`，索引 `gameId`）：遊戲局、建立方式（年度匯入後自動、手動）、年、時點（選填）、補匯的年與時點（直接補匯時，CKPT-08）、建立時間、SHA-256（內容檔案裡的 `sha256`）、註記（選填）、是否釘選（只讀取不建索引，存布林值）。
  - `checkpointContents`（主鍵 `checkpointId`，索引 `gameId`）：內容的位元組。
- **內容**：與備份檔相同的位元組，建立時間就是檔案的匯出時間。匯出與檢查點共用同一個編碼函式（組出內容、雜湊與壓縮），沒有 `CompressionStream` 時同樣存未壓縮的 JSON。驗證沿用備份的讀取與驗證，結構升版後，舊檢查點在回溯時逐版遷移（使用者 2026-09-29 決定）。
- **年與時點**：年取建立當下這一局的目前遊戲年，所以回溯後的目前遊戲年一定等於檢查點的年（CKPT-06）。時點由呼叫端傳入：年度匯入由 CE 匯入傳目前進度的時點，直接補匯另傳補匯的年與時點（需求規格 12.4）；手動建立由畫面決定是否帶時點（使用者 2026-09-29 決定）。建立的輸入 `NewCheckpoint` 維持一個型別，不分自動與手動做成聯合型別：會建立自動檢查點的只有 CE 匯入的 `applyImport`，它一定帶時點，由它的測試驗證；改成聯合型別要改既有的 55 處測試（CE 匯入子計畫 4-2，使用者 2026-10-01 決定）。
- **建立**：先取現在時間作為建立時間，再以唯讀交易讀出整局（一致快照）；編碼在交易外進行，再以一個 rw 交易寫入兩張表並清除超過保留個數的檢查點，回傳新的檢查點與被清除的檢查點。時點不是 1～12 月、1～4 週，或補匯的年不是整數時丟出 `RangeError`；註記去除前後空白，空白時不存。建立檢查點不是資料變更，不改遊戲局的更新時間與應用版本（同「最近備份時間」）。檢查點的建立與年度匯入的交易分開，因為瀏覽器的非同步 API 不能放在 Dexie 交易內；匯入提交後、檢查點寫入前關閉頁面時，那次匯入沒有檢查點。
- **保留**：這一局未釘選的檢查點依建立時間由新到舊，超過保留個數（`settings` 的 `checkpointLimit`，預設 12，要是 1 以上的整數）的連同內容刪除；釘選的不計入也不刪除。剛建立的一定留著，其他未釘選的最多留保留個數減一個：系統時鐘往回調時，新檢查點的建立時間可能不是最新的，不能讓它被自己清掉（使用者 2026-09-29 決定）。只在建立時清除：取消釘選或調低個數不會立即刪除，免得使用者剛取消釘選的檢查點當場消失（使用者 2026-09-29 決定）。
- **管理**：列出一局的檢查點（只讀中繼資料，由新到舊）、釘選與取消釘選（不觸發清除）、事後修改註記（空白時移除），都不改遊戲局的更新時間；找不到遊戲局、檢查點，或檢查點屬於其他局時丟出錯誤。不提供手動刪除單一檢查點（使用者 2026-09-29 決定）。
- **驗證與預覽**：以一個唯讀交易讀出遊戲局、檢查點、內容、目前整局資料與較晚的檢查點；交易外依「讀取與驗證」驗證內容，再核對檢查點的 `sha256` 等於檔案的 `sha256`、檔案的遊戲局識別等於這一局。不通過時回傳拒絕與原因，資料不變（CKPT-05）：備份的拒絕原因之外，另有內容不見與內容對不上。通過時回傳驗證過的檢查點（已遷移到目前的結構）與預覽（CKPT-04）：檢查點本身、目前遊戲年的變化、各表目前與檢查點的筆數、將捨棄的事件（目前有而檢查點沒有的事件，依寫入時間排序）、將移除的較晚檢查點（建立時間晚於這個檢查點，含釘選的），以及預覽當下遊戲局的更新時間。每個寫入操作都寫事件，所以將捨棄的事件就是將捨棄的操作；設定、代表色這類操作不寫事件，預覽列不出來：設定在回溯時沿用目前的值，代表色隨系位置回到檢查點（使用者 2026-09-29 決定）。找不到遊戲局、檢查點，或檢查點屬於其他局時丟出錯誤。
- **回溯**：先以「匯出」匯出目前這一局，交給呼叫端傳入的交付函式（下載由 3-3 的輔助函式負責）；交付函式丟出錯誤時回溯停止，資料不變。接著在一個 rw 交易內（`GAME_TABLES` 與檢查點的兩張表）：遊戲局的更新時間要等於預覽時的值，否則阻止，因為預覽或備份之後有變更時，交付的備份不一定含有將捨棄的全部資料；目標檢查點要還在，否則丟出錯誤；以 `deleteGameData` 刪除整局，再以 `addGameData` 寫回檢查點的資料，識別不變；刪除較晚的檢查點與內容。回傳回溯後的遊戲局與被移除的檢查點（需求規格 12.4、CKPT-06、CKPT-07）。先驗證預覽再下載，是因為預覽本來就要解開檢查點，驗證失敗時也不會白下載一份；資料變動前一定已交出備份（使用者 2026-09-29 決定）。
  - `games` 那一列：目前遊戲年取檢查點（CKPT-06）；局名、起始年、建立時間與還原來源沿用目前的列，它們描述的是這一局本身，不是遊戲進度；應用版本為目前版本；更新時間為回溯的時間，因為回溯本身就是資料變更；最近備份時間沿用目前的列，它只往後不往回，目前的列一定不早於檢查點的列（使用者 2026-09-29 決定）。
  - 不記錄最近備份時間：交付的備份是回溯前的狀態，不含回溯後的資料；記錄下來時，匯出時間與回溯的更新時間是同一個時間，更新時間不晚於最近備份時間，備份提醒就不會請使用者備份回溯後的狀態。交付後被阻止時那次備份不記錄，最多多提醒一次。
  - `settings` 沿用目前的列：定年、提醒年齡與保留個數是管理器的設定，新設定從下一次判斷開始生效（MARE-10），不是遊戲的歷程（使用者 2026-09-29 決定）。系統對照表、系位置（含代表色）與其他資料取檢查點。
  - 回溯不寫事件：歷程整個回到檢查點，回溯前的完整狀態在交付的備份裡。

#### 危險區

- **筆數**：回傳一局 `GAME_TABLES` 各表的筆數與總筆數，供確認前顯示（需求規格 12.1「顯示筆數」）；檢查點的個數由畫面從檢查點清單另外顯示（使用者 2026-09-29 決定）。
- **永久刪除此局**：輸入的局名去掉前後空白後要等於局名，否則阻止，什麼都不刪；名稱核對放在儲存層，畫面漏掉也刪不掉。在一個 rw 交易內從 `GAME_TABLES` 刪除這一局的資料列，連同這一局的檢查點與內容（需求規格 12.4，使用者 2026-09-29 決定）；`meta` 的目前遊戲局指向這一局時一併清除，由畫面請使用者重新選局。不寫事件，因為這一局已不存在。回傳刪除的各表筆數；找不到遊戲局時丟出錯誤。
- **刪除全部存檔**：輸入的文字要是「刪除全部存檔」，否則阻止；第二道確認由畫面負責（需求規格 12.1，使用者 2026-09-29 決定）。在一個交易內清空資料庫的每一張表（含 `meta`），檢查點的兩張表也包含在內；只保留 `meta` 的備份資料夾，它是管理器的設定，不是存檔（需求規格 12.1、DATA-19，使用者 2026-09-30 決定）。封存索引一併清除：它記的是被封存的局，不是管理器的設定；封存檔在外部，仍可用匯入備份還原（需求規格 12.1、DATA-23，使用者 2026-09-30 決定）。回傳刪除的遊戲局數與總筆數；總筆數只算 `GAME_TABLES`，不含檢查點（使用者 2026-09-29 決定）。

#### 瀏覽器整合

下載、持久保存、備份資料夾、自動備份與備份提醒（需求規格 12.2）由儲存子計畫 3-3 負責；封存拆到 3-4（使用者 2026-09-30 決定）。4.1 把持久保存與備份資料夾劃給 `storage`，這裡的函式直接使用瀏覽器 API；畫面、CE 匯入與進入點負責在適當的時機呼叫。

- **下載**：`downloadFile` 以位元組建立 Blob（gzip 為 `application/gzip`，否則 `application/json`），取得 `URL.createObjectURL` 的網址，建立帶 `download` 屬性的 `<a>` 並呼叫 `click()`（不必掛到頁面上），1 分鐘後才 `revokeObjectURL`，免得大檔還沒讀完。觸發下載就算交出：頁面無法得知使用者有沒有存檔（同「備份與還原」的最近備份時間）。`downloadBackup` 下載匯出的備份，簽章符合回溯的交付函式 `deliverBackup`，只交出檔案，不記錄最近備份時間（見「檢查點與回溯」）。環境沒有 `document` 或 `URL` 時丟出例外，回溯因此停止，資料不變。
- **備份資料夾**：全部遊戲局共用一個，檔名含局名與到秒的時間，不會互相覆蓋；同一秒內再備份局名與目前遊戲年都相同的局時覆寫前一份，見「備份與還原」的匯出（使用者 2026-09-30 決定）。資料夾的 `FileSystemDirectoryHandle` 存在 `meta` 的 `backupFolder` 鍵，關閉瀏覽器再開啟後仍能沿用（第 7 節）；`meta` 的列依鍵區分型別：`currentGame` 存字串，`backupFolder` 存資料夾。TypeScript 的 DOM 型別還沒有 `showDirectoryPicker`、`queryPermission`、`requestPermission`，只宣告用到的部分。備份檔不含 `meta`，資料夾不隨備份還原。
  - 支援：瀏覽器有 `showDirectoryPicker` 才支援。
  - 選擇：由使用者點擊觸發，以 `showDirectoryPicker({ mode: 'readwrite' })` 選擇後存入，取代原本的資料夾；回傳選好（附資料夾名稱）、使用者取消或不支援，其他錯誤照常丟出。另有讀出目前的資料夾（供畫面顯示名稱）與清除資料夾設定。
  - 交付目標：`prepareBackupTarget` 要在點擊處理的最前面呼叫，因為瀏覽器只在使用者剛操作後的短時間內允許 `requestPermission`（第 7 節）。依序判斷：不支援時為下載（`unsupported`）；沒有資料夾時為下載（`not-set`）；`queryPermission` 為 `granted` 時為資料夾；否則呼叫 `requestPermission`，`granted` 時為資料夾，拒絕或丟出例外時為下載（`denied`，例外時附錯誤訊息）。權限的查詢與申請不丟例外，最壞是改為下載；讀取 `meta` 失敗是預期外的失敗（第 5 章），照常丟出（使用者 2026-09-30 決定）。
  - 寫入：`getFileHandle(檔名, { create: true })`、`createWritable()`、寫入位元組、`close()`；中途失敗時 `abort()`，瀏覽器丟掉暫存，不留下寫一半的檔案。資料夾被刪除、改名或磁碟已滿都在這一步失敗。
- **儲存備份**：`saveBackup` 先以「備份與還原」的匯出取得備份（遊戲局不存在時丟出錯誤，什麼都沒交出），再交付：目標是資料夾時寫入，失敗時改為下載；目標是下載時直接下載。下載丟出例外時照常丟出，不記錄。交出後才以 `recordBackup` 記錄最近備份時間（匯出時間）。回傳備份摘要（DATA-07）、記錄後的遊戲局與實際的交付方式：寫入資料夾（附資料夾名稱），或下載（附原因 `unsupported`、`not-set`、`denied`、`write-failed` 與錯誤訊息；呼叫端自己選擇下載時沒有原因）。自動備份與手動匯出共用；手動匯出要不要也寫資料夾由畫面計畫決定（使用者 2026-09-30 決定）。
- **自動備份的時機**：年度匯入按下「套用」時先 `prepareBackupTarget`，再做匯入的交易、建立檢查點，最後 `saveBackup`（4.4「資料流」第 7 步）；這個順序由 CE 匯入的 `applyImport` 負責（4.4「流程」）。權限要在耗時處理之前申請，備份要在資料寫入之後匯出，所以分成兩個呼叫（使用者 2026-09-30 決定）。自動備份失敗時匯入已經提交，不回復；最近備份時間沒有更新，備份提醒照常出現。回溯維持自動下載（需求規格 12.4），交付函式是 `downloadBackup`，不寫資料夾。
- **持久保存**：`requestPersistence` 回傳是否支援與是否取得：沒有 `navigator.storage.persist` 時為不支援、未取得；已經持久（`persisted()`）時不再申請；否則回傳 `persist()` 的結果；例外視為未取得，不丟出。結果不存進資料庫：它是這次開啟時瀏覽器的狀態，每次開啟重新申請，由進入點呼叫、畫面顯示（4.1）。
- **備份提醒**：純函式，由遊戲局、設定、是否取得持久保存與現在時間算出（需求規格 12.2、DATA-14、DATA-16、DATA-18）。放在 `storage`，因為它讀的是 `games` 與 `settings` 的列，與最近備份時間是同一件事；`core` 只放遊戲規則。
  - 基準時間：最近備份時間，沒有時用建立時間。更新時間晚於基準時間才算有未備份的變更，所以剛建立的局不提醒（使用者 2026-09-30 決定）。時間都是 `toISOString()` 的字串，可以直接比較。
  - 天數：基準時間到現在經過的完整 24 小時數，不足 0 時取 0（系統時鐘往回調）；以經過時間計，不受時區影響。
  - 醒目：有未備份的變更，且經過時間超過設定的備份提醒天數乘以 24 小時。
  - 未取得持久保存：另外回報，提醒區常駐顯示說明，不改變天數的規則。`file://` 下幾乎一定取不到（第 7 節），改成醒目會常態亮起（使用者 2026-09-30 決定）。
  - 設定：`settings` 的 `backupReminderDays`，預設 7，要是 1 以上的整數（見「寫入操作」的設定）。發布前的舊備份缺這個欄位時不另外處理，同檢查點的保留個數。
- **刪除全部存檔**：保留 `meta` 的備份資料夾，見「危險區」。
- **測試**：Vitest 維持 `node` 環境，不加 jsdom。下載以 `vi.stubGlobal` 換掉 `document`（Node 本身有 `Blob` 與 `URL.createObjectURL`），以假計時器確認釋放網址的時間；資料夾的權限與寫入用假的資料夾物件；資料夾存進 `meta` 的來回以純資料物件測（fake-indexeddb 存物件時會丟掉方法）；持久保存以 `vi.stubGlobal` 模擬 `navigator`。不是由點擊直接觸發的下載由 Playwright 測，資料夾與權限詢問在 Edge 手動驗證（第 7 節「儲存整合的驗證」）（使用者 2026-09-30 決定）。

#### 封存

封存舊遊戲局與封存索引（需求規格 12.3）由儲存子計畫 3-4 負責，沿用「備份與還原」的匯出、讀取與驗證、還原，刪除沿用「危險區」的永久刪除此局（使用者 2026-09-30 決定）。流程拆成兩個呼叫，中間由畫面下載並取得使用者確認。

- **準備**：`prepareArchive` 先確認瀏覽器有 `CompressionStream`，沒有時回傳拒絕（`compression-unsupported`），什麼都不讀：封存檔一律是 `.json.gz`，不比照備份改存 `.json`（需求規格 12.3，使用者 2026-09-30 決定）。接著以「匯出」匯出這一局（遊戲局不存在時丟出錯誤），再以「讀取與驗證」在記憶體讀回同一份位元組（解壓、雜湊、欄位、重複、關聯與筆數），不通過時原樣回傳拒絕原因，不丟例外。通過時回傳準備好的封存：匯出的備份（畫面拿去下載，重新下載也用它）、封存後要寫入的索引列，以及快照當下遊戲局的更新時間（取自驗證過的檔案裡 `games` 那一列，與快照是同一個時間點）。只讀。
- **確認**：畫面以 `downloadBackup` 下載，使用者勾選已下載並輸入局名；確認前以 `listCheckpoints` 顯示將一併刪除的檢查點個數，含釘選的（需求規格 12.3）。頁面無法得知使用者有沒有存檔（同「瀏覽器整合」的下載），這一步由畫面負責；儲存層保證沒通過驗證就拿不到準備好的封存，局名不符或有異動就刪不掉（DATA-09、DATA-20）。
- **封存**：`archiveGame` 在一個 rw 交易內（`GAME_TABLES`、`meta`、檢查點的兩張表與 `archives`）：遊戲局的更新時間要等於準備時的值，否則阻止（`changed-since-archive`），什麼都不刪，由畫面請使用者重新產生（需求規格 12.3「封存後有異動須重新產生」）；接著呼叫「永久刪除此局」（成為子交易），局名不符時阻止（`name-mismatch`），通過時刪除整局、這一局的檢查點與內容，`meta` 的目前遊戲局指向這一局時一併清除；最後寫入索引。回傳索引與刪除的各表筆數。不寫事件，因為這一局已不存在。遊戲局已不存在時丟出錯誤（例如同一份封存送出兩次）。每個寫入操作都會更新遊戲局的更新時間（見「寫入操作」），所以核對更新時間就能發現異動；自動備份的 `recordBackup` 與建立檢查點都不改更新時間，不會擋下封存：前者只改檔案裡的最近備份時間，還原時會改成匯出時間，後者建立的檢查點隨這一局刪除。
- **交付**：只用下載，不寫備份資料夾：封存檔是本機刪除後唯一的一份，要由使用者自己放到長期保存的位置；寫進資料夾會與自動備份混在一起，「確認已下載」也要多一種說法（使用者 2026-09-30 決定）。
- **索引**：`archives`（主鍵 `id`）是全域的表，不帶遊戲局欄位，不屬於 `GAME_TABLES`（見「整局資料」）：備份與檢查點不含它，永久刪除此局不碰它，刪除全部存檔時清除（見「危險區」）。一列記：`id` 為原遊戲局的識別（封存後原局已刪除，還原一律換新識別，所以不會重複，也查得到來源）、局名、封存檔的應用版本與結構版本（結構版本決定之後讀不讀得了）、起始年與封存時的目前遊戲年（年份範圍）、封存檔的匯出時間（也是檔名裡的時間）、檔名、各表筆數（總筆數由它加總，不另存；`GAME_TABLES` 加表後舊索引缺少新表的鍵，加總時當作 0，CE 匯入子計畫 4-2 加入），以及驗證摘要：封存檔裡的 `sha256`，與檢查點核對內容的方式相同（需求規格 12.3，使用者 2026-09-30 決定）。
- **從封存還原**：`listArchives` 列出全部索引，依匯出時間由新到舊。`readArchive` 以「讀取與驗證」讀使用者選的檔案（可傳進度回呼），拒絕原因原樣回傳；檔案的 `sha256` 與索引不同時拒絕（`archive-mismatch`，選錯檔案）；通過時回傳驗證過的備份，畫面再以「還原」還原成新遊戲局，還原來源記下檔名等資訊。還原不消耗封存檔，可以重複還原，所以索引保留；`removeArchive` 只刪索引，不影響檔案，要不要先確認由畫面決定。找不到索引時兩者都丟出錯誤（DATA-21，使用者 2026-09-30 決定）。封存檔本身就是備份檔，沒有索引時（例如刪除全部存檔之後）也能走一般的匯入備份還原。
- **測試**：Vitest 以 `vi.stubGlobal` 拿掉 `CompressionStream`，或換成會截斷輸出的假串流，讓讀回驗證失敗。封存的下載就是既有的 `downloadBackup`，不是由點擊直接觸發的下載已在 3-3 驗證（第 7 節「儲存整合的驗證」），所以不加端對端測試，也不另做 Edge 手動驗證（使用者 2026-09-30 決定）。

#### 資料流

以年度匯入為例，對應需求規格 11.1 的流程（使用者 2026-10-01 決定）：

1. 畫面取得檔案（選檔或拖放，一次一個）。
2. `ce-import` 讀檔：解碼，並從檔名解析年與時點、預選類型；使用者確認類型與年份。
3. `ce-import` 解析：依類型的格式驗證欄數與必要欄位，依位置讀成該格式的列；整份停止的檢查都在這一步（見「解析」）。
4. `storage` 讀資料庫，組出核心的匯入比對快照：既有馬匹、母馬、配種紀錄、匯入紀錄、目前進度與遊戲局的更新時間。
5. `ce-import` 以快照與 `core` 比對身分，產生差異預覽（可套用、略過、待核對、警告、錯誤），並判斷重複、資料更正、直接補匯、回溯與推進年份。
6. 畫面顯示預覽，使用者修改用途、決定待核對的處理並確認警告；`ce-import` 產生核心的套用計畫。
7. 按下「套用」時呼叫 `storage` 的套用（`applyImport`）：年度匯入先以 `prepareBackupTarget` 取得交付目標（第一個 `await`，見 4.3「瀏覽器整合」）；接著開一個 rw 交易，先核對遊戲局的更新時間與快照相同，不同時回傳 `changed-since-preview`，由畫面重新預覽；需要時先推進年份，再把計畫逐項交給寫入操作（巢狀交易，見 4.3「寫入操作」），寫入匯入紀錄。交易提交後，年度匯入建立檢查點並依需求規格 12.2 自動備份；這兩步失敗不撤銷匯入，結果附上失敗的原因。
8. 畫面顯示結果摘要。

任一步發生阻擋錯誤時，交易不會開始，或者整筆回復，資料保持不變（IMP-06）。

- `ce-import` 與 `storage` 互不引用（4.1）：匯入比對快照與套用計畫的型別放在核心（4.2）。`ce-import` 是純函式、不碰 Dexie；`storage` 不解析檔案；畫面只負責串接與顯示。套用、檢查點與自動備份的先後由 `storage` 負責，可以用 `fake-indexeddb` 測試。
- 套用計畫的每一項對應一個寫入操作：既有的（例如自家母駒轉入、買回與回歸），或 CE 匯入新加的（例如年度資料、階段馬番号、補齊血統）。各操作在交易內照常重做規則檢查，任一項阻止時整筆回復。
- 匯入紀錄（需求規格 11.1）加進 `GAME_TABLES`，連同 `PRIMARY_KEYS` 與 `RELATIONS`；事件記匯入紀錄的識別。目前進度由匯入紀錄推導，取年度匯入中最大的年與時點，不另外保存：直接補匯不會讓進度倒退，回溯時匯入紀錄隨檢查點一起回復。欄位見下方「流程」；DATA-02 的別名是一月取代手動名時保存的別名（BRD-09），存在 `horses` 的 `aliases`（見下方「一月」）。

#### 解析

由 CE 匯入子計畫 4-1 負責（使用者 2026-10-01 決定）。分兩步，中間由使用者確認類型與年份：

- **讀檔**（`readImportFile`）：
  - 解碼：先以 UTF-8 嚴格解碼（有 BOM 時去掉），失敗再以 CP932（`TextDecoder('shift_jis', { fatal: true })`）嚴格解碼，兩者都失敗時停止。純 ASCII 用哪一種解碼結果都相同，日文的 CP932 位元組幾乎不會剛好是合法的 UTF-8，所以先試 UTF-8 不會誤判；反過來 UTF-8 的位元組常常也能以 CP932 解開（例如 `é` 會變成 `ﾃｩ`），所以不能先試 CP932。BOM 開頭的位元組（`EF BB`）在 CP932 沒有對應的字元，有 BOM 但不是合法 UTF-8 的檔案也不會被當成 CP932。
  - 檔名：開頭為「`YYYY年 M月W週`」（空白可有可無，月 1～12，週 1～4）時取出年與時點。類型依 `_` 或 `._` 之後的名稱預選：`二歲新馬` 為一月二歲馬總表，`幼駒誕生` 為四月誕生幼駒名單，`種牡馬` 為種牡馬總表，`繁殖牝馬` 依月份，5 月為五月繁殖圈名單、7 月為七月受胎名單、10 月為十月全世界繁殖牝馬總表，其他月份不預選。候選 TXT 與目標種牡馬 TXT 沒有樣本（需求規格 Q-03），不預選。解析不了時年、時點與類型都留空，由使用者選（IMP-03）。
- **解析**（`parseImportFile`，傳入確認後的類型與年份）：
  - 分行與分隔：CRLF 與 LF 都接受，略過檔尾的空行。表頭含 Tab 時為 Tab 分隔，否則為逗號分隔；逗號分隔時處理雙引號包住的欄位（欄位內的逗號，以及以兩個雙引號表示的雙引號）（IMP-22）。
  - 欄數：附錄 A 的欄數（78、63、61、63，含尾端的空白欄），尾端空白欄可有可無；資料列的欄數要與表頭相同。
  - 欄名：只比對要讀的位置，表頭在那些位置的欄名要與附錄 A 相同。四月誕生幼駒名單與種牡馬總表都是 63 欄，以此區分（IMP-04）。
  - 依位置讀附錄 A 的主要欄位（另外各格式都讀第 2 欄 `国`），產生四種格式的列（二歲馬、幼駒、繁殖牝馬、種牡馬）：
    - 數值與副能力帶括號附加值時取括號前的主值（`72(72)`、`42( +0)`、`B(0)`）。整數欄不是 0 以上的整數、`活力` 不在 0～100、`性` 不是 `牡`、`牝` 之一、副能力不是 `isSubAbilityGrade` 接受的等級、芝與ダ不是 `◎○△×` 之一時停止。
    - 能力番号與馬番号以 `normalizeAbilityNumber` 統一寫法，格式不符時停止。史実番号不讀（JAN-07）。
    - 番号欄（`生牧`、`馬主`、`繋牧`、`牧場`）空白時當作沒有值，下面的範圍檢查把空白也視為範圍異常（MAY-01「缺少」）。
    - `父系` 以 `normalizeSystemName` 去掉結尾「系」（IMP-17）。`活力` 的前置 `*` 表示増強。
    - 馬名與父母名保留原文、不修剪；基本馬名另讀最後一個 `馬名` 欄（附錄 A、JAN-06），比對階段以 `splitHorseName` 核對第 1 欄。兩者不一致時存哪一個、算不算資料異常由 4-3 一月決定（使用者 2026-10-01 決定）。
    - 出生年＝年份減 `年` 欄馬齡，各格式通用：一月二歲馬總表全是 2 歲，等於年份減 2；四月誕生幼駒名單是 0 歲，等於年份。
  - 整份停止的檢查：四月誕生幼駒名單的 `年` 不是 `0`、馬主不是 `46／47`、繋牧不在 `32`～`35`（需求規格 11.4、APR-04；性別見上）；五月與七月名單的牧場不在 `32`～`35`（MAY-01、11.6）；七月名單的 `状態` 不是四種之一（JUL-06）；目標種牡馬 TXT 不是剛好一筆（STL-04）；任何類型的檔內能力番号重複（`duplicateAbilityNumbers`，4.2）。
  - 結果：成功時回傳列；失敗時回傳全部問題（原因、行號、欄名與檔案裡的值；欄位格式與表頭的問題另附欄號），畫面可以一次列出。格式錯誤都是阻擋錯誤（IMP-06），解析不做「略過該筆」；略過非管理的馬或其他牧場屬於比對階段。表頭不能用（沒有任何一行、欄數或欄名不符）時不讀資料列，也不做整份停止的檢查；有格式錯誤的列不採用，整份停止的檢查只看讀得出來的列；但目標種牡馬 TXT 的筆數以資料列數計，不論那一列讀不讀得出來，好讓問題一次列出（使用者 2026-10-01 決定）。只有表頭、沒有資料列的檔案視為 0 筆，目標種牡馬 TXT 除外。
- `ImportType`、`GameTiming`、`Sex`、`SurfaceAptitude`、`Vigor`、`Conception` 從 `storage/records.ts` 移到核心；`records.ts` 從核心引用並轉出，儲存層的其他檔案照舊從 `records.ts` 引用。
- 測試：`tests/support/ce-files.ts` 依附錄 A 的表頭（取自實檔的表頭）與虛構的值組出匯出檔的內容，驗收測試再以 `iconv-lite` 編成 CP932，或轉成 Excel 式 CSV、含 BOM 的 UTF-8；不另外產生範例檔。`tests/local/` 讀 `.references/` 的實檔，驗證 JAN-01、APR-01、STL-08、OCT-01 的筆數、欄數與出生年，沒有實檔時略過。

#### 流程

由 CE 匯入子計畫 4-2 負責（使用者 2026-10-01 決定）。計畫的項目由 4-3 以後的各塊加入，這一塊以空的計畫驗收。

- **核心的型別與常數**（`core/imports.ts`）：
  - `AnnualImportType` 是四種年度匯入，`ANNUAL_TIMINGS` 是它們的固定時點：一月 1 月 1 週、四月 4 月 1 週、五月 5 月 1 週、七月 7 月 1 週（需求規格 4.1、11.1）。`importCategory` 回傳年度、累加或選用。
  - `isGameTiming` 從 `storage/writes.ts` 搬到核心，另加時點的先後比較：先比年，再比月，最後比週。4-1 留下的重複常數一併搬到核心：受胎狀態、芝ダ適性、據點 32～35（`Base`），`ce-import` 與 `storage` 都改為引用核心。
  - 目前進度 `importProgress`：年度匯入紀錄中最大的年與時點，沒有年度匯入時沒有進度。不分套用方式：補匯的那一筆一定早於進度，資料更正的那一筆不晚於進度，全部一起取最大值結果相同。
- **匯入紀錄**（`imports`）：一列是一次套用。型別 `ImportRecord` 放在核心，因為 `ce-import` 從快照讀它。
  - 欄位：識別、遊戲局、類型、年（使用者確認的年份）、時點（年度匯入依類型固定；累加與選用照檔名，解析不了時不存）、檔名、`sha256`（檔案原始位元組的 SHA-256，小寫十六進位）、套用時間、套用方式 `mode`（`normal`、`correction`、`catch-up`）、`corrects`（資料更正時被更正的那一筆，也就是同類型、同年、同時點最新的一筆；需求規格 11.1 的「兩份來源檔與時間」由這個連結取得）、結果摘要 `summary`（這一塊定 `total`、`applied`、`skipped` 三個筆數，之後各塊再加自己的欄位）、確認過的匯入層級警告 `confirmedWarnings`（例如晚兩年以上）。
  - 主鍵 `id`，加進 `GAME_TABLES` 與 `PRIMARY_KEYS`；`RELATIONS` 加 `imports.corrects`、`events.source.importId`、`horseNumbers.source.importId`，都指向 `imports`。
  - `EventSource` 的匯入改為 `{ kind: 'import'; importType; importId }`，`importId` 必填：匯入寫的事件一定屬於某一筆匯入紀錄。
  - 套用本身不另寫事件，匯入紀錄就是歷程；推進年份照 4.3「寫入操作」的目前遊戲年，也不寫事件。最後紀錄年加上匯入紀錄的最大年份（同一處）。
- **快照**（`ImportSnapshot`，核心）：通用的部分是遊戲局識別、目前遊戲年、更新時間、這一局的匯入紀錄，以及檢查點的摘要（識別、年、時點、建立時間）。`storage` 的 `loadImportSnapshot(db, gameId, { type, year })` 在一個唯讀交易內讀出，類型與年份是使用者確認的；各類型要用的資料依類型只讀需要的部分，由 4-3 起各塊加入（一月見「一月」）（使用者 2026-10-07 決定）。
- **雜湊**：`ce-import` 的 `hashImportFile(bytes)` 以 `crypto.subtle` 算 SHA-256。核心維持同步的純函式；`ce-import` 不引用 `storage`，所以不共用備份的雜湊函式。

**判斷**（`ce-import` 的 `judgeImport`，純函式）：輸入檔名、雜湊、類型、年份、檔名解析出的時點與快照。年份不是整數時丟出 `RangeError`，`parseImportFile` 同樣檢查（4-1 留下的「確認類型與年份的介面驗證年份是整數」）。年度匯入的檔名時點與類型的時點不同時附一個只提示的說明。「同一組」指同類型、同年、同時點中套用時間最新的一筆：

| 分類 | 情況 | 結果 |
| --- | --- | --- |
| 年度 | 同一組已有，雜湊相同 | 重複，不產生計畫（IMP-07） |
| 年度 | 同一組已有，雜湊不同 | 資料更正（`corrects` 指向那一筆）；檔案早於目前進度時另外提供回溯（IMP-08、IMP-21） |
| 年度 | 沒有，晚於進度或還沒有進度 | 一般套用 |
| 年度 | 沒有，早於進度 | 回溯或直接補匯（IMP-09、IMP-20） |
| 選用 | 同一組已有，雜湊相同／不同／沒有 | 重複／資料更正／一般套用，不提示回溯 |
| 累加 | 這一局同類型的任何一筆雜湊相同 | 重複；其他情況一般套用（IMP-19） |

- 重複只和同一組最新的一筆比：先匯入 A、更正成 B，再匯入 A 是把 B 更正回 A。
- 推進年份（各分類都適用）：檔案年份晚於目前遊戲年時附上推進到的年份，使用者確認才能產生計畫（IMP-14）；晚兩年以上另附 `year-far-ahead` 警告（IMP-15），確認後記在匯入紀錄。
- 回溯的推薦：有時點、而且年與時點早於這份檔案的檢查點中，年與時點最晚的一個，一樣時取建立時間最新的；找不到時仍提供回溯，只是沒有推薦，由使用者從清單選。手動把遊戲年推到進度之前很遠時，檢查點的年是當時的遊戲年，推薦可能不準，使用者在回溯預覽（CKPT-04）確認。
- 結果：重複時附那一筆紀錄；其他情況列出可選的做法（一般、資料更正、直接補匯、回溯）、`corrects`、推薦的檢查點、推進年份與提示。

**計畫**（`ImportPlan`，核心；`ce-import` 的 `buildImportPlan(判斷結果, 使用者的選擇, 內容)` 產生，內容是各類型的預覽產生的摘要與項目）：遊戲局識別、快照當下的更新時間 `expectedUpdatedAt`、檔名、雜湊、類型、年、時點、套用方式、`corrects`、推進到的年份 `advanceYear`（不推進時沒有）、確認過的警告、摘要與項目 `items`。每一項對應一個寫入操作，型別 `ImportPlanItem` 是各類型項目的聯合型別（4-2 時沒有項目，4-3 加入一月的 `foal-name`，見「一月」；4-4 加入五月對帳的九種，見「五月對帳」）。選了判斷沒有提供的做法，或需要推進而沒有確認時丟出 `RangeError`（畫面不會送出）。回溯不是計畫的一種：回溯後資料變了，要重新組快照、重新預覽，再產生新的計畫。

**套用**（`storage` 的 `applyImport(db, plan, { now })`，畫面在「套用」的點擊處理裡直接呼叫）：

1. 年度匯入時第一個 `await` 是 `prepareBackupTarget`；順序放在儲存層，以 `fake-indexeddb` 就能測。累加與選用匯入不備份，不呼叫，免得跳出權限詢問。
2. 一個 rw 交易，範圍是 `GAME_TABLES`，巢狀的寫入操作用到的表都在內：
   - 遊戲局的更新時間不等於 `expectedUpdatedAt` 時回傳 `changed-since-preview`，什麼都不寫。
   - 有 `advanceYear` 時以 `setCurrentYear` 推進（巢狀交易）；往後推一定會成功，沒有成功時丟出錯誤，整筆回復。
   - 逐項套用 `items`：依項目的種類呼叫對應的寫入操作（巢狀交易），事件來源是 `{ kind: 'import', importType, importId }`，時點取計畫的時點，寫入時間是套用時間。某一項回傳阻止時丟出內部的例外，整筆回復，推進年份與前面的項目都不留；`applyImport` 在交易外接住，回傳 `item-blocked`，附第幾項（`index`，從 0 起算）、那一項，與寫入操作的阻止原因（`ImportItemBlock`，各類型寫入操作的阻止原因的聯合型別）。被阻止時不建立檢查點、不備份（CE 匯入子計畫 4-3，使用者 2026-10-07 決定）。某一項回傳待確認時同樣丟出內部的例外、整筆回復，回傳 `item-unconfirmed`，附第幾項、那一項與寫入操作的警告；畫面請使用者確認後，把那一項標為已確認（項目的 `confirmed` 為 true，套用時傳給寫入操作的 `confirmed`），重新產生計畫再套用。只有可能要確認的項目帶 `confirmed`（五月對帳的 `mare-return`、`mare-create`、`mare-usage`；可以確認的種類由項目型別有沒有 `confirmed` 推導，兩邊不會不同步），其他項目回傳待確認時丟出錯誤（預期外的失敗）。一次只回報第一個要確認的項目：要確認的只有用途把關改掛時的 8.3 與 7.3 警告，很少同時出現兩筆（CE 匯入子計畫 4-4，使用者 2026-10-08 決定）。
   - 以 `runWrite` 寫入匯入紀錄（識別事先產生），遊戲局的更新時間跟著更新。
3. 交易提交後（只有年度匯入）：先 `createCheckpoint`（`auto`，時點是套用後的目前進度，直接補匯另傳補匯的年與時點；資料更正與補匯不改變進度，所以時點仍是原本的進度，CKPT-08），再以第 1 步的目標 `saveBackup`。兩步各自以 try/catch 包住：失敗不撤銷匯入，檢查點失敗也照樣備份，結果附上錯誤訊息（IMP-12、DATA-15）。套用時間同時用作匯入紀錄的套用時間、遊戲局的更新時間、檢查點的建立時間與備份的匯出時間：自動備份成功後最近備份時間等於更新時間，備份提醒不會把這次匯入算成未備份的變更。
4. 回傳匯入紀錄、檢查點的結果與備份的結果，或阻止（`changed-since-preview`、`item-blocked`、`item-unconfirmed`）。遊戲局不存在時丟出錯誤。

- **回溯後再套用**：不加儲存函式，由畫面串接：`readCheckpoint` 驗證並預覽回溯（CKPT-04）→ 確認後 `rollbackToCheckpoint`（交付函式 `downloadBackup`）→ `loadImportSnapshot` → `judgeImport`（回溯後這份檔案晚於進度，成為一般套用）→ 使用者確認新的預覽 → `buildImportPlan` → `applyImport`。舊計畫本來就會被 `changed-since-preview` 擋下；重新預覽也讓使用者看到回溯後的配對結果。驗收測試照這個順序串一遍（IMP-09）。
- **畫面的串接順序**：`readImportFile` → 使用者確認類型與年份 → `parseImportFile` → `hashImportFile` → `loadImportSnapshot` → `judgeImport` → 預覽與選擇（一月是 `previewJanuary`，使用者指定列後重新預覽，再以 `januaryContent` 產生內容；五月是 `previewMay`，使用者每做一個決定就重新預覽，再以 `mayContent` 產生內容）→ `buildImportPlan` → `applyImport`（回傳 `item-unconfirmed` 時請使用者確認，標記那一項後重新產生計畫再套用）。
- **測試**：單元測試涵蓋核心的分類、時點先後與目前進度；`judgeImport` 上表的每一格、推進與 `year-far-ahead`、回溯推薦（含時鐘往回調、沒有時點的手動檢查點）與年份不是整數；`buildImportPlan` 的兩種錯誤；`applyImport` 的 `changed-since-preview`、推進年份與寫紀錄在同一交易、`prepareBackupTarget` 是第一個 `await`、檢查點與備份失敗不撤銷、累加與選用匯入不申請權限也不建檢查點；備份驗證的三條關聯；封存索引缺少的鍵當 0。驗收測試（計畫一律用空的 `items`）：IMP-06～09、11、12、14～16、19～21，CKPT-01、CKPT-08、DATA-15；IMP-08 只驗框架的部分（要選資料更正、`corrects` 連到被更正的那一筆，兩筆的檔名、雜湊與時間都在），原值與新值由各類型的事件保存，從 4-3 起驗收；IMP-20 只驗框架的部分（補匯、標記完成、補匯的套用方式），幼駒留給 4-7 四月。

#### 一月

由 CE 匯入子計畫 4-3 負責，對應需求規格 9.4、11.2、11.3、JAN、BRD-09、IMP-05、IMP-10（使用者 2026-10-07 決定）。

- **快照**：類型是一月二歲馬總表時，`loadImportSnapshot` 在同一個唯讀交易內另讀 `january`：出生年（年份減 2）與 `foals`，也就是那一年出生的自家產駒（有出生紀錄的馬），以 `[gameId+birthYear]` 讀出。每匹帶識別、出生年、能力番号、完整馬名、基本馬名與馬名來源、已記的競走馬馬番号，以及父母名的兩種值：經匯入確認的名稱（規則同 4.3「規則輸入快照的彙整」的既有馬匹：保存的匯入名稱優先，沒有時用連結馬匹經匯入確認的基本馬名），與任何已知的名稱（保存的名稱，沒有時用連結馬匹的基本馬名，手動輸入的也算）。型別 `ImportFoal`、`JanuarySnapshot` 放在核心；其他類型不讀產駒。產駒連結的父母找不到時丟出錯誤（資料列互相矛盾，同 4.3「規則輸入快照的彙整」）。只讀一個出生年、用既有的索引，資料量是幾十匹；一律讀全部自家產駒時，每次匯入都要讀這一局所有產駒與父母，之後各塊再加母馬與配種紀錄會越來越重（使用者 2026-10-07 決定）。
- **配對**（`ce-import` 的 `previewJanuary`，純函式）：
  1. 能力番号與出生年都和一匹產駒相同的列，與那匹配成一對。
  2. 還沒有能力番号的產駒，與第 1 步沒配到的列，以父母退回配對：檔案的 `父馬`、`母馬` 以 `splitHorseName` 去掉前綴、忽略前後空白後，與產駒父母的任何已知名稱都相同，出生年也相同。產駒只配到一列、那一列也只配到這匹產駒時配成一對。產駒缺父馬或母馬名時不配對。
  3. 沒配成對的產駒列入待核對：配不到（沒有候選列）、無法唯一配對（候選兩列以上，或候選列也配到別的產駒；附候選列）、未見於總表（已有能力番号，第 1 步沒配到）。
  4. 其他的列都是非管理的馬，只計入略過，不建立任何東西（JAN-02）；出生年不是年份減 2 的列配不到產駒，也在這裡。

  零筆或多筆從產駒這一邊判斷：總表有一千多列電腦 AI 的馬，從列這一邊看會全部變成人工確認（使用者 2026-10-07 確認）。
- **配對後的檢查**（自動配成的對與使用者指定的對都做），錯誤的對不套用：
  - 以能力番号配到、經匯入確認的父母名與檔案明顯不符（兩邊都有值而且不同，忽略前後空白）時為錯誤（需求規格 6.2、ID-03）；手動輸入的父母名不比，同 4.2「同一匹馬」。
  - 產駒的馬名已經匯入確認、與第 1 欄或第 77 欄不同時，資料更正改用新名，其他套用方式為錯誤（6.4；只有基本馬名不同也算，經匯入確認的名稱任一部分都不在一般套用下改寫，使用者 2026-10-08 決定）。
  - 第 1 欄只有前綴、沒有馬名，或第 77 欄空白時為錯誤（6.4 的「警告並略過該筆」）。
  - `splitHorseName(第 1 欄)` 的基本馬名與第 77 欄不同時警告，照樣套用，基本馬名取第 77 欄（使用者 2026-10-07 決定）。
  - 「這一局另一匹馬已有相同的能力番号與出生年」只由寫入操作檢查（4.3「一月總表的正式馬名」的 `same-horse`），預覽不預檢：只有同一局有出生年相同、手動填了相同能力番号的非自家產駒時才會碰到，這時預覽顯示可套用，套用時整筆回復並指出是哪一項（使用者 2026-10-08 決定）。
- **使用者指定**：`previewJanuary(entries, snapshot, mode, picks)` 的 `picks` 是「產駒 → 行號」，畫面每指定一次就重新預覽（一千多列與幾十匹產駒，純函式重算即可），指定後的衝突直接出現在預覽的錯誤裡。指定的產駒要是配不到或無法唯一配對的待核對產駒，那一列要在檔案裡、不能已配給別的產駒（自動配對或其他指定），出生年要與產駒相同，否則丟出 `RangeError`（畫面不會送出）；未見於總表的產駒不能指定（需求規格 11.3，使用者 2026-10-07 決定）。
- **預覽的結果**：出生年（年份減 2，供使用者確認，11.3）；配成的對（產駒、行號、配對方式：能力番号、父母或指定；要做的變更：原本與新的完整馬名、會不會留別名、補上的能力番号、新的競走馬馬番号；警告）；錯誤（行號、產駒與原因）；待核對的產駒（原因與候選行號，候選不含已指定給別的產駒的列）；IMP-05 的五種筆數：
  - 可套用：有變更的對的列數。
  - 略過：非管理的列，加上配成對但什麼都不用改的列。
  - 錯誤：錯誤的列數。
  - 待核對：還沒處理的產駒匹數；未見於總表的產駒沒有列，所以以匹計。
  - 警告：可套用的列中有警告的列數，是可套用的一部分。

  可套用、略過與錯誤加起來等於檔案的列數。
- **內容**：`januaryContent(preview)` 產生「流程」的內容：每一個可套用的對一個項目，不必改的對不產生項目。摘要的 `total` 是列數，`applied`、`skipped` 是可套用與略過的列數；`ImportSummary` 另加選填的 `pending`、`warnings`、`errors`，一月填待核對、警告與錯誤的筆數，其他類型沒用到時不存，4-2 的程式與測試不變。
- **項目**：`ImportPlanItem` 的第一種，`{ kind: 'foal-name', horseId, birthYear, fullName, baseName, abilityNumber, horseNumber }`，帶這一列的值（完整馬名取第 1 欄，基本馬名取第 77 欄，`horseNumber` 是競走馬馬番号）；要改什麼由寫入操作在交易內與目前的資料比對（4.3「寫入操作」的「一月總表的正式馬名」）。套用方式不放在項目裡，由 `applyImport` 依計畫傳入是不是資料更正。

## 5. 錯誤處理

對應需求規格 5.2 的三類處理：

| 類型 | 做法 |
| --- | --- |
| 阻止 | 核心回傳「阻止」結果，附上錯誤的一方與正確的系、代數；畫面顯示原因，不能保存 |
| 警告並確認 | 核心回傳警告清單；畫面逐項取得確認後，帶確認再呼叫寫入操作；確認內容寫進該次操作的事件、配種紀錄或匯入紀錄 |
| 資料來源異常 | 解析器回傳錯誤；依需求規格決定整份停止或略過該筆 |

- 規則檢查用回傳結果表達，不用例外；例外只用在預期外的失敗。
- 寫入操作在交易內重做規則檢查，阻止或尚未確認時什麼都不寫（4.3「寫入操作」）。
- 預期外的失敗讓 Dexie 交易回復，畫面顯示錯誤，資料不變。

9 個 CP932 樣本字元在 Edge 與 Chromium 解碼後，全部與 Windows 一致，沒有任何差異。

**決定**

- 不能用的項目只有「持久保存」：採用本節表格的替代做法「顯示未取得，加強備份提醒」。需求規格已有對應規則（12.2「持久保存」與 DATA-14），不修改需求規格。
- 其他項目（IndexedDB、SHA-256、gzip、CP932 解碼、選擇備份資料夾與重新授權、下載）都能用，照原設計實作，不需要替代做法；其中資料夾寫入與重新授權只在 Edge 測過。
- 備份資料夾在關閉瀏覽器再開啟後，第一次寫入需要由使用者操作觸發，並在瀏覽器詢問時允許；未授權時依需求規格 12.2 改為自動下載備份檔。
- 瀏覽器只在使用者剛操作後的短時間內允許重新授權（`requestPermission`）。年度匯入要在使用者按下「套用」時先申請權限，再做交易、檢查點等耗時處理；否則會取不到權限而每次改為自動下載。這個時機與非點擊觸發的自動下載，留給儲存計畫驗證（見下方「儲存整合的驗證」）。
- CP932 解碼結果與 Windows 全部一致，`ce-import` 不需要額外正規化，第 4.4 節不修改。
