# WPStudBook 技術設計

## 1. 文件資訊

- 對應需求：[需求規格](需求規格.md)
- 最後更新：2026-09-23

## 2. 決策摘要

| 項目 | 決定 | 主要理由 |
| --- | --- | --- |
| 成品形式 | 單一 HTML 檔，以 `file://` 在 Windows 最新版 Edge／Chrome 離線使用 | 免安裝、工具鏈最單純；資料安全以備份強化補足（需求規格 12.2） |
| 語言 | TypeScript（strict） | 規則、匯入與畫面同一種語言 |
| 前端框架 | Vue 3（`<script setup>`）＋Pinia＋Vue Router（hash 模式） | 模板接近 HTML、狀態管理直覺、生態成熟；`file://` 只能用 hash 路由 |
| 可及性元件、大清單 | Reka UI、TanStack Virtual | 對話框、頁籤、清單已處理鍵盤與焦點；匯入預覽與清單需要虛擬捲動 |
| 建置 | Vite＋`vite-plugin-singlefile` | JS、CSS 全部內嵌，輸出 `WPStudBook.html` |
| 資料庫 | IndexedDB＋Dexie | 結構版本升級、複合索引、批次寫入與交易 |
| 測試 | Vitest、`fake-indexeddb`、Vue Test Utils、Playwright | 核心與資料庫層在 Node 測；端對端以 `file://` 開建置出的單檔 |
| 程式風格 | ESLint（Vue、TypeScript 規則）＋Prettier | |
| 執行環境 | Node 24、npm | 本機已安裝；`package-lock.json` 納入版控 |

瀏覽器內建能力直接使用，不加套件：CP932 解碼（`TextDecoder`）、gzip（`CompressionStream`）、SHA-256（`crypto.subtle`）。只有測試用的 CP932 範例檔需要在 Node 產生，因此加入開發用套件 `iconv-lite`。

## 3. 考慮過但未採用

- **桌面版（WPF＋WebView2 或 MAUI HybridWebView）**：好處是資料存成本機檔案、可監看 CE 匯出資料夾、可用 SQLite 查詢。未採用的原因：一年只匯入 4～5 次，拖放檔案不麻煩；單局幾萬筆資料在瀏覽器記憶體內計算就夠快；真正的差別只剩資料安全，改以需求規格 12.2 的持久保存與自動備份處理。桌面版還要重寫需求規格第 12、14 章，並多一套 .NET 工具鏈。日後若改走桌面，建議 WPF＋Blazor Hybrid（規則、資料、畫面全用 C#），不建議 MAUI（只用 Windows 時多出 WinUI 3 與打包的複雜度）。
- **React**：生態與可及性元件（React Aria）最完整，但 hooks 的依賴陣列與重複渲染較容易出錯，程式也較不像 HTML。
- **Svelte 5**：程式碼最少，但生態較小，寫法與一般 HTML 差異較大。

## 4. 架構

### 4.1 模組與依賴方向

| 模組 | 路徑 | 責任 | 可依賴 |
| --- | --- | --- | --- |
| 核心 | `src/core/` | 領域模型與規則，全部是作用於一般資料的純函式 | 無（不得引用 Vue、Dexie、DOM 或其他 `src` 模組） |
| CE 匯入 | `src/ce-import/` | 匯出檔解碼、解析、驗證、身分比對、差異預覽、產生套用計畫 | `core` |
| 儲存 | `src/storage/` | Dexie 資料庫、套用計畫的單一交易寫入、檢查點、備份與還原、持久保存、備份資料夾 | `core` |
| 畫面 | `src/ui/` | Vue 元件、頁面、Pinia store、路由 | 以上全部 |
| 進入點 | `src/main.ts` | 建立 Vue 應用、開啟資料庫、申請持久保存 | 以上全部 |

依賴方向以 ESLint 的 `no-restricted-imports` 強制：`core` 不得引用其他模組；`ce-import` 與 `storage` 只能引用 `core`；沒有模組可以引用 `ui`。

### 4.2 核心的內容

- 系位置、建系分支與新系編號（需求規格 7.3）、兩兩互換配對表（4.3）。
- 產駒的系與代數，替代母馬以她替代的代數計（8.2）。
- 任務產生：可開啟的分支、循環任務、世代交接（7.3、7.4）；斷血補系的補公系配對、補母系、暫停與結束，以及宣告補系前的檢查（7.6）。
- 規則檢查：阻止（10.3）、警告並確認（8.3、10.2）、零代種牡馬例外補入（7.3）。
- 血統推算：3 代前 8 匹祖先、推定父親的系統與始祖例外、4 代內重複（10.2），以及活血種數與「至少 N 種」的判斷（4.3、10.2）。
- 系統對照表查詢：子系統的親系統與分出來源、八系親系統的種類數與重複（7.2）。
- 同一匹馬的判斷（6.2）；姊妹接替狀態與代的成立（8.9、8.2）；母馬的定年、高齡與出售母親提醒，以及是否列入任務（8.5）。
- 種牡馬的兄弟比較、選定現任、替換時的系統比對與年齡提醒（7.7）；正式後繼的核對（9.6）。
- 產駒的追蹤名與 `サ`（9.3、9.4）。

`docs/specs/八系巡迴圖.html` 裡的配對與血統推算是這部分的參考實作，移入核心時改寫成 TypeScript 並補上測試。

#### 規則輸入快照

核心不定義資料表結構，也不保存狀態。規則以「規則輸入快照」為輸入，快照由儲存層依資料表彙整：

- 八個系位置各一筆：是否已開啟（建系起點或建立新系時已填寫系統與零代市場種牡馬，需求規格 7.1），以及各代種牡馬狀態與各代母馬群。
- 種牡馬狀態每（系, 代）一個值（需求規格 7.7）：在崗；已指定但還沒正式供用（尚未誕生、競走中、已引退待指定）；已離場，指退出生產行列或已引退、而且同一代沒有其他在崗或已指定的種牡馬。
- 母馬群每（系, 代）一筆：是否已成立（第一匹自家母駒以暫定或正式保留轉入，需求規格 8.2，依 `establishesGeneration` 判斷；只有替代母馬時為未成立）、列入任務的母馬數（依 `mareListedInTasks`：在繁殖圈內、未達定年，自家母駒還要是暫定保留、候選或正式保留），以及其中的自家母馬數（建立新系時由使用者判斷自家母馬是否不足，需求規格 7.3；不得多於列入任務的母馬數）。母馬歸哪個母馬群依 `damPlacement`：自家母駒依出生紀錄的系與代數，替代母馬依她替代的系與代數，起點母馬歸第 1 系起點母馬群；待指定用途的市場母馬（需求規格 8.4）與自由配種所生的母駒（11.5）不屬於任何母馬群，不計入。
- 第 1 系 0 代母馬群就是第 1 系起點母馬群。
- 已宣告的斷血補系（需求規格 7.6）：每系一份清單，每筆是斷血的代數與斷掉的一方（公系或母系）；補公系另帶補入的零代市場種牡馬狀態（與種牡馬狀態同樣三種，還沒選定時留空）。代數要在該系成立的代數以後，同一系同一代同一方只有一筆；使用者更正（撤銷）宣告時從清單移除。補入的零代市場種牡馬不放進該系的種牡馬狀態，零代那一格仍是建系時的零代市場種牡馬。補系結束後這一筆仍留在清單，因為補公系配對永久取代一般配對。補入的零代市場種牡馬依 7.7 提前引退並替換時，狀態取替換後那一匹，比照零代那一格。補公系配對產出 4 代以內（建系期）時，補入的零代市場種牡馬算 10.2 的建系期市場種牡馬，血統樹的建系期標記為是；循環期補入的不算（使用者 2026-09-24 決定）。
- 系統對照表：每個子系統一筆，含親系統與選填的分出來源；分出來源只用在始祖例外（10.2）。
- 八系目前的系統：每個系位置的目前子系統與親系統，系尚未開啟時兩者都沒有值。
- 血統樹：一次配種往上四代，每個位置是一匹馬或「沒有內部紀錄」。每匹馬帶內部識別（判斷 4 代內重複）、馬名（判斷始祖例外，10.2）、本身的父系，以及是不是建系期的市場馬（零代市場種牡馬或替代母馬，10.2 的例外判斷用）。
- 零代市場種牡馬的父系欄留空時，儲存層彙整快照時改填該系目前的子系統（需求規格 10.2）；核心只看快照裡的父系，不另外查系位置。

#### 任務看板的判斷

以下是需求規格 7.3、7.4、7.6、7.7 的詮釋，`src/core/board.ts` 依此實作：

- **到達某代**：該系該代有種牡馬紀錄（任何狀態），或該代母馬群已成立。只有替代母馬的母馬群不算。
- **可開啟的分支**：新系尚未開啟，且原系到達分支前一代。建系起點在第 1 系開啟前一直可開啟。
- **任務出現**：建系起點與建立新系在該系開啟後出現；推進原系在原系到達前一代時出現；循環任務在該系前一代有種牡馬紀錄、而且配對系前一代母馬群已成立時出現。
- **任務結束**：同系下一代任務已出現，而且這條任務的母馬群已沒有列入任務的母馬，或種牡馬已離場。
- **沒有下一代任務時**：母馬群已成立但沒有母馬，顯示「已成立，母馬群待補」；種牡馬已離場，任務暫停並顯示缺少現任種牡馬（零代時為缺少目標種牡馬）。
- 指定配種檢查只比對系與代數；種牡馬是否為現任，由任務看板的種牡馬狀態判斷。
- **補公系**：第 p 系 N 代宣告補公系後，第 p 系 N+1 代的指定配對固定為補公系配對（`restorationPairing`：第 p 系零代 × 原本指定的配對系 N 代母馬群），補系結束後也一樣。補公系任務宣告後就出現，種牡馬狀態看補入的零代市場種牡馬；世代交接照一般規則，所以斷血那一代的重試任務在原本的種牡馬離場或母馬全部離圈時結束。
- **補母系**：第 q 系 N 代宣告補母系後，配它的循環任務不等母馬群成立，配對系 N 代有種牡馬紀錄就出現。
- **補系進行中與結束**：補公系進行中，該系還沒開啟的分支都不能開啟；補母系不暫停。補公系在第 p 系 N+1 代有種牡馬紀錄（任何狀態）時結束，補母系在補系任務產出的那一代母馬群成立時結束；結束只解除暫停。看板列出每筆補系的補系任務與是否進行中。
- **宣告補系的檢查**（`checkRestoration`）：該系還沒開啟、那一代還沒成立、同一代同一方已經宣告，都阻止。補公系另外阻止：該系還沒到達那一代（沒有種牡馬紀錄，母馬群也沒成立）、那一代已有在崗或已指定的種牡馬、下一代已有種牡馬紀錄；那一代的種牡馬已離場時不阻止。補母系另外阻止那一代母馬群已成立。

#### 身分、母馬、種牡馬與後繼

以下是需求規格 4.6、6.2、7.6、7.7、8.1、8.5、8.9、9.3、9.4、9.6 在核心的輸入約定，以及規格沒有逐字寫出、由核心決定的判斷。儲存層與匯入層依此彙整輸入：

- **同一匹馬**（`identity.ts`）：只傳目前遊戲局的馬匹，馬番号不參與判斷。能力番号由匯入層與手動輸入統一寫法後保存與比對，`0x0000` 是有效值。馬名與父母名稱用基本馬名；還不是正式馬名的名稱（四月的「母馬名の0歳」、未命名的產駒）不傳。手動輸入、尚未經匯入確認的馬名要標 `manualName`：只用來輔助配對，與匯入名稱不同時不算衝突，由匯入名稱取代（需求規格 6.4、9.4、BRD-09）；經匯入確認的馬名不同時仍是衝突（ID-08）。兩邊都有值而且不同才算「明顯不符」，比較時忽略前後空白。以馬名輔助配對時，候選是馬名相符、出生年相同或未填的紀錄；候選兩筆以上，或能力番号與出生年配到兩筆以上，都列為衝突（需求規格 11.5「無法判斷的身分列入衝突」）；輔助配對到的紀錄父母明顯不符也是衝突；以馬名配到的紀錄已有不同的能力番号時也是衝突，不得覆寫。同一匯入檔內重複的能力番号由 `duplicateAbilityNumbers` 列出，只看能力番号、不看出生年，有任何一個時整份停止套用。一月總表以父馬、母馬、出生年配對舊產駒（11.3）屬於匯入層。
- **姊妹接替**（`sisters.ts`）：同父同母以父母的內部識別判斷，任一方不明就不算姊妹。「在圈」指在繁殖圈內，被取代但還沒賣出的姊妹也算。選定正式保留時，只把在圈而且列入任務的姊妹改為已被取代。輸入有在圈但狀態是已售出的母馬時丟 `RangeError`。
- **母馬的年齡與列入任務**（`mares.ts`）：定年與高齡提醒年齡由儲存層從設定帶入，預設 25、18 歲。高齡提醒只在未達定年時顯示，因為已達定年的母馬不能賣出（需求規格 4.6）。五月缺席的預設原因只看上次五月的馬齡，被取代的姊妹也照同一條規則；馬齡不明時預設售出。列入任務時馬齡不明當作未達定年。出售母親提醒只看暫定保留或正式保留的女兒。馬齡不是 0 以上的整數時丟 `RangeError`。
- **種牡馬**（`stallions.ts`）：兄弟比較以比較對象（通常是現任）為準，選入的要同系、同代、同父，任一方的父馬不明就不算同父。選定現任只把同系同代原本在崗的一匹改為已被取代；前任、後任、生效年與原因由儲存層保存。市場種牡馬替換零代種牡馬，或補公系補入零代市場種牡馬（需求規格 7.6）時，比較他本身的父系與該系目前的子系統，父系不明時不警告；他的子系統沒登錄在對照表、查不到親系統時，仍回報親系統不同，讓畫面提示補登。現任的提醒年齡由設定帶入，預設 26 歲。`StallionStatus` 的 `retired` 是種牡馬已引退；預定後繼的「已引退待指定」（競走馬已引退、還沒接任）對應 `status` 留空，不是 `retired`，否則 `chooseIncumbent` 會拒絕接任。
- **正式後繼**（`successor.ts`）：用出生紀錄連結的配種紀錄的規則快照（實際種牡馬的系與代數、母馬當時的身分）核對，不用母馬目前的用途，因為用途修改從下一次配種才生效（需求規格 8.4）。除了父母與重算的系與代數，也以 10.3 確認這次配種是出生紀錄那一代的指定配對，所以偏離規則配到別系種牡馬的產駒會被阻止（5.2；10.3「刻意偏離請登記為自由配種」，使用者 2026-09-23 確認）。沒有配種紀錄、或配到八系以外種牡馬的產駒比照自由配種。`verifySuccessor` 的第二個參數是要進入的母馬群，或要接任、指定為預定後繼的系與代數，與出生紀錄不符時阻止。補公系所生的產駒，配種紀錄的規則快照要記 `restoration`，以補公系配對核對（需求規格 7.6）；補母系所生的產駒是一般指定配對，照常核對。
- **產駒名稱與 `サ`**（`foal.ts`）：追蹤名用母馬的基本馬名加實際出生年，不帶 `(外)`、`[地]` 前綴（產駒在自家牧場出生，前綴不適用；使用者 2026-09-23 決定）；正式馬名是空字串或只有空白時視為清空，回退追蹤名。`サ` 由 `checkSubAbilityTotal` 計算並與匯入值比對：七項副能力都有等級時才計算，沒有匯入值時不比對。等級文字只接受 `G`～`S+`，匯入層用 `isSubAbilityGrade` 判斷欄位內容。

### 4.3 儲存

- Dexie 資料表依需求規格的實體劃分：遊戲局、馬匹、階段馬番号、系位置與系統歷程、系統對照表、繁殖紀錄、事件（離圈、回歸、轉場、改名、更正等）、匯入紀錄、檢查點、設定。
- 索引照需求規格 12.5；每張表都帶遊戲局欄位，所有查詢以遊戲局為前提。
- 結構版本用 Dexie 的版本升級管理；備份檔的結構版本與遷移沿用同一套版本號。
- 檢查點：整局資料以 gzip 壓縮後存入檢查點表，記錄年、時點、時間與 SHA-256（12.4）。

### 4.4 資料流：年度匯入

以五月繁殖圈名單為例，對應需求規格 11.1 的流程：

1. 畫面取得檔案（選檔或拖放，一次一個）。
2. `ce-import` 解碼 CP932、判斷分隔字元、依位置讀欄，並從檔名解析年與時點。
3. `ce-import` 用 `core` 比對身分，產生差異預覽：繼續在圈、新進、回歸、缺席、衝突，以及用途把關。
4. 畫面顯示預覽，使用者修改用途並確認需要確認的警告。
5. `ce-import` 產生套用計畫，也就是要新增、更新哪些資料，要建立哪些事件。
6. `storage` 在單一 Dexie 交易內寫入計畫；接著建立檢查點，並依需求規格 12.2 自動備份。
7. 畫面顯示結果摘要。

任一步發生阻擋錯誤時，交易不會開始，或者整筆回復，資料保持不變。

## 5. 錯誤處理

對應需求規格 5.2 的三類處理：

| 類型 | 做法 |
| --- | --- |
| 阻止 | 核心回傳「阻止」結果，附上錯誤的一方與正確的系、代數；畫面顯示原因，不能保存 |
| 警告並確認 | 核心回傳警告清單；畫面逐項取得確認，確認內容寫進配種或匯入紀錄 |
| 資料來源異常 | 解析器回傳錯誤；依需求規格決定整份停止或略過該筆 |

- 規則檢查用回傳結果表達，不用例外；例外只用在預期外的失敗。
- 預期外的失敗讓 Dexie 交易回復，畫面顯示錯誤，資料不變。

## 7. 技術驗證（實作第一步）

先做一個最小的驗證頁，建置成單檔後，以 `file://` 在 Edge 與 Chrome 逐項確認：

| 項目 | 不能用時的替代做法 |
| --- | --- |
| IndexedDB 讀寫、重新整理後資料仍在 | 無替代，須能用 |
| `navigator.storage.persist()` 能否取得持久保存 | 顯示未取得，加強備份提醒 |
| `crypto.subtle` 的 SHA-256 | 改用純 JS 的 SHA-256 實作 |
| `CompressionStream`／`DecompressionStream` | 改用純 JS 的 gzip 套件（需求規格 12.2 已允許改輸出 `.json`） |
| `TextDecoder('shift_jis', { fatal: true })` | 改用純 JS 的 CP932 解碼 |
| 檔案系統存取（選擇備份資料夾、寫入檔案、下次開啟時重新授權） | 年度匯入後自動下載備份檔 |

驗證結果寫回本文件，再開始正式實作。

### 驗證結果（2026-09-22）

**測試環境**

- Microsoft Edge 153.0.4234.48（本機安裝版；版本取自安裝的瀏覽器，不是 `edge.json` 的 `userAgent`——那是 Playwright「Desktop Edge」裝置描述檔的固定字串）。
- Chromium：Playwright 1.63.0 附帶的 Chromium 153.0.8010.12（Chrome for Testing）。
- Chrome 未測，以 Playwright Chromium 代替（本機未安裝 Chrome）。
- 開啟方式：`file://` 開啟 `app/dist/WPStudBook.html`。

**結果表**

| 項目 | Edge（自動測試） | Chromium（自動測試） | 手動測試（Edge，一般視窗） |
| --- | --- | --- | --- |
| IndexedDB 讀寫、重新整理後資料仍在 | 可用（重新整理、關閉再重新開啟瀏覽器後資料都仍在） | 可用（重新整理、關閉再重新開啟瀏覽器後資料都仍在） | 與自動測試一致，未另外手動測試 |
| `navigator.storage.persist()` 持久保存 | 不能用（申請後仍為 false） | 不能用（申請後仍為 false） | 原本已持久：false；申請結果：false（已用 888235 bytes／配額 10738306475 bytes）→ 未取得持久保存 |
| `crypto.subtle` 的 SHA-256 | 可用 | 可用 | 未另外手動測試 |
| `CompressionStream`／`DecompressionStream`（gzip） | 可用 | 可用 | 未另外手動測試 |
| `TextDecoder('shift_jis', { fatal: true })`（CP932 解碼） | 可用 | 可用 | 未另外手動測試 |
| 檔案系統存取（選擇備份資料夾、寫入、重新授權、下載） | 偵測到 `showDirectoryPicker`；下載可用；寫入與重新授權見手動測試 | 偵測到 `showDirectoryPicker`；下載可用；寫入與重新授權未測 | 選擇備份資料夾並寫入成功；關閉 Edge 再重新開啟後按「用上次的資料夾寫入」，瀏覽器跳出權限詢問，允許後寫入成功、檔案時間有更新；下載測試檔成功 |

`file://` 下 `secure-context` 為 true（視為安全環境）。Playwright 端對端測試（`npm run test:e2e`）在 Edge 與 Chromium 各 5 項全數通過，涵蓋 IndexedDB（含重新整理與關閉再重新開啟瀏覽器）、SHA-256、gzip、CP932 解碼、下載與讀取 CP932 範例檔；持久保存只記錄結果、不做斷言；資料夾寫入與重新授權只在 Edge 手動測試。

**CP932 與 Windows 對照**

9 個 CP932 樣本字元在 Edge 與 Chromium 解碼後，全部與 Windows 一致，沒有任何差異。

**決定**

- 不能用的項目只有「持久保存」：採用本節表格的替代做法「顯示未取得，加強備份提醒」。需求規格已有對應規則（12.2「持久保存」與 DATA-14），不修改需求規格。
- 其他項目（IndexedDB、SHA-256、gzip、CP932 解碼、選擇備份資料夾與重新授權、下載）都能用，照原設計實作，不需要替代做法；其中資料夾寫入與重新授權只在 Edge 測過。
- 備份資料夾在關閉瀏覽器再開啟後，第一次寫入需要由使用者操作觸發，並在瀏覽器詢問時允許；未授權時依需求規格 12.2 改為自動下載備份檔。
- 瀏覽器只在使用者剛操作後的短時間內允許重新授權（`requestPermission`）。年度匯入要在使用者按下「套用」時先申請權限，再做交易、檢查點等耗時處理；否則會取不到權限而每次改為自動下載。這個時機與非點擊觸發的自動下載，留給儲存計畫驗證。
- CP932 解碼結果與 Windows 全部一致，`ce-import` 不需要額外正規化，第 4.4 節不修改。
