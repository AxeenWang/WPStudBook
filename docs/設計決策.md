## 4. 目錄與分層（D-07）

> 2026-09-15 變更：程式專案移入 `app/`，應用服務層由 `app` 改名為 `services`。原因：第 1 版把程式專案放在 repo 根目錄，與文件、專案規則混在一起；若外層改名 `app/` 而服務層仍叫 `app`，會出現意思重複的 `app/src/app`。

### 4.1 Repository 版面

```text

  AGENTS.md、AGENTS_cht.md、CLAUDE.md、.gitignore
  .github/                      GitHub Actions（GitHub 規定必須放在根目錄）
  docs/                         需求規格、開發計畫、驗收追蹤、設計決策、實作計畫
  .references/                  使用者提供的實檔（不進版本控制）
  .claude-tmp/、.codex-tmp/     Agent 暫存區（不進版本控制）
  app/                          程式專案：所有程式、設定、依賴與建置測試產出
    package.json、package-lock.json、tsconfig.base.json、tsconfig.json、WPStudBook.html
    vite.config.ts、vitest.config.ts、playwright.config.ts
    eslint.config.js、eslint.layers.js、.prettierrc.json、.prettierignore
    src/  tests/  scripts/
    node_modules/  dist/  test-results/  playwright-report/   （不進版本控制）
```

- 規則寫在專案 `AGENTS.md` 的 Repository Layout，所有 agent 都必須遵守。
- npm、建置、程式檢查與測試指令一律在 `app/` 內執行；不得在根目錄執行 `npm install` 或建立工具設定。
- 新增根目錄檔案或資料夾前，必須取得使用者同意。
- 資料夾名稱不得重複上層的意思，例如 `source/src`、`app/src/app`。
- 程式從 `app/` 讀取 repo 根目錄的資料時使用相對路徑，例如 `../docs/需求規格.md`、`../.references/`。
- 2026-09-15 補充：TypeScript 設定分成 `tsconfig.base.json`（共用編譯選項）、`tsconfig.json`（測試、腳本與設定檔，含 Node 型別）與 `src/tsconfig.json`（瀏覽器程式，不含 Node 型別）。原因：階段 0 單一設定讓瀏覽器程式也看得到 Node 型別，誤用 Node API 時型別檢查不會發現。

### 4.2 程式專案（`app/`）與分層

```text
app/
  src/
    domain/    純函式規則：身分判斷、系與代數、建系分支與循環任務、血統檢查、匯入責任與差異
    import/    解碼、分隔、依位置取值、各格式解析器 → 產生預覽資料，不寫資料庫
    storage/   IndexedDB 結構與交易、備份還原、檢查點
    services/  應用服務：每個完整操作（配種、匯入套用、回溯…）組合 domain、import、storage
    ui/        React 畫面與元件
    main.tsx
  tests/
    unit/         domain 與 import 解析、services 個別函式、scripts 工具腳本測試（Node）
    integration/  services ＋ storage（Node ＋ fake-indexeddb）
    e2e/          Playwright，只測建置後的 app/dist/WPStudBook.html
    references/   本機實檔測試（見本文件 7.4 節）
    fixtures/     合成樣本產生器的設定
  scripts/        合成樣本產生器、情境覆蓋清單等工具
```

> 2026-09-15 補充：`tests/unit/` 也包含 `services` 個別函式（例如 `environment-check.ts`）與 `scripts/` 工具腳本自身的測試，不只 domain 與 import 解析。

引用規則以 ESLint（`no-restricted-imports`、`no-restricted-globals`）強制，違反時檢查失敗：

| 層 | 可以引用 | 不可引用 |
| --- | --- | --- |
| `domain` | 只用標準 JavaScript | 其他各層、React、`idb`、瀏覽器全域物件（`window`、`document`、`indexedDB`、`localStorage` 等） |
| `import` | `domain` | `storage`、`services`、`ui`、React、`idb` |
| `storage` | `domain`（只限型別） | `import`、`services`、`ui`、React |
| `services` | `domain`、`import`、`storage` | `ui`、React |
| `ui` | `services`；`domain`（只限型別） | `storage`、`import`、`idb` |

- 2026-09-15 補充：`src/main.tsx` 只能引用 `ui`；`src` 全部禁止動態 `import()`，並禁止對外連線、裝置存取與直接存取檔案系統的 API（`fetch`、`WebSocket`、`EventSource`、`navigator.sendBeacon`、`showSaveFilePicker` 等），作為 BLD-04「不附加遊戲程序、不讀記憶體、不控制 CE、不寫回遊戲」的程式檢查。原因：階段 0 的規則沒有涵蓋 `main.tsx` 與動態 import，BLD-04 也需要可自動執行的證據。

## 5. 資料契約第 1 版（D-08）

### 5.1 總原則

1. **主鍵 `[gameId, id]`**：各局資料表的主鍵都是 `[gameId, id]`，`id` 只需在同一局內唯一（`crypto.randomUUID()`）。還原為新遊戲局時只換 `gameId`，互相引用的 `id` 不必重編；刪除整局只刪一個主鍵範圍。
2. **目前狀態＋事件歷程**：紀錄保存目前狀態供查詢，每次變更在同一個交易內寫入 `events`，歷程只新增不改寫（5.3）。寫入遊戲局資料時，遊戲局的更新時間與程式版本在寫入交易內讀出遊戲局後合併更新，不以操作開始時讀到的舊紀錄覆蓋。（2026-09-15 補充，階段 2-1。原因：以操作開始時讀到的整筆紀錄寫回，會把期間其他遊戲局層級的寫入靜默還原，例如最近備份或其他分頁更新的目前遊戲年。）
3. **唯一規則做成唯一索引**：規格要求唯一的組合，建立 IndexedDB 唯一索引作為第二道防線。IndexedDB 不會為缺少索引欄位的紀錄建索引，因此未填能力番号的手動紀錄不受「能力番号＋出生年」唯一索引限制，符合 6.2。
4. **可推導的資料不存**：任務、年齡、母馬群數量、追蹤名、輪空、場地型摘要都由現有資料推導（5.3）。規則快照例外，必須保存（7.4）。

- **名稱查詢**：IndexedDB 的多值索引不能和複合鍵合用，所以 `horses.nameKeys` 存成「`gameId` ＋ 分隔字元 ＋ 名稱」的字串陣列，包含完整馬名、基本馬名、正式馬名與別名，供匯入時的精確名稱對照（11.8 父馬名稱對照等）。`nameKeys` 不收錄於備份（本文件 5.4 節）。
- **關鍵字搜尋**：部分比對無法使用索引，在記憶體中比對已載入的名稱與別名（13.3、12.5）。
- 2026-09-15 補充：`games` 保存 `appVersion`，對應需求規格 12.1「版本」。整局層級事件的 `subjectId` 固定為 `game`，不使用 `gameId`，還原為新遊戲局時不必改寫；事件型別目前有 `gameYearChanged`（目前遊戲年變更）與 `schemaMigrated`（結構遷移），各階段新增時補列。還原與回溯本身不寫事件，讓還原後的集合筆數與來源一致；經過遷移時寫一筆 `schemaMigrated`。

### 5.3 值的表示

| 情況 | 表示方式 | 例子 |
| --- | --- | --- |
| 未取得、未知 | 欄位不存在。不用 `null`、`-1` 等特殊值，不存 `undefined` | 手動新增時沒填的仔出、父馬 |
| 空白本身有意義 | 只有規格明寫空白意義的欄位存空字串 `""` | 牝系空白＝不屬於具名牝系（8.8） |
| 多種狀態 | 明確列舉每種狀態 | 活力 `{ state: 'notApplicable' }`、`{ state: 'pending' }`、`{ state: 'confirmed', value, boosted }`；受胎狀態欄位不存在＝未登記，否則存日文原文 `空胎`、`受胎`、`不受胎`、`未確認` |
| 番号 | 整數 0～65535；顯示為 `0x` 開頭的 4 位大寫十六進位 | `0x0000` 存為 `0`，是有效值 |
| 布林 | 只用於真正只有是否的事實，不代表未知 | `boosted`、`freeBred`、`pinned` |
| 遊戲時間 | 遊戲年、月、週各為整數 | `gameYear: 1968`、`timing: { month: 5, week: 1 }` |
| 現實時間 | ISO 8601 UTC 字串 | `2026-09-14T12:00:00Z` |
| 系統名稱 | 去掉結尾「系」 | `エクリプス系` → `エクリプス` |
| 馬名 | 保留原文，不做全面修剪（11.1） | — |

### 5.4 備份格式

```json
{
  "format": "WPStudBook-backup",
  "schemaVersion": 1,
  "appVersion": "0.1.0",
  "exportedAt": "2026-09-14T12:00:00Z",
  "game": { "name": "…", "startYear": 1968, "currentYear": 1969 },
  "counts": { "horses": 1234, "mares": 88 },
  "sha256": "…",
  "collections": { "gameSettings": [ … ], "horses": [ … ], "mares": [ … ] }
}
```

- **收錄範圍**：`collections` 收錄該局除了 `checkpoints`、`checkpointData` 以外的所有資料表。檢查點是本機回溯點，本身就是備份，不重複收錄。`archives` 與 `appMeta` 屬於應用層，不收錄。`games` 以 `game` 摘要（名稱、起始年、目前遊戲年）表示，不放在 `collections`；`gameSettings` 在備份中是只有一筆、不含 `gameId` 的陣列；`counts` 列出 `collections` 的每個資料表，0 筆也列出。
- **不存 `gameId`**：備份內的紀錄都不帶 `gameId`，匯入時才加上目標局的 id，因此還原為新遊戲局不必改寫資料，也不會混入其他局。含 `gameId` 或可由其他欄位重建的推導欄位也不收錄：`horses.nameKeys` 匯出時剔除、匯入時忽略，由寫入馬匹的程式依名稱欄位重建（階段 2 實作）。（2026-09-15 補充：`nameKeys` 含 `gameId`，原設計還原為新遊戲局後會指向舊局。）
- **SHA-256**：以 `{ "collections": …, "game": … }` 的標準化 JSON 計算。規則是欄位名依字典序排序、每個資料表的紀錄依 `id` 排序、陣列保持原順序、不含空白、UTF-8 編碼。同樣的資料永遠得到同樣的雜湊。（2026-09-15 變更：雜湊範圍加入 `game` 摘要。原因：原本只算 `collections`，局名、起始年與目前遊戲年被修改時無法發現。）
- **壓縮**：支援 `CompressionStream` 時輸出 `.json.gz`，否則輸出 `.json`（12.2、DATA-06）。匯入時以檔頭 `1F 8B` 判斷是否為 gzip，不看副檔名。
- **匯入順序**：解析 → 格式與版本 → 筆數 → 雜湊 → 遷移 → 欄位 → 識別與關聯 → 預覽 → 單一交易寫入。任一步失敗時資料不變（12.2、DATA-04）。（2026-09-15 變更：原順序為「解析 → 格式與版本 → 欄位 → 關聯 → 筆數 → 雜湊」。原因：筆數與雜湊必須以檔案原版本的內容驗證，欄位與關聯規則以目前版本定義，所以遷移放在雜湊之後、欄位之前。）
- **欄位規則**：`horses`、`lines`、`systemMap`、`stallionDuties`、`mares`、`mareYearly`、`breedings`、`matingRatings`、`foals`、`events` 依 `app/src/storage/backup/record-rules.ts` 檢查必填欄位、型別、列舉值與範圍；其他資料表在定義型別的階段補上規則，之前只檢查通用規則（物件、非空 `id`、不含 `gameId`、只含 JSON 值）。規則不檢查未列出的欄位。（2026-09-15 補充，階段 2-1。`mares`、`mareYearly` 於階段 2-2 加入，`breedings`、`foals` 於階段 2-3 加入，`matingRatings` 於階段 2-4 加入。）
- **原始資料匯出**：本機資料不符合資料契約、無法產生備份時，資料管理頁提供「匯出原始資料」：不驗證、不壓縮，`format` 為 `WPStudBook-raw-export`、`restorable` 為 `false`，內容是遊戲局紀錄與全部備份資料表的原樣快照，檔名含「原始資料_不能還原」；只供保存與除錯，匯入時以格式不符拒絕，也不記錄最近備份。（2026-09-15 補充，階段 2-1。原因：欄位規則變嚴後，本機資料一旦不符合契約，備份與檢查點都會被擋下，使用者需要保留資料的出口。）

### 5.5 檢查點與封存

- **檢查點**：內容就是該局的 gzip 備份（本文件 5.4 節），存在 `checkpointData`。回溯時先驗證備份，再以單一交易取代該局資料（12.4）。
- **封存**：封存檔也是同一種格式（12.3）。
- 備份、檢查點、封存共用同一套序列化與驗證程式。

### 5.6 版本遷移

- `schemaVersion` 是整數，從 1 開始，IndexedDB 版本與備份格式共用同一個號碼。
- 每次結構改版提供：
  1. 把第 N 版 `collections` 轉成第 N+1 版的純函式。
  2. IndexedDB 升級時資料表與索引的調整；本機資料的轉換呼叫同一個純函式。
- 舊版備份與檢查點依序逐版遷移，並寫入一筆遷移事件（DATA-05）。比目前程式新的版本一律拒絕（DATA-04）。
- `appVersion` 是程式版本，與 `schemaVersion` 分開；只改介面不升結構版本。
- 2026-09-15 補充（階段 2-1）：階段 2 期間 `schemaVersion` 維持 1。已經有欄位規則的資料表，合併後只能新增選填欄位或新的列舉值；新增必填欄位、收緊既有規則或改變欄位意義時，必須升級結構版本並提供遷移。較舊的程式讀取較新程式產生、含新欄位值或列舉值的備份時，會以欄位錯誤（`recordInvalid`）拒絕，而不是未來版本（`futureVersion`）。

### 7.6 `file://` 的 IndexedDB 共用範圍（階段 1 驗證）

2026-09-15 補充。原因：需求規格 12.2 原本提醒「搬移 HTML 會看不到原資料」，階段 1 收尾前以實際瀏覽器驗證，結果不成立；已依使用者裁定更正需求規格 12.2 與頂部狀態列的提醒。

方法：以 Playwright 驅動本機 Edge（headless），把同一份建置檔複製到兩個不同資料夾，另寫一個不含 WPStudBook 程式、檔名與資料夾都不同的本機 HTML，全部以 `file://` 開啟；先在同一個瀏覽器 context 內比對，再開一個新的 context 對照。

| 項目 | 結果 |
| --- | --- |
| 驗證日期 | 2026-09-15 |
| 本機 Edge | 153.0.4234.32（Playwright `msedge` channel） |
| `location.origin`／`self.origin` | 每個頁面都是 `"file://"`／`"null"`，與檔名、資料夾無關 |
| 同一建置檔放在兩個資料夾，同一 context | 第二份的頂部狀態列與直接讀取資料庫，都看到第一份建立的遊戲局（同一筆 `id`） |
| 無關的本機 HTML，同一 context | `indexedDB.databases()` 列出 `wpstudbook`，可開啟並讀出全部資料表名稱與遊戲局紀錄 |
| 新的瀏覽器 context | 看不到上述遊戲局；資料庫是該 context 開啟程式時自己建立的空資料庫 |

結論：

- Edge 的 `file://` 頁面在同一瀏覽器設定檔內共用一個儲存來源，IndexedDB 不依檔名或資料夾分開。搬移、複製或改名 HTML 檔仍看得到原資料；換到其他設定檔（本次以新的 browser context 代表）則看不到。
- 同一設定檔中開啟的任何本機 HTML 都能開啟並讀取 `wpstudbook` 資料庫。本次只驗證讀取；寫入受同一個儲存來源規則管轄，推定同樣可行。
- 限制：不同設定檔的隔離以 Playwright 新的 browser context 代表，沒有實際切換 Edge 設定檔；Chrome 同為 Chromium 核心，本次沒有另外驗證。

## 8. 版本號、分支與 CI（D-11、D-12）

### 8.1 版本號

- `appVersion`：開發期間 `0.x.y`，完成一個計畫階段升 x、修正升 y；符合計畫第 10 章第一版完成定義時發布 `1.0.0`。建置時由 `package.json` 帶入，頁面與備份檔都可看到。
- `schemaVersion`：本文件 5.6 節，只在資料結構改變時升級。

### 8.2 分支流程

- 分支名稱沿用「主題_YYYYMMDD」，例如 `source_20260914`。
- 程式與文件修改一律走：主題分支 → `/repo-push` → `/repo-open-pr` → CI 通過 → 合併 → `/repo-clean-branch`，不直接推送 `main`。變更只涉及 `docs/` 或 Markdown 檔的 PR 會跳過端到端測試。
- 合併使用 GitHub 預設的 merge commit，保留每個 commit，不改寫歷史。
- 「CI 通過才能合併」的分支保護屬於 repo 設定，需使用者另外同意後才設定。

### 8.3 CI（GitHub Actions）

| 工作流程 | 觸發 | 內容 |
| --- | --- | --- |
| `ci.yml` 檢查 | PR、推送到 `main` | Ubuntu：`npm ci` → lint → typecheck → 單元與整合測試 → 建置 → 檢查成品沒有外部載入 → 保存建置檔 |
| `ci.yml` 端到端 | 檢查通過後；變更只涉及 `docs/` 或 Markdown 檔時跳過 | Windows：取用上一步的建置檔，以 Playwright 驅動 Edge 與 Chrome 各執行一次；失敗時保留 trace、截圖與報告 |
| `release.yml` 發布 | 推送 `v*` 標籤 | 重跑建置與測試 → 建立 GitHub Release 並附上 `WPStudBook.html` |

- 工作流程預設只有讀取權限，只有發布流程可以寫入 Release。
- 工作流程以 `app/` 為指令的預設工作目錄；上傳與下載建置檔的路徑為 `app/dist/`。
- 2026-09-15 修正：`ci.yml` 端到端失敗時原訂保留「錄影」，實作已停用影片錄製並改為 trace 與失敗自動截圖，因 Playwright 影片錄製需要另外下載 ffmpeg 執行檔，而本計畫不下載額外執行檔（見 `app/playwright.config.ts`）；上表已同步修正。
- Node 版本固定為 24，依賴以 `app/package-lock.json` 鎖定。
- CI 只使用合成樣本，不接觸 `.references/`。
- repo 根目錄的 `.gitignore` 加入 `node_modules/`、`dist/`、`test-results/`、`playwright-report/`、`tests/fixtures/generated/`；規則不帶前導斜線，因此涵蓋 `app/` 內的產出。
- 2026-09-15 補充：第三方 action 一律以 commit SHA 釘選並在行尾註明版本，升級時同步更新兩個工作流程；`release.yml` 先確認標籤指向 `main` 上的 commit 才建置，端到端失敗時同樣保留報告。
